# 清涵课表 产品规划书

- 产品名：**清涵课表**。全文「本应用」均指清涵课表。
- Android 包名（applicationId）：**`vip.qinghan.withu`**。
- 定位：**开源、免费、无广告**的 Android 课表软件；开源许可 GPL-3.0-or-later（见 7.1）；Android only；客户端技术栈 Flutter。

---

## 1. 产品定位与目标用户

### 1.1 一句话定位

清涵课表是一款**开源、免费、无广告的 Android 课程表应用**：单人可以完整地管理自己的课表；两人在双方分别授权后可以互相查看课表，**桌面卡片能同时显示两个人的课表，课表界面可以便捷地切换两个人的课表**。**本期的分发范围限定为自用与小范围测试**：源码以 GPL-3.0-or-later 开源、任何人可自行构建，但 5.2.0 不做面向公众的大规模分发。天气数据由服务端经和风天气获取，服务端须按和风条款使用；客户端不持有任何第三方天气密钥（见 4.6、7.4、7.5）。

### 1.2 产品主张

- **单人是完整可用的基础功能**，不是共享课表功能的前置任务。单人课表功能不登录、不依赖自有服务端即可全部使用（课表录入／展示／导入导出／提醒／统计等主体能力离线可用）；三处例外是单人也具备的网络能力——**天气经 withU 现有课表接口的 `action=weather` 获取（服务端经和风取数，需要连接 withU）**、**节假日数据更新与应用内自更新检查由客户端直连公开数据源**、**教务导入的适配清单与脚本在用户主动使用该功能时才从镜像源／GitHub 获取**（见 3.3、4.2、4.6、7.3）。天气是可选增强：未连接 withU 时只是没有天气，课表主体不受影响。是否把课表上传到服务器由用户决定，云端备份默认关闭（见 3.4）。
- **共享课表是主线特色，且只做两件事**：互相查看对方课表（界面可一键切换自己／对方的课表）；桌面卡片同时显示两个人的课表。
- **差异化落点是「双人同屏」**：桌面卡片同屏显示两人的课表与当前课程状态，应用内便捷切换两个课表。课表共享在同类产品里已有先例，把「两人课表同屏 + 便捷切换」做成默认体验是本应用的差异点。
- **免费、无广告是产品承诺**：应用内不出现广告、付费入口与商业化导流（见 1.4、3.5、7.5）。

### 1.3 目标用户

| 用户 | 特征 | 主要诉求 |
| --- | --- | --- |
| 高校在读学生 | 每学期课表固定、按周次循环、有节次时间模板，需要经常看课表；手机以 Android 为主 | 免去反复打开教务系统查看课表的烦恼：低成本录完课表、看得清今天和本周、课前有提醒、桌面能看到下一节课 |
| 查看好朋友课表的一方或双方 | 两人在同一所学校或不同学校；想减少「你几点下课」「你现在有课吗」这类反复确认 | 不用问就知道对方当前状态；桌面一眼看到两人课表；同时不被持续监视 |

目标用户描述的是产品形态的取向；**5.2.0 的实际分发范围见 1.1 与 7.6——自用与小范围测试，不是面向公众的大规模分发**。

### 1.4 非目标与红线

- 不做社交关系链、不做公开课表广场、不做陌生人匹配。
- 不做任何监视性功能。对方状态只由课表数据与时间推算，不采集任何行为数据。此类功能是**永久红线**：不进入候选、不进入任何里程碑，也不因版本演进重新讨论（范围界定见 3.5，其中说明「课程地点」与「用户位置」的区别：前者是课表字段、后者才是红线禁止的对象）。
- 不把共享关系做成可以单方面建立的关系：**绑定关系必须由双方各自明确同意**。任何一方表达意向都不代替另一方的同意，不存在默认同意、推定同意，也不存在由一方代另一方确认的路径；一次同意只对当次绑定有效，`pending` 失效后重发、解绑后再绑都需双方重新同意。
- 不把共享关系做成不可解除的强绑定：任何一方都能单方解绑，且解绑后对方的跨账号读取立即失效。解除关系不需要对方同意，与上一条的「建立关系需双方同意」不矛盾。
- 「免费、无广告」是产品承诺：本应用自身不引入付费、广告、内购与商业化导流，并只使用与该定位兼容的数据源（见 7.1、7.5）。这不构成对使用者的许可限制——本项目以 GPL-3.0-or-later 发布，他人可依该许可商用。

## 3. 功能范围

范围分四块：单人基础功能（3.1）、共享课表功能（3.2）、天气功能（3.3）、账号与服务端数据能力（3.4）。每条给出**用户价值**与**验收点**（验收点写成可观察现象，不依赖实现细节）。范围之外的内容集中在 3.5，功能与服务端接口的对应关系集中在 3.6；界面设计特色不属于上述四块范围，单列于 3.7。

### 3.1 单人基础功能（In scope）

| 功能 | 用户价值 | 验收点（可观察现象） |
| --- | --- | --- |
| 课表录入与展示 | 一次录入整学期可用 | 能新建学期并录入多门课程；周视图按当前周正确渲染课程块；左右滑动可切换周次；今日视图只显示当天课程 |
| 课程字段 | 课程信息完整且贴近真实上课场景 | 每门课可设名称、教师、地点、周次、节次范围、颜色；同一时段可存在两门并行课程且都被显示 |

| 本地数据与备份 | 换机不丢课表 | 课表可导出为文件备份；导入备份文件后课表与备份前一致 |

| 首次使用引导 | 一次性把关键选择做完，之后不再打扰 | 首次启动出现引导界面：引导「是否开启天气」——开启时若未连接 withU，先引导连接／登录；已连接则当场请求定位权限并取一次定位（或改用地点搜索），不开启则**不发起任何定位**，后续用户自行开启天气时再触发定位；引导可跳过，跳过与拒绝都不阻塞进入课表主界面；引导完成后不再自动出现 |

| 应用内自更新 | 官网 APK 分发场景下不必手动重装 | 可检查更新、下载 APK 并校验哈希后唤起安装；更新源支持镜像配置 |

### 3.2 共享课表功能（In scope，仅以下两条）

**「双人模式」的定义（全文引用此词处一律按本定义理解）**：双人模式由**一个独立的用户开关**决定，该开关在设置中由用户手动开启／关闭；**前提条件满足时默认开启**（首次进入双人形态前弹一次说明，用户确认或跳过），与 1.2「双人同屏是默认体验」的主张一致；用户可随时关闭，关闭选择本地记住。开启的前提条件是**已登录且存在 `active` 关系**：前提满足且开关开启时进入双人模式——顶栏标题区并列显示双方昵称、双人小组件按两列渲染，课表切换入口在对方可见性为 `full` 时可切换自己／对方两份课表（`status_only` 时按 3.7 第 (2) 种情形不列出对方课表）；前提不满足（未登录或不存在 `active` 关系）时开关置灰并附「先登录／先绑定」引导，无法开启。开关只在客户端本地保存，不入云端同步（与 4.4 的同步范围一致，不同步本地偏好）。关闭开关（或前提失效：任一方解绑、注销）即退出双人模式，退回单人形态：标题区只显示自己、切换入口不列出对方课表（按 3.7 第 (3) 种情形处理）、双人小组件回到单列只渲染自己的课表——不再渲染对方侧，也不新增 `no_data` 原因取值（对方侧数据停止展示，而非展示原因文案）。**因此对方侧的 `no_data` 原因只在双人模式已开启（即存在 `active` 关系）时成立，只有 `peer_visibility_off` 与 `peer_no_schedule` 两种；`not_linked`／`pending`／`unbound` 属于「前提不满足」，由课表切换入口（3.7）与共享关系管理界面（F4）承接，不作为 F2 对方列的原因文案。** 因此「双人模式未开启」=「开关关闭」**或**「前提不满足」两者之一；开关只控制**展示形态**，不改变关系状态与可见性（5.3），也不向服务端上报开关状态。

| 功能 | 说明 | 用户价值 | 验收点（可观察现象） |
| --- | --- | --- | --- |
| F1 互相查看对方课表（界面切换） | 双方各自授权后，可在应用内查看对方当前学期的课表（周视图／今日视图，需对方授权为 `full`；`status_only` 时只可见实时状态、不开放课表），只看不改；课表界面提供便捷的切换入口，可在自己与对方的课表之间一键切换 | 不再需要反复要课表截图；对方课表变化后看到的是最新版本 | 未登录时入口可见、可点，点击后引导注册／登录（登录成功且已有关系则进入对应课表，否则进入共享关系管理界面）；已登录但未建立关系时入口**不能用于切换到对方课表**（本机多份课表之间仍可正常切换；对方课表不作为可切换项出现，以「去绑定」形态呈现，点击该项只落到绑定流程，不进入空白课表）；建立关系且**对方**把可见性设为 `full` 后，能通过切换入口打开对方课表并看到与对方本机一致的课程（对方为 `status_only` 时入口不能用于切换课表，见 3.7 第 (2) 种情形）；切换后视图形态（周／日）与操作方式与本机课表一致；对方修改课表后，本机下拉刷新能看到变更；任一方关闭授权后对方立即无法查看且切换入口退回**不能切换**的状态 |
| F2 双人课表桌面卡片 | 桌面小组件**同时显示两个人的课表**：各自当天的课程块／当前课程与下一节课，同屏分列或分区呈现；本机侧由本地课表推算，对方侧由服务端按需下发或由本机按已拉取的对方课表推算（见 5.4.10）；卡片可点击——课表区域点开后直接停在对应一侧的课表，课程块点开后显示该课程详情（见下方点击行为） | 不用打开应用，桌面一眼看到两个人现在在上什么课、接下来是什么 | 添加小组件后同屏显示两人的当日课程与当前课程名；任一方课程结束进入下一节后，小组件在刷新周期内更新；某一方当天无课时该侧显示空闲状态；某一侧无数据时**显示具体原因**（对方未共享／对方没有课表／本机没有课表，见下方原因表；关系未建立／待确认／已解除属双人模式前提不满足，按 3.2 的定义不渲染对方列，由 3.7 的入口口径承接），而不是只显示「未连接」或空白，也不显示他人数据；本机有课表且未登录时本机侧照常显示自己的课表；点卡片课表区域与点课程块的结果与下方点击行为表一致 |

**F2 中每个人侧的状态口径（必须实现为这四种之一，不允许出现第五种含义）**：

| 状态 | 含义 | 展示要点 |
| --- | --- | --- |
| `in_class` | 正在上课 | 课程名、下课时间；可选**课程地点**（该节课的上课地点，取自课表字段，受 5.3 可见性控制；不是用户所在位置，也不属于 1.4／3.5 红线所禁的位置类字段） |
| `break` | 未在上课、今天还有后续课程（含当天第一节课之前、以及两节课之间） | 下一节课名与上课时间。**当天首节课开始之前视为 `break`**——此时「下一节课」即今天的第一节，展示口径与两节课之间完全一致（都显示下一节课名与上课时间），因此不需要第五种状态 |
| `free` | 今天已无后续课程 | 今日课程已结束 |
| `no_data` | 该侧没有可展示的课表数据 | 该侧的**具体原因必须显示出来**，不得只说「未连接」或留空；原因取值必须来自下表，并按适用侧区分（对方侧两种、本机侧一种），展示时给出对应的独立文案与下一步操作入口 |

**`no_data` 的原因口径（必须区分，不得合并成一句「未连接」）**：

| `no_data_reason` | 适用侧 | 含义 | 展示文案与操作 |
| --- | --- | --- | --- |
| `peer_visibility_off` | 对方侧 | 对方把可见性设为不共享 | 「对方未共享课表」+ 提示「请对方在其设置中开启共享」，不提供直接修改对方的入口 |
| `peer_no_schedule` | 对方侧 | 关系有效且可见性允许，但对方尚未上传课表 | 「对方还没有课表」+ 提示「可提醒对方录入课表」 |
| `self_no_schedule` | 本机侧 | 本机没有课表 | 「本机还没有课表」+ 「**导入课表**」或「**登录账号同步课表**」两个入口——无论登录与否，本地导入始终可用；登录只作为把云端课表同步下来的可选路径，不强制 |

- 对方侧两种原因**互斥且必须按优先级判定**：`peer_visibility_off` > `peer_no_schedule`。
- **`not_linked`／`pending`／`unbound` 不是 F2 对方列的原因**：它们表示双人模式的前提（已登录且存在 `active` 关系）不满足，此时按 3.2 的双人模式定义只渲染本机单列、不渲染对方侧，因此不产生对方列的 `no_data` 文案；这三种关系状态由课表切换入口（3.7 第 (1)(2) 种情形）与共享关系管理界面（F4）承接。服务端状态接口仍可能按关系状态返回这三种取值（见 5.4.10），客户端只用于关系引导，不作为 F2 对方列的展示依据。
- **本机侧的 `no_data` 原因只有 `self_no_schedule` 一种**：本机没有课表时显示「本机还没有课表」，并给出「导入课表」「登录账号同步课表」两个入口；**未登录不是本机侧的原因**——本机有课表且未登录时，本机侧照常由本地课表推算并显示自己的课表（单人功能不登录即可用，见 3.4 规则 3），不因登录态而把本机侧置为无数据。
- `no_data` 与原因同样适用于本机侧的异常情形：本机无课表用 `self_no_schedule`，本机侧显示对应原因而不是空白，也不套用对方侧的 `peer_visibility_off`／`peer_no_schedule`。
- 本机侧的 `self_no_schedule` 按本机本地课表判定；服务端 `self` 侧则按「服务端是否持有本机上传的课表副本」判定——有副本时返回按副本推算的结果，**无副本时同样返回 `no_data` + `self_no_schedule`，不得返回 `free`**（`free` 的语义是「今日课程已结束」，与「没有数据可展示」是两回事，见 5.4.10）。客户端对 `self` 侧以本地推算为准：服务端 `self.state=no_data` 只表示服务端没有副本，不表示本机没有课表，客户端直接忽略、不据此显示「本机还没有课表」。5.4.10 的 `self` 侧取值与本表一致。
- 无论哪种原因，都不得借该状态泄露任何未授权方的课程内容。

**F2 只读取课表推算的状态**：状态完全由课表数据与时间推算，不采集任何行为数据。**自己的侧始终由本地课表实时推算，不受登录态影响**——本机有课表且未登录时照常显示自己的课表状态；未登录且有本地课表时本机侧不进入 `no_data`。对方的侧只在授权范围内由服务端下发数据推算。

**F2 卡片点击行为（点哪里、进到哪，必须一一对应）**：

| 点击位置 | 打开后的结果 |
| --- | --- |
| 卡片的课表区域（某一侧的任意空白或状态区域） | 打开应用并**直接停在该侧对应的课表**上：单人卡片停在卡片绑定的那份课表；双人卡片左半停在自己的课表，右半在对方可见性为 `full` 时停在对方课表（无需再手动切换），对方为 `status_only`／`off` 时按 3.7 第 (2) 种情形不能用于切换课表，改为进入共享关系管理界面（或对应设置页） |
| 课程块（某一侧的具体一节课） | 打开应用、先切到该侧课表，再**展开该课程的详情**（课程名、教师、地点、周次、节次与当周该次课的时间）；对方侧的课程详情只读，且仅在对方可见性允许时可得 |
| 某一侧处于 `no_data` 的原因区域 | 按该侧原因分两类，**不一律切换**：本机侧（`self_no_schedule`）打开应用并停在本机课表界面，由「导入课表」「登录账号同步课表」入口承接——本机课表界面本身有内容（空态引导），不算空入口；对方侧的原因（`peer_visibility_off`／`peer_no_schedule`）**不切到对方课表**——这些情形下对方课表入口**不能用于切换课表**（与 3.2 F1、3.7 的口径一致），点击只打开应用并直接进入共享关系管理界面（或对应设置页），由该侧原因对应的下一步操作入口承接（如「查看共享设置」「提醒对方录入课表」），不弹空详情、不切换到空白课表；`not_linked`／`pending`／`unbound` 下对方列不渲染（双人模式前提不满足，见 3.2 的双人模式定义），不存在该点击区域 |

- **切换先于详情**：点击课程块时先完成课表切换再展开详情，避免在错误的课表上打开同名课程。
- **降级一律回落到普通打开，不猜目标课表**：卡片绑定的课表已被删除或失效时普通打开；课程在该课表中已不存在时只完成切换、不弹空详情；双人卡片在双人模式未开启时不做静默切换，改为在应用内提示用户手动开启该开关（见 3.2 的双人模式定义），不擅自替用户开启。
- **冷启动与热启动结果一致**：应用未运行、已在后台、已在前台三种情形下，点击同一位置得到相同结果；点击只触发一次跳转，不产生重复弹窗或重复切换。
- **不额外采集数据**：卡片点击只用于确定「打开哪份课表、展开哪门课」，不上报点击行为，也不因点击扩大任何一侧的可见范围。

### 3.3 天气功能（In scope）

| 功能 | 用户价值 | 验收点（可观察现象） |
| --- | --- | --- |
| 课表页天气呈现 | 出门前知道要不要带伞、穿多少 | 已连接 withU 且已有位置（地点搜索结果或定位坐标）时课表页显示本地天气（温度、天气现象、降水概率）；未连接 withU 或没有位置时天气区显示「暂无天气」/连接提示，且不阻塞课表使用 |
| 天气随日期变化 | 看课表时能直接看到当天的天气 | 切换到其他日期时，天气跟着该日期的预报变化 |
| 数据来源与署名 | 客户端零密钥、数据来源可追溯 | 天气数据经 withU 服务端获取，客户端不直连和风／高德／Open-Meteo；客户端代码、构建脚本与 APK 中检索不到任何第三方天气 Key、Token 或直连域名（规划书与附录中的历史研究记录除外）。服务端若按和风条款需要署名，天气区域展示服务端提供的署名文案／链接 |
| 位置来源（城市／地区搜索优先） | 不必开启系统定位也能拿到天气，也不需要每次看课表都重新定位 | 提供地点搜索入口，输入关键字后经 `action=weather&mode=lookup` 返回城市／地区级候选（和风 GeoAPI 为城市级，不承诺校区／车站／商圈等 POI 级粒度），选中后立即出天气；选中地点在用户再次更新前保持不变；**不强制开启系统定位（GPS）**，拒绝定位权限时地点搜索通道仍完整可用；地点搜索与天气一样需要连接 withU（未登录 401、非情侣账号 403），未连接时入口提示并保留已有缓存 |
| 系统定位（按需，由引导与手动触发） | 定位只用于确定天气坐标，不常驻、不轮询 | 定位用 Android 系统定位（`LocationManager`，GPS／网络 provider，不依赖 GMS 与任何第三方定位 SDK），只取经纬度；**在已连接 withU 的前提下，仅在引导界面选择开启天气、设置中首次开启天气时自动取一次**（或由用户在该步改用地点搜索），以及用户点击「获取当前位置」时取一次；引导未开启天气时**不发起任何定位**，直到用户后续自行开启天气；除上述触发外不发起点位请求（无后台持续定位、无定位类前台服务）；仅授予粗略定位（Android 12+「大致位置」）仍能出天气；定位服务关闭／无可用 provider 时不取点、不报错，天气区显示「暂无天气」或沿用已有位置，课表全部功能可用 |
| 实况与地名（可选增强） | 当前天气与地点名可读 | 服务端已配置和风凭据且 `mode=now` 成功时，天气区显示实况与地名；`mode=now` 失败时客户端退化为只显示逐小时预报，不报错、不崩溃（本条不作硬验收点） |

约定：**位置来源为「城市／地区搜索优先 + 系统定位按需」；地点搜索、实况、逐小时预报统一经 withU 现有课表接口 `GET /api/timetable.php?action=weather` 获取，服务端持和风天气凭据并对客户端零密钥**（见 4.6、5.4.13、7.4）；定位取系统 API（`LocationManager`），不引入任何第三方定位 SDK，也不引入地图 SDK。**客户端不持有任何第三方天气服务密钥，也不直连和风／高德／Open-Meteo**。天气需要连接 withU 且为情侣账号；未连接时只影响天气，不影响课表主体。数据源许可与免费无广告约束落在第 7 章。

### 3.4 账号与服务端数据能力（In scope）

第 5 章的接口按本节与 3.1、3.2、3.3 的功能条目划分，编号如下：`A` 为账号与服务端基础能力（A1 账号与设备、A2 云端课表副本、A3 服务端配额与限流反馈），`B` 为变化通知能力（B1），`F` 为共享课表功能（F1–F4），`W` 为天气数据能力（W1：withU 服务端经和风获取地点、实况与逐小时预报，客户端零密钥）。

**登录与上传规则（约束本节全部服务端能力）**：

1. **注册方式：QQ 号 + 自设密码**。QQ 号是账号的唯一标识（账号 ID），注册时同时设置登录密码；登录以「QQ 号 + 密码」完成鉴权。注册过程不需要邮箱验证、不发验证码，填写 QQ 号、设置密码、提交即完成注册（见 5.4.1）。QQ 号同时用于换取 QQ 头像作为账号头像。**这里的密码是用户注册时为清涵课表自行设置的登录密码，与 QQ 账号密码无关**：应用不要求、不接受也不使用 QQ 账号密码，不提供 QQ 账号登录；注册界面的密码输入框需就地注明「设置清涵课表的登录密码（不是 QQ 密码）」。
2. **账号的用途边界**：QQ 号只用于「标识账号 + 取头像 + 建立唯一的共享关系」，不用作第三方登录授权、不读取 QQ 空间／好友关系、不申请任何 QQ 开放平台权限。
3. **单人不强制登录**：全部单人功能在未登录状态下完整可用；登录时用户主动以「QQ 号 + 清涵课表登录密码」注册或登录。
4. **单人云端备份默认关闭**：是否把课表上传到服务器由用户在设置中决定，默认不上传；开启后自动完成登录并上传，关闭后单人备份的上传与自动拉取停止（本地课表不受影响）。**课表上传有两条相互独立的理由，任一成立即上传，互不覆盖**：一是**云端备份处于开启状态**——此时课表一律上传，与共享关系、可见性档位无关（关系处于 `none`／`pending`／`unbound`、或本机可见性为 `off` 都不影响），这是 A2 的多设备同步路径；二是**未开启备份但「存在 `active` 关系且本机可见性非 `off`」**。因此：未开启备份的单人场景（无共享关系）不向服务端上传课表数据；未开启备份但存在 `active` 关系且本机可见性非 `off` 时，课表上传按 4.4 的上传门控继续、不因关闭备份而停止，该情形须在设置页与 7.3 向用户明示。
5. **双人必须登录才能同步**：共享课表的绑定、互相查看、双人卡片与变化通知，以双方各自持有服务端身份为前提。**未登录时共享课表入口照常可见、可点击，点击后引导注册／登录（这就是「首次使用共享课表」的入口，见 A1）；登录成功后按当前关系状态决定下一步**——无关系时进入共享关系管理界面（发起绑定），已有关系时进入对应界面。单人功能在任何登录态下都不受影响。**「入口不能用于切换课表」只针对已登录但无 `active` 关系、对方未授权（`off`）、或对方只共享实时状态（`status_only`）的情形**（见 F1、3.7）——此时以置灰或「去绑定」形态呈现，点击落到绑定流程而非切换；**不适用于未登录**：未登录不表现为隐藏或置灰，而是以引导登录来承接点击。

**邀请注册的交互规则（约束 F3 与注释册流程）**：

1. **邀请码是注册入口，只在注册流程内使用**：已注册用户可生成邀请码／邀请链接，尚未注册的被邀请人凭码完成注册。邀请码的全部作用范围就是这一次注册流程——**被邀请人在注册当场（响应提示期间）可以选择与邀请人绑定，也可以选择暂不；无论选哪个，邀请码都在该次注册流程内被消费掉，此后不能用于登录，也不能再用于绑定**。「注册流程内」由服务端客观判定：`bind_on_accept=true` 的邀请在注册成功后进入 `awaiting_response` 状态并下发一次性 `bind_grant` 凭据，**消费时点是这个待响应窗口的结束**——窗口内绑定成功即消费，窗口到期（注册成功后 13 分钟，`bind_deadline`）未被响应也消费；`bind_on_accept=false` 的邀请则在注册成功时即消费、没有窗口。凭据与窗口的判定规则见 5.4.4、5.4.5。注册完成之后要建立关系，一律走「填写对方 QQ 号 → 对方确认」这条路径（见 5.4.5 方式二）。
2. **绑定意向由邀请人在生成时决定，默认不勾选**：点「生成邀请」时弹出确认弹窗，弹窗内含一个默认**未勾选**的选项「同时与被邀请人建立课表共享关系」；用户勾选后生成带绑定意向的邀请，不勾选则生成纯注册邀请。弹窗不做记忆：每次生成都回到未勾选状态。
3. **被邀请人是否看到绑定提示，完全取决于邀请人的勾选**：
   - 邀请人勾选过：被邀请人注册成功后看到「{邀请人} 请求与你建立课表共享关系」的提示，可自行选择「绑定」或「暂不」，选择后不再提示。
   - 邀请人未勾选：**被邀请人注册成功后看不到任何绑定提示**，也不应出现关系相关的引导文案。
4. **绑定必须双方各自同意，没有默认同意**：这是适用于全部绑定路径的无条件规则（见 1.4 与 5.4.5）。邀请人勾选只是表达自己愿意绑定的意向，不代替被邀请人的同意，必须由被邀请人在提示中点「绑定」才建立关系；反过来，被邀请人同意也不代替邀请人。按 QQ 号发起同理：发起方的提交只是意向，要等对方确认。一次同意只对当次绑定有效，`pending` 失效后重发、解绑后再绑都要双方重新同意。
5. **被邀请人始终有权拒绝**：即使邀请人勾选，绑定也不自动成立；被邀请人点「暂不」后不再提示，也不产生任何关系。
6. **邀请码只用于注册，不承担授权**：凭邀请码注册不产生任何课表可见性；可见性仍由绑定后的三档独立设置（5.3 规则 1、规则 2）。邀请码也**不是**注册后可反复使用的绑定凭据——`bind_on_accept=false` 的码注册成功即消费，`bind_on_accept=true` 的码在待响应窗口（13 分钟）截止或绑定完成后消费，两者都不会再次生效。

### 3.7 界面设计特色

主界面的结构性入口只有两处：右上角一个隐藏入口承担全部设置与管理，顶栏标题区承担课表切换。主界面默认不叠加任何常驻功能栏，课表占满可用高度。

| 设计特色 | 做法与用户价值 | 验收点（可观察现象） |
| --- | --- | --- |
| 默认不设常驻底栏（dock），设置收进右上角隐藏入口 | 常见的课表类应用把设置、统计、管理等功能做成课表下方的常驻底栏（dock），占掉一整条课表高度，也在视觉上与课表内容争夺注意力。本应用主界面的默认形态**不设常驻底部导航栏**：课表区域从顶栏下沿延伸到屏幕底部（只避让系统手势条／导航条）；全部设置与管理入口收进右上角一个入口，点开后是锚定在该按钮旁的弹层，按功能、数据、偏好、关于分组列出，选中进入对应页面。用户价值：课表可视面积最大，主界面只呈现课表本身。 | 首次进入（未改动任何设置）时，主界面课表下方不存在常驻功能栏；右上角入口点开后可看到全部分组入口，**不存在只能从常驻栏进入的功能**——即使某个常驻栏形态被用户主动开启，它也只是重复入口，不得成为唯一入口；从任一入口返回后，当前周次、当前日期与滚动位置保持不变；在常见屏幕比例与手势／三键导航下，课表最后一行不被遮挡。 |
| 课表顶部一键切换课表 | 切换课表在同类产品里通常要先进入设置或课表管理，再点选目标课表，多步跳转。本应用把顶栏的标题区本身做成切换入口：点一次弹出课表列表，选一次即完成切换，全程**不超过两次点击**。双人模式（见 3.2 的定义：已登录且有 `active` 关系、且用户已开启双人模式开关）下标题区并列显示双方昵称并高亮当前一侧，对方可见性为 `full` 时点一下即在自己与对方的课表之间切换（`status_only` 按下方第 (2) 种情形不能切换），切回同样只需一次点击。用户价值：切换课表是最高频操作之一，代价降到最低。 | 从主界面切换到另一份课表不超过两次点击；双人模式下在自己与对方课表之间切换为一次点击；切换后标题区高亮侧、周次与课表内容同时更新，无需进入设置页；**入口的可用性分四种情形且互不混淆**——(1) 未登录：入口可见可点，点击后引导注册／登录，登录后按关系状态进入下一步（这是「首次使用共享课表」的入口）；(2) 已登录但关系未建立、对方未授权（`off`）、对方只共享实时状态（`status_only`）或已解绑：入口**不能用于切换到对方课表**（本机多份课表之间仍可正常切换）；对方课表不作为可切换项出现，以置灰或「去绑定／查看共享设置」形态呈现，点击该项只落到「绑定／重新绑定／查看共享设置」这类操作入口，不进入空白课表、也不进入必然返回 403 的课表，不出现可点进去却无内容的入口（`status_only` 的文案说明对方只共享实时状态）；(3) 关系有效、对方已授权为 `full`，但用户**未开启双人模式开关**：入口用于在本机多份课表之间切换，但**不列出对方的课表**；若用户点击提示「开启双人模式」，只做提示与跳转设置，不擅自替用户开启；(4) 关系有效、对方已授权为 `full`，且双人模式开关已开启：正常切换自己／对方两份课表。 |

```
presentation（页面与小组件展示模型）
        ↓ 调用
application（用例：录入课表、切换周次、测算双人状态、同步编排）
        ↓ 调用
domain（纯 Dart：课程/节次模板/学期/可见性/状态推算，无平台依赖）
        ↓ 调用
data（本地数据库 + 远端服务端客户端 + 平台能力桥接）
        ↓ 调用
platform（Android 原生：小组件 Provider、通知、闹钟、定位、广播接收器）
```

读法：箭头方向就是**调用方向**（上层调下层）。`platform` 是被调用方，因此在图上排在 `data` 之下、列表末端。`domain` 不接受任何平台符号，`platform` 不包含业务规则，两者的边界就是「消息与数据结构」。

**本文档约束的是依赖方向，不是目录名。** 层与模块是逻辑边界；目录如何组织以实现为准，不因本文档的命名而重排代码。判定是否合规只看三条硬约束，不看文件名。

**三条硬约束（可机器校验）**：

1. **依赖单向**：`data`／`application`／`domain` 不得导入 `presentation` 的任何模块。唯一的例外是调试专用入口（如深链直达某个页面），它必须与业务代码隔离、并在发布构建中可剔除。
2. **`domain` 纯度**：`domain` 只依赖 Dart 核心库与自身数据模型，**不导入任何 Flutter 包**（`flutter/foundation.dart` 也不例外）。这条不成立，`domain` 与 `platform` 的边界就只是纸面约定，`domain` 的单元测试也必须跑在 Flutter 测试环境里。
3. **application 收口**：`presentation` 不得直接构造 `data` 层服务实例，也不得直接发起数据层调用，一律经 `application` 暴露的用例方法。这是「改动数据层不波及界面」与「界面可被独立测试」的共同前提；绕过这一层会同时失去这两项保障。

**强制机制**：上述三条必须落成静态检查（`analysis_options.yaml` 的导入规则或 `custom_lint`），在 CI 中作为构建期错误拦截。只写在文档里、靠评审记忆维持的边界，会在两个迭代内失效。

**application 层的组织方式**：按用例划分控制器，一个控制器只承担一组相关用例（例如「周次切换」「导入应用」「设置合并」「小组件数据下发」各一个），不得出现单个控制器同时承担多个无关用例的形态。判定标准是：一个控制器的方法集合能否用一句话概括。

**适配脚本的分发与加载边界**：教务适配脚本是从远端获取并执行的代码，分发源与执行边界都必须显式约束，不能当普通配置对待。

- **静态清单随包内置，脚本体不内置**：客户端安装包里只带一份内置的适配清单骨架（含字段格式说明与一个示例条目，用于让客户端在没有任何远端脚本时仍有可解析的空清单结构），适配脚本本体一律从远端获取，不打包进 APK——否则适配更新就必须重新发版，社区化维护失去意义。**内置骨架不构成任何可用的学校适配**：它只在客户端侧提供格式与解析结构，教务导入入口在无远端脚本时显示**空列表 + 「如何添加适配」指引**（骨架本身不作为列表项渲染，见 6.2 的验收点）。
- **规范源为 GitHub 独立仓库；本项目另做服务器镜像分发**：仓库托管在 GitHub，本项目把同一份内容同步到自有服务器作为镜像，供国内网络访问。**客户端只在用户主动使用教务导入时**按「镜像优先、GitHub 兜底」的顺序取同一份清单（用户不使用教务导入则不发起这类请求，隐私口径见 7.3），两者都不可达时教务导入入口显示为空列表并给出添加指引。
- **「镜像与规范源不一致时以规范源为准」是发布侧义务，不是客户端行为**：客户端不做清单一致性比较（没有依据、也没有必要——镜像不可达时正需要兜底），它只信任「校验和与其清单匹配」这一层。「以规范源为准」约束的是**本项目的发布流程**：维护者在同步镜像时以规范源内容覆盖镜像，镜像落后或被篡改的纠正手段是重新同步，而不是让客户端去比较两个源。客户端侧的防篡改手段只有校验和（见下一条），不引入额外的一致性判定。
- 客户端只加载清单中声明、且校验和匹配的脚本；校验和不符、清单缺失或来源不在配置的源列表内时拒绝加载并提示原因，不执行来源不明的脚本。
- **信任机制是「清单 + 校验和」，本项目不实现脚本签名**：清单本身从受信源（配置的镜像地址或 GitHub 规范源）获取，清单内为每个脚本写明哈希；客户端下载脚本后重算哈希比对，两者一致且来源合法才加载。原表述「客户端不做脚本签名以外的信任假设」中的「签名」一词不准确——本项目没有签名机制，应读作：**校验和之外不做任何其他信任假设**（不信任源域名本身、不信任传输层、不信任内置骨架里的任何脚本条目）；脚本运行在受限环境，只能产出既定格式的课程数据，不得读取本地课表、令牌或其他应用数据。若未来校验和被证明不足以防投毒，升级路径是清单级签名，属后续候选。
- 镜像地址是可配置项而非写死的常量：官方镜像失效时用户可改配置，不因单一镜像不可用而失去教务导入能力。

模型约定：

- 课程的唯一身份是本地的课程 `id`；同步到服务端后由服务端返回同一 `id`（客户端生成 UUID 并以 `upsert` 语义提交，见 5.6）。
- 所有时间字段分两类：**日期类**用 `YYYY-MM-DD`（学期开始日期、调课日期）；**时刻类**用「当日 0 点起的分钟数」（节次时间），避免夏令时与跨时区歧义。与外部交互的时间戳用 ISO 8601（见 5.7）。
- 「对方状态」不落永久表，只进 `status_cache`，且只保存 F2 展示所需的字段；本机自己的状态不入缓存，由本地课表直接推算。

### 4.4 本地优先与服务端边界

- **本地优先**：单人功能全部离线可用（唯一的联网部分是天气——全部经 withU 服务端的 `action=weather`；未连接 withU 时天气不可用，课表主体照常）；任何网络失败都不得阻塞课表读写与展示。
- **上传门控（默认不上传）**：客户端向服务端提交课表数据的条件是「已登录，且满足以下任一条」——**A. 云端备份已开启**；**B. 存在 `active` 关系且本机 `my_visibility != off`**。两条理由是**或**关系，任一成立即上传：**备份开启时无条件上传**（与共享关系、可见性档位无关），因此下面的逐条含义**只适用于备份关闭的情形**。备份关闭时逐条含义：单人场景（无共享关系）时，`pending_change` 队列只入不出，不发生任何课表上传；存在 `active` 关系但本机 `my_visibility = off` 时同样不上传——`off` 意味着服务端不得向对方下发本机任何课表内容；关系有效且本机档位为 `status_only` 或 `full` 时，为支撑 F1／F2（两种档位都需要服务端持有课表才能推算状态与下发课程），课表上传不因用户关闭云端备份而停止。备份关闭时，解除关系（撤回、解绑、任一方注销）后回到不上传状态；`pending` 不是关系，等待确认期间不上传。备份关闭时把档位从 `off` 改为 `status_only`／`full` 的那一刻门控即满足，按 4.5 的规则补传队列中的存量变更。**云端副本的删除只走注销账号（5.4.3）：解绑、把可见性改为 `off`、关闭备份都不删除服务端已持有的副本——只要账号还在，副本随账号保留（不下发即不可读，账号注销时一并清除）。该行为必须在设置页与隐私说明（7.3）中向用户明示**：绑定有效且本机在共享课表（非 `off`）时，即使关闭云端备份，课表仍会上传到服务端。
- **服务端边界**：服务端只承担五件事——账号与设备、课表云端副本、共享关系的可见性判定与对方数据下发、**变化通知的注册与投递**（B1，见 3.4、5.2 第 11 条、5.4.11；通知只做「有变化，去取一次」，不承载课表内容）、**天气数据代理**（`action=weather`：地点搜索、实况、逐小时预报；服务端持和风凭据，见 4.6、7.4）。它**不是**课表的主存储，客户端始终以本地库为准；天气动作也**不是**课表数据的存储或中转，不落库任何用户位置历史或搜索记录（见 7.3）。
- **写权限边界**：共享关系下**只读**对方的课表数据。客户端不得提供「编辑对方课表」的入口；接口层面也不申请任何写对方数据的路径（见 5.2、5.3）。
- **可见性判定在服务端**：客户端不做「对方能不能看我」的假设，一律以服务端返回的 `peer_visibility` 与接口返回 403 为准，防止本地状态被篡改导致越权读取。
- **同步范围**：只同步课表域数据（课程、节次模板、学期、调休）与可见性设置；不同步天气缓存、不同步本地提醒设置、不同步对方状态缓存、**不同步时区**（本期不保证跨时区双方状态一致，见 4.9）。

### 4.5 同步架构

- 本地每次变更写入 `pending_change` 队列；满足 4.4 的上传门控时提交给服务端（`POST /v1/sync/push`），携带 `base_rev` 做乐观并发；冲突按 5.6 处理；门控未满足时队列只入不出，联网也不上传，待门控满足后按 `created_at` 升序补传。
- 拉取用游标（`GET /v1/sync/pull?since=`），客户端维护 `last_cursor`；游标只前进不后退。
- 对方课表按需拉取并缓存，缓存键为 `(peer_user_id, semester_id, cursor)`；本地缓存是展示来源，服务端是权威来源。
- 所有推送到服务端的请求带 `Idempotency-Key`，重试不会造成重复课程。

### 4.6 天气链路（位置来源 + withU 服务端天气动作）

数据分工：**位置来源为「城市／地区搜索 + 系统定位按需」；地点搜索、实况与逐小时预报统一经 withU 现有课表接口的天气动作 `GET /api/timetable.php?action=weather` 获取（服务端持和风天气凭据并转发；客户端零第三方密钥，见 7.4）。** 天气动作与 login / bootstrap / partner 同一个 host、同一套会话（`PHPSESSID` + `withu_device`）；未登录 401、非情侣账号 403。天气是可选增强：未连接 withU 时只是没有天气，课表主体不受影响。

位置来源**只有两条**（不设第三条：不做网络／IP 位置估算，也不引入地图 SDK 的定位），用户可任选，二者产出的都是同一个「当前坐标」：

1. **城市／地区搜索（主路径）**：输入关键字，经 `mode=lookup&q=` 返回城市／地区候选并选定一个，立即作为当前坐标，无需任何定位权限。
2. **系统定位（按需）**：触发点与天气开关绑定——在已连接 withU 的前提下，引导界面选择开启天气时自动取一次（或用户在该步改用地点搜索）；之后由用户点击「获取当前位置」时取一次；用户在引导时未开启天气，则**完全不发起定位**，直到其后续自行开启天气那一刻。除上述触发外不发起定位请求。

```
当前坐标（地点搜索 / 系统定位）
   └→ withU 服务端 GET /api/timetable.php?action=weather
         ├→ mode=lookup（关键字或经纬度 → 城市／地区候选）
         ├→ mode=now（实况）
         └→ mode=hourly（逐小时预报）
               ↓ 服务端持和风凭据转发，并按模式做短时缓存
```

**服务端天气动作的边界（与 4.4 服务端边界一致）**：

- **客户端不持有和风 Key／Token**：和风 API Key、JWT、Ed25519 私钥只存在服务端；客户端不出现任何天气 Key 常量或 `--dart-define` 注入点。客户端不直接请求和风、高德或 Open-Meteo 域名。
- **不新增域名／路径**：天气是现有 `timetable.php` 的一个 `action`，与课表接口共用 baseUrl、会话 Cookie、401／403 处理和超时；不是独立的 `/v1` 天气代理路径。
- **需要登录且为情侣账号**：未登录 401、非情侣账号 403；客户端未连接时不发天气请求，保留已有缓存；登录后自动补拉一次。天气不可用不影响课表主体。
- **服务端降级**：服务端未配置和风凭据返回 503 `weather_not_configured`；上游失败／超时返回 502／504 `weather_upstream_error` / `weather_timeout`；有旧缓存时可返回 `stale: true`。客户端对这些错误静默隐藏天气，不弹错误；地点搜索入口给出「天气服务暂不可用」提示而不是空白。
- **缓存与限流**：服务端按模式缓存（`now` 5 分钟、`hourly` 20–30 分钟、`daily` 60 分钟、`lookup` 24 小时），缓存 key 含模式、坐标（2 位小数）、`lang`、`unit`、`days/hours`；上游失败时用旧缓存兜底。和风配额由服务端统一承担、监控与限流（见 7.4、8.2 Q5）。
- **不留位置历史**：服务端只做短时缓存与转发，不落库用户坐标、搜索关键字或天气请求日志；缓存按地点而非账号组织，不用于行为分析（见 7.3）。

**地点搜索的粒度**：

- 和风 GeoAPI 是**城市级**搜索与反查，不提供街道级逆地理，本期不承诺校区、园区、车站、商圈、小区、建筑等 POI 级结果；`mode=lookup` 返回 `locations[]`，每条带 `name`、`latitude`、`longitude`、`admin1`、`country`、`district`、`timezone`、`adcode`（和风 LocationID，客户端当不透明 ID）。
- 城市名搜索与坐标反查都走同一 `mode=lookup`，`q` 与 `lat/lng` 二选一；客户端不引入地图 SDK、不嵌入地图控件、不直连和风；**地图选点本期不做**（见 3.5）。
- 若后续要恢复 POI 级地点搜索，需要服务端更换支持 POI 的地理数据源，属范围变更，不在本期承诺。

实现约束：

- **位置是持久状态，不是每次打开都重算**：当前坐标存本地，地点搜索或系统定位取得后写入；后续打开应用直接沿用，直到用户再次选定地点或点击「获取当前位置」。
- **不强制开启 GPS**：应用不得把定位权限或定位服务可用作为天气功能的前置条件；拒绝权限、关闭定位服务、无可用 provider 时，地点搜索通道完整可用（前提是已连接 withU），天气照常显示。
- 定位只用系统 API，**不引入任何第三方定位 SDK**，也不依赖 GMS：经 `Context.getSystemService(LOCATION_SERVICE)` 拿 `LocationManager`，按 provider 可用性选择 GPS／网络 provider，取一次坐标即停止。
- 单次取点的写法按 API 等级分档：**API 26–29** 用 `requestLocationUpdates` 拿到首个有效结果后立即 `removeUpdates`；**API 30+** 优先用 `getCurrentLocation`（可直接回调单次结果）。两条路径都必须保证「取到即停」。
- 权限：运行时申请 `ACCESS_COARSE_LOCATION`（或 `ACCESS_FINE_LOCATION`）。**仅授予粗略定位时也必须能出天气**，不得把精确定位作为前置条件。引导界面的自动取点必须先取得权限；用户拒绝时不重复弹窗，该步可改用地点搜索完成设置。
- 可用性判定：先查 `LocationManager.isProviderEnabled(...)` 与 `getProviders(true)`；无可用 provider 或定位服务被关闭时不取点、不报错，沿用已有坐标或显示「暂无天气」，课表全部功能照常可用，不崩溃、不弹错误弹窗。
- **触发时机由天气开关驱动**：在已连接 withU 的前提下，引导界面开启天气、用户点击「获取当前位置」，以及用户在设置中首次开启天气，三者之外一律不发起定位。**不做后台持续定位**、不注册定位类前台服务、不在进入课表页或切换日期时发起定位。
- **实况与预报**：`mode=now` 与 `mode=hourly` 可以并行请求；`now` 失败只降级实况，不影响逐小时预报。`mode=hourly` 的 `data` 是列式结构（`time`、`temperature_2m`、`precipitation_probability`、`precipitation`、`snowfall`、`weather_code`），`time` 为不带偏移的墙钟、`weather_code` 为 WMO 码（服务端由和风图标码映射）。客户端请求 `hours=168`，服务端按套餐返回 24／72／168 中可用的窗口；若 168 被判为 `weather_invalid_params`，客户端退到 `hours=24` 重试一次。不要假设一定有 16 天。
- **实况字段**：`mode=now` 的 `data` 同时提供 `weather`／`temperature`／`humidity`／`winddirection`／`windpower`／`reporttime` 与 `desc`／`temp`／`windDir`／`windScale`／`obsTime`，以及 `wmo_code`；客户端优先用 `wmo_code` 归类，缺省回落中文文本。`mode=daily` 契约保留，但本期课表页不消费逐日预报。
- **降级口径**：`weather_not_configured`、`weather_upstream_error`、`weather_timeout` 等天气错误一律静默隐藏天气，不弹错误；有旧缓存时继续展示旧数据；地点搜索入口显示「天气服务暂不可用，请稍后再试」。客户端不区分服务端状态。
- **缓存与去重**：客户端沿用 3 小时 TTL、15 分钟失败退避、单飞；同一坐标同一日期不重复请求；服务端再做一层短时缓存与合并限流。
- **坐标**：客户端传 WGS-84、6 位小数；服务端按和风要求转成 `lng,lat` 并四舍五入到 2 位；客户端不做 GCJ-02 纠偏。
- **署名**：和风的署名／许可要求由服务端按其条款处理；若要求客户端展示，服务端在契约中提供文案／链接，客户端在天气区域展示。客户端不再有 Open-Meteo 链接义务。
- **客户端不持有任何第三方密钥（见 7.4）**：天气动作由服务端持和风凭据完成，客户端请求不携带任何第三方凭据；服务端未配置凭据时天气不可用，客户端按上面的降级口径处理。

### 4.7 桌面小组件实现路径

小组件是「Flutter 数据层 + Android 原生渲染」的**双份实现**，不是 Flutter 直写。**下面的原生侧以 RemoteViews 描述；若 8.2 Q2 最终选定 Jetpack Glance，本节的数据下发通道与刷新分层不变，只把原生渲染侧替换为 Glance**：

```
Dart 侧：算出本机与对方两侧的最新状态快照
   → HomeWidget.saveWidgetData('<key>', value)      // 数据下发
   → HomeWidget.updateWidget(name: '<Provider>')     // 通知刷新
   ↓
原生侧：<receiver> 声明 android.appwidget.action.APPWIDGET_UPDATE
        + android:appwidget.provider 元数据指向 AppWidgetProviderInfo XML
   → AppWidgetProvider.onUpdate() 读 SharedPreferences 快照 → RemoteViews 渲染
```

- `home_widget` 只提供**数据下发、读取与刷新通知**的统一接口；Flutter 不能直接渲染原生小组件。
- 小组件分为单人小组件（今日课程／下一节课）与双人课表卡片（同屏显示两人课表与当前状态，按 3.2 的双人模式定义：前提为已登录且有 `active` 关系、且用户已开启双人模式开关），各自独立的 Provider，不要用一个 Provider 同时承担单人卡片与双人卡片（避免刷新逻辑耦合）。**双人课表卡片在双人模式开关关闭时仍由该 Provider 渲染，但只渲染本机单列**（与 3.2、6.6 的开关验收点一致）——这是同一 Provider 内的布局分支，不是把单人卡片与双人卡片合并成一个 Provider。
- **刷新分层**：
  1. 小组件刷新本身受系统后台限制，不保证分钟级；两侧状态在小部件上的**分钟级推进由本地推算完成**（本机侧用本地课表、对方侧用 `status_cache` 里已有的下课时间与下一节课时间，`in_class → break → free` 均可在本机按时间自推），不依赖每次刷新都联网。
  2. 联网校时走后台执行插件（如 `flutter_workmanager` 一类后台执行方案）与 `GET /v1/couple/status`，返回 304 时不重绘。
  3. 变更驱动：通过 `POST /v1/couple/events` 注册的变化通知（通道待定，见 8.2 Q7）收到对方课表变更时，立即触发一次数据下发与刷新。未注册任何通道（`channel=none`）时，本条缺失，改为依赖下一次拉取时机（见 5.10）。
- **重排刷新**：必须监听并处理开机、修改系统时间、修改时区三类事件后的小组件重排（`RECEIVE_BOOT_COMPLETED` + `TIME_SET` + `TIMEZONE_CHANGED` 广播，并让小组件 Provider 也响应 `APPWIDGET_UPDATE`），否则设备重启或跨时区后小组件内容与当前周错位。
- **点击直达**：卡片的点击由原生侧用 `PendingIntent` 携带「卡片实例标识」以及可选的「侧别」「课程标识」启动主界面，Flutter 侧在启动流程中读取并消费一次，完成课表切换与课程详情展开后再清空，保证冷启动与热启动只生效一次（对应 3.2 的点击行为表）。双人卡片的行点击通过 `PendingIntentTemplate` + fill-in intent 区分左右两侧，避免每一行单独注册 PendingIntent。
- 小组件主题跟随系统深色模式，样式常量放在应用侧 style，原生与 Dart 侧共用同一套色值定义。
- 小组件的后台刷新周期上限与 Doze 下的行为，官方文档本次取证失败，需在 5.2.0-1 动工前补齐官方依据（见 8.2 Q1、Q10）。

### 4.9 与「超范围」的架构隔离

- 共享课表相关的所有网络能力集中在 `couple` 与 `sync` 两个模块，单人功能不依赖它们，保证「不登录也能用」。
- 云端备份是 `sync` 模块内的可选路径，由用户开关门控且默认关闭；门控未满足时 `sync` 模块不发起任何课表上传（见 4.4）。
- 状态推算在 `domain` 层纯函数实现，便于单元测试与后续复用；这条同时是 4.2「`domain` 纯度」约束的直接应用——纯函数实现的前提就是 `domain` 不碰平台符号。**纯函数的输出是三态（`in_class`／`break`／`free`），不是 F2 的四态**：它只负责「有课表时的时间推算」，输入为课表 + 当前时间 + 时区（见 4.9 末条）。`no_data` 及其原因依赖关系状态、可见性、对方是否上传课表、本机是否有课表等课表之外的信息，不由这个纯函数产生，而是由 `application` 层在调纯函数之前先判定「该侧有无数据、无数据属于哪种原因」，再决定是直接展示 `no_data` 还是调纯函数算三态。因此 F2 的完整四态由「`no_data` 判定（application）+ 三态推算（domain 纯函数）」组合而成，两者职责不重叠。
- **本期不保证跨时区双方的状态一致性**：`domain` 的推算函数要求「对方课表」与「当前时间」在同一时区下解释，服务端按各自登记的 `timezone` 解释、客户端按本机时区解释，因此跨时区时对方侧的 `in_class`／`break`／`free` 可能算错（处理方式见 5.4.10）。这不是接口能力缺口，而是本期范围的显式限定——`sync/pull` 与 `status` 都不向客户端下发对方时区（见 4.4「同步范围」未列时区），跨时区支持属后续候选，本期不做、也不为跨时区增加额外分支。
- **跨模块不得绕过 `application`**：任一模块要读取另一模块的数据或触发其用例，只能经 `application` 暴露的方法；模块之间不直接持有对方的 `data` 层实现（对应 4.2 第 3 条硬约束）。
- 后续候选功能（6.7）不得在第 4 章的模块边界内预留半成品入口。

## 5. 客户端对服务端的接口口径

本章规定客户端与服务端之间的接口契约：能力、路径、字段、错误码、鉴权、同步时序与冲突处理、时间格式、分页约定。

> **声明（非规范性）**：本章是**能力需求说明**，不是对既有服务端或既有客户端实现的描述。本文不宣称任何一条已经实现；实际实现形态以本地代码为准。

### 5.1 通用约定

- 传输：HTTPS + JSON（`application/json; charset=utf-8`）。
- 路径前缀：`/v1`。版本升级不兼容时提升前缀版本号，不做同一路径下的破坏性变更。
- 请求头（逐项豁免见下表与下方说明；未列豁免的一律必带）：

| 头 | 必填 | 说明 |
| --- | --- | --- |
| `Authorization: Bearer <access_token>` | 是（豁免见下） | 见 5.5 |
| `X-Client-Version` | 是 | 客户端版本号，服务端据此做最低版本拦截 |
| `X-Device-Id` | 是（`register`／`refresh` 豁免，见下） | 设备标识，用于冲突裁决的确定性排序（见 5.6） |
| `Idempotency-Key` | 写接口必填 | 客户端生成的 UUID，重试复用同一值 |
| `If-None-Match` | 读接口可选 | 携带上次响应的 `ETag`，用于省流 |

- **`Authorization` 的两处豁免**：`POST /v1/auth/register`（尚未持有令牌，凭据在请求体中）、`POST /v1/auth/refresh`（正是因为 `access_token` 已过期才调用，凭据是请求体中的 `refresh_token`）。这两类接口不得校验 `Authorization`，其余 `/v1` 接口一律必带；`X-Client-Version` 与写接口的 `Idempotency-Key` 按上表要求。`register` 的设备标识在请求体 `device_id`（5.4.1），`refresh` 的请求体只有 `refresh_token`（5.4.2），两者都不带 `X-Device-Id`。
- **天气动作不是 `/v1` 接口**：它是现有 `timetable.php` 的 `action=weather`，使用会话 Cookie（`PHPSESSID` + `withu_device`）而不是 `Authorization: Bearer`，**需要登录且为情侣账号**（未登录 401、非情侣账号 403），响应外层与字段见 5.4.13；因此它不在本节 `/v1` 的鉴权豁免与信封约定之内。

- 响应体统一信封：

```json
{ "data": { }, "error": null, "server_time": "2026-10-20T02:41:00Z" }
```

失败时 `data` 为 `null`，`error` 为：

```json
{ "code": "COUPLE_NOT_BOUND", "message": "对方还未与你建立关系", "retryable": false, "details": {} }
```

- 列表响应统一分页字段：`{ "items": [], "next_cursor": "…", "has_more": false }`（见 5.9）。天气动作的 `mode=lookup` 返回 `locations[]`，不是 `/v1` 列表资源，不适用本节分页约定（见 5.4.13）。
- **`server_time` 的位置固定在外层信封，不进入 `data`**：所有接口的每次响应都是「`data` + `error` + `server_time`」三层，`server_time` 一律与 `data` 同级。5.4 各接口的响应示例为简洁起见只列出 `data` 的内容（外层的 `error: null` 与 `server_time` 按本节信封理解）；5.4.8 因要演示同步流程的完整形态，给出了含外层信封的完整示例。

### 5.3 共享关系与可见性规则（服务端必须实现的三条硬规则）

**规则 1：绑定不产生任何默认可见权限。**

- 新建关系后，双方的 `visibility` 默认都是 `off`。绑定成功时对方的课表不可见。
- 「我能看对方」的充分必要条件是**对方**的 `visibility != off`；不是「我设了就能看」。可见性由被查看方单方面决定并可随时刻修改。
- 字段命名固定为 `my_visibility`（我允许对方看到什么）与 `peer_visibility`（对方允许我看到什么），两者都是 `off` / `status_only` / `full` 三档之一。任何响应中都不用嵌套的 `peer.visibility` 形式。

**规则 1 补充：关系状态的取值与取值时机。**

| 取值 | 含义 | 何时返回 |
| --- | --- | --- |
| `none` | 从未建立过关系 | 由 `GET /v1/couple/link` 返回（本机从未发起或接受过绑定；对方提交的待确认请求超时失效后也回落到 `none`，见下面的 `pending` 条目）；对 `pending` 调用 `POST /v1/couple/unbind`（撤回／拒绝）时，该接口的响应同样为 `state=none` |
| `pending` | 一方已提交对方 QQ 号，等待对方确认 | `POST /v1/couple/bind` 提交后、对方确认前；双方都能看到，不产生任何数据可见性 |
| `active` | 关系有效 | 双方各自明确同意后（接受带绑定意向的邀请，或按 QQ 号发起并经对方确认），直到任一方解绑或任一方注销 |
| `unbound` | 曾经建立、现已解除 | 任一方 `POST /v1/couple/unbind` 之后、或任一方 `POST /v1/auth/delete` 之后，直到本机建立新关系 |

- `state=none` 与 `state=unbound` 的分工：`none` 是「从来没有」，`unbound` 是「有过但已解除」。**客户端的数据与缓存处理一致**（都不显示对方数据、都清空对方数据缓存），**差异体现在文案与入口的文字上**：`not_linked` 显示「尚未绑定」+「绑定」入口，`unbound` 显示「关系已解除」+「重新绑定」入口（见 3.7 第 (2) 种情形与 F4；这两种状态不在 F2 对方列渲染，见 3.2 的双人模式定义）——两者点击后的实际操作相同（都进入绑定流程），只是文案区分「从未绑定」与「曾解除后重绑」，让用户知道发生了什么。
- `pending` 不是关系：处于 `pending` 时对方课表、状态、可见性一律不可读（按无关系处理），且不占用「一个 `active` 关系」的名额；`pending` 超过 7 天未确认自动失效并回落到 `none`。
- 无关系（`none` / `unbound`）时各接口的返回码分两类，规则固定如下：

| 接口 | 无关系时的返回 |
| --- | --- |
| `GET /v1/couple/link` | 200，`link_id` 为 `null`、`peer` 为 `null`、双方可见性为 `off`、`state` 为 `none` 或 `unbound` |
| `GET /v1/couple/status` | 200，`peer.state=no_data`（`self` 侧仍按 5.4.10 正常返回——确有副本时为 `in_class`／`break`／`free`，无副本时为 `no_data` + `self_no_schedule`，不受无关系影响；**不报 404**，避免小组件走异常分支） |
| `GET /v1/sync/pull?scope=peer` | 404 `COUPLE_NOT_BOUND`（不返回部分数据） |

- 上表的兜底只针对**读取对方数据的接口**：`scope=peer` 的拉取在无关系时返回 404 `COUPLE_NOT_BOUND`。**「无关系时返回 200 的接口只有两个」这一说法只在「需要关系才能读取或修改对方数据的接口」这一范围内成立**——该范围内确实只有 `link` 与 `status` 两个在无关系时返回 200 而不报 404（见上表）。**范围之外还有两个接口在无关系时也返回 200**，因为它们既不读取也不修改对方数据：`POST /v1/couple/unbind`（已 `unbound` 时幂等返回 200，便于客户端重试）与 `DELETE /v1/couple/events`（幂等，见下面「另外三类接口」）。`state=pending` 按无关系处理（等待确认期间不可读对方数据），`link` 接口例外地返回 200 并带 `direction`。
- 另外三类接口在无关系时的行为单独规定，不适用上面的读取口径：
  - `GET`／`PUT /v1/couple/visibility`：无关系（含 `pending`）时返回 404 `COUPLE_NOT_BOUND`（没有关系就没有可读写的可见性权级）。
  - `POST /v1/couple/unbind`：`none`（从未建立关系）时返回 404 `COUPLE_NOT_BOUND`；`pending` 时可调用，语义为撤回或拒绝，响应 `state=none`（`pending` 不是关系，不进入 `unbound`）；已解绑（`unbound`）时幂等返回 200 + `state=unbound`，便于客户端重试。
  - `DELETE /v1/couple/events`：**幂等**，无关系或已解绑时也返回 200（只做「解除该设备的通知注册」，不依赖关系状态），便于解绑流程无条件调用。

**规则 2：可见性三档，语义固定。**

| 值 | 含义 | 允许下发的内容 |
| --- | --- | --- |
| `off` | 不共享 | 除关系状态外不下发任何课表内容；`GET /v1/couple/status` 的 `peer.state` 为 `no_data` |
| `status_only` | 只共享实时状态 | 只允许 `GET /v1/couple/status` 的 `peer` 侧返回白名单字段——`state`、`no_data_reason`、`course_name`、`started_at`、`ends_at`、`next_course_name`、`next_starts_at`（即 5.4.10 的 `peer` 侧字段中除 `location` 外的全部；`location` 仅 `full` 档返回）；`GET /v1/sync/pull?scope=peer` 必须返回 403 `FORBIDDEN_VISIBILITY` |
| `full` | 共享完整课表 | 允许 F2 对方侧完整状态，且允许按 5.4 的字段定义拉取对方课表 |

**规则 3：解绑与撤回立即生效。**

- 任一方 `POST /v1/couple/unbind` 后，`GET /v1/sync/pull?scope=peer` 立即返回 404 `COUPLE_NOT_BOUND`；`GET /v1/couple/status` 则返回 200 + `peer.state=no_data`（不报 404，见规则 1 补充与 5.4.10）；`GET /v1/couple/link` 返回 200 + `state=unbound`。客户端必须清空 `status_cache` 与对方课表缓存。
- 任一方把 `visibility` 改为 `off` 时，对方的读取立即返回 403 `FORBIDDEN_VISIBILITY`（状态接口则降级为 `no_data`，不报错，避免小组件异常）。
- 解绑后落败方已缓存的对方数据不做远程擦除承诺（技术上不可保证），但客户端在解绑后必须立即删除本地缓存；服务端在解绑后不得再向任一方下发对方数据。**服务端已持有的云端副本在解绑后不删除**——只要账号还在，副本随账号保留，解绑只停止下发与读取，不触发删除；副本删除只走注销账号（5.4.3，见 4.4）。

### 5.4 请求／响应字段

#### 5.4.1 `POST /v1/auth/register`

注册与登录共用本接口：QQ 号未注册时创建账号（注册），已注册时校验密码后登录。服务端以 QQ 号作为账号唯一标识，以密码作为登录凭证。**密码是用户在注册时为本应用设置的登录密码，不是 QQ 账号密码**：接口不接受、不校验、不转发 QQ 账号密码，也不存在用 QQ 账号密码登录的路径；QQ 号仅作为账号 ID 与头像来源（见 3.4、5.5）。

请求：

```json
{ "qq": "10001", "password": "…", "invite_code": "8F3K2Q7M", "device_id": "uuid", "platform": "android", "app_version": "0.1.0", "locale": "zh-CN", "timezone": "Asia/Shanghai" }
```

- `qq` 必填，账号 ID；`password` 必填，本应用的登录凭证——由用户在注册时自行设置，与 QQ 账号密码无关，客户端不得在任何文案中暗示需要 QQ 账号密码。
- `timezone` 必填，IANA 时区名（如 `Asia/Shanghai`）：服务端登记该账号的时区，用于在 `GET /v1/couple/status` 按对方时区解释对方课表（见 5.4.10）。本期不校验双方时区是否一致（见 4.9），因此该字段只做登记与解释用途，不下发给对方。
- `device_id`／`platform`／`app_version`／`locale` 用于设备标识、最低版本拦截与本地化，属技术标识，不用于账号身份判定（隐私范围见 7.3）。
- `invite_code` 可选，**仅在本次调用会创建新账号（即注册）时有意义**：不带时为普通注册；带有效邀请码时，服务端在注册成功后按该邀请的绑定意向返回 `invite` 字段（见下）。已注册用户（登录）提交该字段一律被忽略。

语义与错误口径：

- **QQ 号未注册**（新账号）：校验通过后创建账号并直接登录，`is_new_account=true`。密码为空或低于最低要求时返回 400 `BAD_REQUEST`（`details.reason = "invalid_password"`）。
- **QQ 号已注册**（登录）：校验密码；密码正确则发放令牌，`is_new_account=false`；密码错误返回 401 `INVALID_CREDENTIALS`，客户端提示「QQ 号或密码不正确」，**不得区分两种失败原因**（避免账号枚举）。
- 鉴权强度由密码承担：QQ 号本身不是凭证，仅凭 QQ 号无法登录任何账号；该密码是清涵课表的登录密码，不是 QQ 账号密码，应用也不提供「用 QQ 账号登录」的方式。
- 不做邮箱验证、不发验证码：注册不经邮箱或短信确认即生效，没有待验证状态；密码找回不依赖邮箱，忘记密码时联系管理员重置（口径见 5.5）。

响应 `data`：

```json
{
  "user_id": "uuid",
  "qq": "10001",
  "avatar_url": "https://q1.qlogo.cn/g?b=qq&nk=10001&s=100",
  "is_new_account": true,
  "invite": {
    "inviter_user_id": "uuid",
    "inviter_qq": "10002",
    "inviter_avatar_url": "https://q1.qlogo.cn/g?b=qq&nk=10002&s=100",
    "bind_requested": true,
    "bind_grant": "…",
    "bind_deadline": "2026-10-20T02:54:00Z"
  },
  "access_token": "…",
  "refresh_token": "…",
  "expires_in": 7200,
  "refresh_expires_in": 7776000
}
```

约定：

- **QQ 号是账号标识，密码是登录凭证**：服务端以 QQ 号作为账号 ID 并在响应中回显；一个 QQ 号对应一个账号，不做多账号合并。同一 QQ 号在另一台设备以正确密码登录即回到同一账号，`user_id` 与云端课表副本不变。**这里的密码是用户为清涵课表设置的登录密码，与 QQ 账号密码无关**：应用不要求、不接受也不使用 QQ 账号密码，不做 QQ 账号登录，也不引导用户到 QQ 侧授权。
- **不做邮箱验证、不发验证码**：提交即生效，没有待验证状态。
- **密码要求**：长度与复杂度下限由服务端定义并在客户端注册界面明示；密码仅用于本接口的登录校验，服务端只存加盐哈希，任何响应与日志不得回显密码明文。该密码由用户在注册时自行设置，不是 QQ 账号密码；注册界面必须就地说明这一点。
- `avatar_url` 由服务端按 QQ 号生成（`https://q1.qlogo.cn/g?b=qq&nk=<qq>&s=100`），客户端只当作普通图片 URL 使用并自行缓存；该地址不可用时客户端显示默认头像，不阻塞任何流程（该端点为腾讯未公开文档的地址，见附录 C.4.3）。
- `expires_in` 单位秒：`access_token` 2 小时，`refresh_token` 90 天。
- **`invite` 字段只在该次注册使用了有效邀请码时出现**（见 5.4.4）。`bind_requested` 原样反映邀请人生成邀请时的勾选结果：
  - `bind_requested=true`：客户端在注册成功后显示「{inviter_qq} 请求与你建立课表共享关系」的提示，用户选择「绑定」→ 调 `POST /v1/couple/bind`（带 `invite_code` 与 `bind_grant`）完成绑定；选择「暂不」则不建立任何关系，客户端不发起请求，邀请在窗口超时后由服务端自动消费。`invite` 同时携带 `bind_grant`（一次性绑定凭据，主判定依据）与 `bind_deadline`（待响应窗口截止时刻，注册成功时刻 + 13 分钟），两者语义与校验规则见 5.4.5。
  - `bind_requested=false`：**不显示任何绑定提示**，注册流程直接结束；该邀请只用于注册，不建立也不提示建立关系，响应的 `invite` 里不出现 `bind_grant` 与 `bind_deadline`（邀请即已消费完毕）。
  - 邀请码无效／过期／已使用时，注册仍然成功，但响应不含 `invite` 字段，客户端不应因此报错（见 5.4.4 的失效口径）。
  - **已注册用户提交邀请码不再有任何绑定效果**：登录（即 `is_new_account=false`）时服务端一律忽略 `invite_code`，响应不含 `invite` 字段，客户端也不得据此显示绑定提示。要建立关系请走 5.4.5 方式二（填写对方 QQ 号并发起绑定）。这一条保证邀请码的作用范围严格限于一次注册流程。

#### 5.4.2 `POST /v1/auth/refresh`

请求 `{ "refresh_token": "…" }`；响应同 5.4.1 的令牌字段（不含 `is_new_account`）。`refresh_token` 一次性轮换，旧的立即失效。**本接口不校验 `Authorization`**：正是因为 `access_token` 已过期才调用它，凭据是请求体中的 `refresh_token`（见 5.1 的豁免说明）。

#### 5.4.3 `POST /v1/auth/delete`

请求 `{ "confirm": true }`；响应 `{ "deleted_at": "…" }`。语义：注销账号、解除关系、删除云端课表副本；客户端一并清空本地共享课表相关缓存。

#### 5.4.4 `POST /v1/couple/invite`

请求：

```json
{ "bind_on_accept": false }
```

响应 `data`：

```json
{
  "invite_code": "8F3K2Q7M",
  "invite_url": "https://<host>/invite/8F3K2Q7M",
  "bind_on_accept": false,
  "expires_at": "2026-10-22T02:41:00Z"
}
```

约定：

- **两件事一次完成，都发生在被邀请人的这一次注册流程内**：邀请码同时承担「注册入口」与「是否表达绑定意向」两个语义，但后者由邀请人在生成时显式选择，且只是邀请人单方的意向、不构成对方的同意；关系仍须被邀请人本人在待响应窗口内点「绑定」后才成立（见 1.4）。两个语义都随该次注册流程的邀请码消费一起失效：`bind_on_accept=false` 的码在注册成功时即消费，`bind_on_accept=true` 的码在待响应窗口（13 分钟）内绑定成功或窗口到期时消费（判定依据见下面的生命周期条目）。
- `bind_on_accept` 是生成时固化的意向，**默认 `false`**，必须由客户端弹窗明确询问，用户勾选才传 `true`；未传时服务端按 `false` 处理，不得默认绑定。
- 生成后该意向不可修改：要改变意向需重新生成邀请码（新码使旧码失效）。
- 邀请码 8 位大写字母与数字，一次性使用，24 小时有效；同一用户同时只有一个有效邀请码。
- `invite_url` 是带邀请码的落地链接，客户端分享出去的内容用它；链接被打开时若能唤起应用则携带邀请码进入注册流程。**已注册用户打开该链接不产生任何效果**——不建立关系、不给绑定提示，客户端只提示「你已经是清涵课表用户，可直接登录」。
- 邀请码无效／过期／已使用时：**注册本身不受影响**，`POST /v1/auth/register` 仍返回 200，只是响应不带 `invite` 字段。不为此设独立错误码，避免「邀请码失效导致新用户注册失败」这种放大后果。
- **邀请码的两段式生命周期（`issued` → `awaiting_response` → 消费）**：
  - `issued`：邀请人生成后、被邀请人尚未用它注册。此时码只是注册入口，**最长保持 24 小时**——生成后 24 小时内无人用它注册即失效（与上面「邀请码一次性、24 小时有效」同一条规则）。
  - `awaiting_response`：被邀请人凭码完成注册、且该邀请 `bind_on_accept=true` 时进入此状态，`bind_deadline = 注册成功时刻 + 13 分钟`。**这个状态就是「还在注册流程内」的客观判定依据**——服务端不靠猜用户是否还停在提示界面上，只看该邀请是否处于 `awaiting_response` 且未过 `bind_deadline`。
  - 消费：以下任一先发生即消费完毕，码不可再用——(a) 被邀请人在窗口内调 `bind` 成功；(b) **窗口内对同一邀请的 `bind` 调用因凭据问题累计失败 5 次**（仅统计 `invalid_bind_grant`；服务端按 `invite_code` 计数，达 5 次即消费，后续提交一律按 `invite_window_closed` 拒绝——这是对 `bind_grant` 的防爆破上限）；(c) `bind_deadline` 到期（用户点了「暂不」但不发请求、或直接放弃，都靠这条兜底）。
    - **计入失败的只有 `invalid_bind_grant`**：它是唯一「凭据本身不对、且提交方可在窗口内反复重试」的 400。`invite_window_not_open`／`invite_without_bind` 针对的是窗口从未打开的邀请，计入会给 `issued` 状态的邀请新增一条「5 次即失效」的路径，与上面「`issued` 最长保持 24 小时」冲突；`invite_window_closed` 只在窗口结束后出现，此时邀请已消费、计数无意义；**409 `COUPLE_ALREADY_BOUND` 不计入**——它反映的是邀请人或被邀请人已存在 `active` 关系，与 `bind_grant` 爆破无关；`429` 与 `5xx` 同样不计入（前者是限流、后者是服务端异常，都不代表提交方在猜凭据）。
  - `bind_on_accept=false` 的邀请在注册成功时即消费，**不进入 `awaiting_response` 状态**、没有窗口。
- **主判定是 `bind_grant` 凭据，窗口只是兜底**：邀请处于 `awaiting_response` 期间，`POST /v1/couple/bind` 必须携带注册响应下发的 `bind_grant`（一次性、与「该邀请码 + 该注册用户」绑定，见 5.4.1），服务端校验凭据本身即可确认「确实来自刚完成的那次注册」，不依赖时钟推断；`bind_deadline` 只用于回收「一直没有响应」的码，不用于区分「刚注册」与「注册很久」。**校验顺序上是「先状态后凭据」**（见 5.4.5 的判定顺序）：凭据只在状态合格时才可能合法，状态判定必须在前，否则状态类错误原因会被「凭据不匹配」盖掉。
- **邀请码的消费时点不再表述为「注册流程结束」**：因为客户端点「暂不」不发请求（见 5.4.1），服务端无法感知流程何时结束，所以消费改由上面的显式状态与 `bind_deadline` 决定。据此，5.4.5 用三个 reason 精确区分失败原因——`invalid_bind_grant`（凭据问题）、`invite_window_not_open`（邀请仍为 `issued`、窗口从未打开）、`invite_window_closed`（窗口曾打开但已结束），不再用一个码兼表多种情形。

#### 5.4.5 `POST /v1/couple/bind`

有两条绑定路径，共用同一接口；按 QQ 号路径分「发起」与「确认」两次调用：

| 调用 | 请求 | 结果 |
| --- | --- | --- |
| 接受邀请（仅限注册流程内） | `{ "invite_code": "8F3K2Q7M", "bind_grant": "…" }` | `active` |
| 按 QQ 号发起绑定 | `{ "peer_qq": "10002" }` | `pending` |
| 确认对方发起的绑定 | `{ "link_id": "uuid", "action": "accept" }` | `active` |
| 拒绝或撤回 `pending` | `POST /v1/couple/unbind` `{ "link_id": "uuid" }` | `none` |

**接受邀请**：**只在邀请处于 `awaiting_response` 且未过 `bind_deadline` 时有效**（即被邀请人凭该码注册成功后 13 分钟内，见 5.4.4）。请求必须同时带 `invite_code` 与注册响应下发的 `bind_grant`；服务端按以下顺序判定（前四条都是 `400 BAD_REQUEST`，靠 `details.reason` 区分）——**先查邀请状态，再校验凭据**，因为 `bind_grant` 只在邀请进入 `awaiting_response` 后才下发（见 5.4.1），对状态不对的邀请先校验凭据只会得到「凭据不匹配」，把真正的失败原因（窗口从未打开／已关闭／未勾选绑定）全部盖掉：

1. `invite_code` 不存在（从未生成或已生成过但格式非法）→ `details.reason = "invite_window_not_open"`（未知邀请按窗口从未打开处理，不泄露邀请码是否存在）。
2. **邀请仍处于 `issued`**（从未被用于注册，窗口从未打开）——典型情形是已注册用户拿别人生成但尚未被任何新用户使用的邀请码来提交 → `details.reason = "invite_window_not_open"`。
3. **邀请曾打开窗口但已结束**（`awaiting_response` 已消费，或 `bind_deadline` 已过）→ `details.reason = "invite_window_closed"`。
4. 邀请 `bind_on_accept=false`（该邀请已在注册成功时消费、窗口从未存在）→ `details.reason = "invite_without_bind"`。**这一步只有在第 2 步未命中时才可达**：未勾选绑定但**尚未被任何新用户使用**的邀请仍属 `issued`，按第 2 步返回 `invite_window_not_open`；只有它已被那次注册消费后再提交，才命中本步。
5. **邀请状态合格（`awaiting_response` 内）后才校验 `bind_grant`**：缺失、与 `invite_code` 不匹配、或已被使用过 → `details.reason = "invalid_bind_grant"`。
6. 邀请人或被邀请人任一方已有其他 `active` 关系 → 409 `COUPLE_ALREADY_BOUND`（**本条不是 400**；一个用户同时只能有一个 `active` 关系，见下方约定）。

**为什么这个顺序**：第 2、3、4 步的判定依据都是服务端自己维护的邀请状态，不需要任何凭据；只有邀请确实处于 `awaiting_response` 时才可能持有合法 `bind_grant`，所以凭据校验必须放在状态判定之后。反过来排（先凭据后状态）会让第 2、3、4 步全部不可达——任何提交只要凭据不对就停在第一步，`invite_window_not_open` 与 `invite_without_bind` 永远不会返回。第 2、3 条的区分依据是邀请状态的两种取值（`issued` 未用 vs 曾打开后结束），不需要用一个码兼表两义。**「处于 `awaiting_response` 而 `bind_deadline` 已过」的邀请按第 3 步返回 `invite_window_closed`；`bind_on_accept=false` 的邀请在被注册消费后无独立剩余状态，按其是否处于 `awaiting_response`——`false` 不进入该状态——由第 2 步（尚未被使用）或第 4 步（已被使用）判定，不落入第 3 步**。客户端按 reason 分别提示：「这个邀请码无法用于绑定」（第 2 条）与「绑定窗口已关闭，请改用填写对方 QQ 号的方式发起」（第 3 条）。全部通过才建立关系并返回 `active`，同时立即消费该邀请（`awaiting_response` → 已消费）。邀请人生成邀请时的勾选与被邀请人的本次调用构成双方同意。**注册完成之后要绑定，只能走下面方式二**。

**按 QQ 号发起**：**注册完成之后建立关系的唯一路径**。提交后关系为 `pending`，不产生任何数据可见性；被请求方确认后才转 `active`（见 5.3 规则 1 补充）。

**确认 `pending`**：只有该 `link_id` 的被请求方、且关系仍为 `pending` 时可调用；调用成功后转 `active`。发起方不能用 `action=accept` 自行确认，否则返回 400 `BAD_REQUEST`（`details.reason = "invalid_pending_action"`）。

响应 `data`（`pending` 与 `active` 两种形态）：

`pending` 形态的 `data`（按 QQ 号发起后）：

```json
{
  "link_id": "uuid",
  "state": "pending",
  "peer": { "user_id": "uuid", "qq": "10002", "avatar_url": "https://q1.qlogo.cn/g?b=qq&nk=10002&s=100" },
  "my_visibility": "off",
  "peer_visibility": "off",
  "requested_at": "2026-10-20T02:00:00Z",
  "bound_at": null,
  "unbound_at": null
}
```

`active` 形态的 `data`（接受邀请或确认 `pending` 成功后）：

```json
{
  "link_id": "uuid",
  "state": "active",
  "peer": { "user_id": "uuid", "qq": "10002", "avatar_url": "https://q1.qlogo.cn/g?b=qq&nk=10002&s=100" },
  "my_visibility": "off",
  "peer_visibility": "off",
  "requested_at": "2026-10-20T02:00:00Z",
  "bound_at": "2026-10-20T02:41:00Z",
  "unbound_at": null
}
```

约定：

- **两条绑定路径都需双方同意，区别只在同意的收集时机**：在注册流程内接受邀请时，邀请人生成邀请时勾选 `bind_on_accept` 是其本人对本次绑定的同意，被邀请人点「绑定」是另一方本人的同意，两方各自表达后即 `active`；按 QQ 号发起时，发起方的提交只是意向、不构成对方的同意，必须由被请求方通过 `action=accept` 明确确认后才 `active`。任何一方的意向都不代替另一方的同意（见 1.4、3.4 邀请规则 4）。
- **`pending` 不是关系**：`pending` 期间对方课表、状态、可见性一律不可读；拒绝、撤回或超时失效后都回落到 `none`，不进入 `unbound`。超时后可重新发起。
- 同意只对当次绑定有效：`pending` 失效后重新发起、解绑后重新绑定，都需要双方各自重新表达同意；邀请码一次性使用、且只在待响应窗口内对凭 `bind_grant` 的调用有效，不能复用为他人的同意，也不能由已注册用户事后再拿来绑定。
- 一个用户同时只能有一个 `active` 关系；任一已有 `active` 关系时返回 409 `COUPLE_ALREADY_BOUND`。
- 绑定（`active`）成功后双方的 `my_visibility` 与 `peer_visibility` 都为 `off`（规则 1）。`peer` 对象只含身份信息（`user_id`、`qq`、`avatar_url`），可见性一律用同级的 `peer_visibility` 表达。

#### 5.4.6 `POST /v1/couple/unbind`

请求 `{ "link_id": "uuid" }`。`active` 关系调用时响应 `{ "state": "unbound", "link_id": "uuid", "unbound_at": "…" }`，解绑后 `GET /v1/couple/link` 持续返回 `state=unbound`；`pending` 关系调用时语义为撤回或拒绝，响应 `{ "state": "none", ... }`，不进入 `unbound`；已 `unbound` 时幂等返回 200 + `state=unbound`；无关系（`none`）时返回 404 `COUPLE_NOT_BOUND`。单方即可调用，无对方同意要求。**本接口只解除关系，不删除任何云端副本**——双方的课表副本随各自账号保留，解绑后服务端不再向任一方下发对方数据，副本删除只走注销账号（5.4.3，见 4.4）。

#### 5.4.7 `GET`／`PUT /v1/couple/visibility`

`GET` 响应：

```json
{ "link_id": "uuid", "state": "active", "my_visibility": "status_only", "peer_visibility": "full", "updated_at": "…" }
```

`PUT` 请求 `{ "my_visibility": "status_only" }`，取值 ∈ `off` / `status_only` / `full`；响应同 `GET`。语义：只改「我允许对方看到什么」，不影响对方对我的可见性。

#### 5.4.8 `POST /v1/sync/push`

请求：

```json
{
  "semester": { "id": "uuid", "name": "2026 秋", "start_date": "2026-09-01", "total_weeks": 20, "week_start_day": 1, "current_week": 1, "time_slot_set_id": "uuid", "base_rev": 3, "updated_at": "2026-10-20T02:30:00Z" },
  "time_slot_sets": [
    { "id": "uuid", "name": "夏季作息", "semester_id": "uuid", "base_rev": 1, "updated_at": "2026-10-20T02:30:00Z",
      "slots": [ { "index": 1, "start_minute": 480, "end_minute": 530 } ] }
  ],
  "courses": [
    { "id": "uuid", "semester_id": "uuid", "name": "高等数学", "teacher": "…", "location": "教三 201",
      "color": "#3B82F6", "week_pattern": "custom", "weeks": [1,2,3,5,7], "day_of_week": 1,
      "slot_start": 1, "slot_end": 2, "base_rev": 4, "updated_at": "2026-10-20T02:30:00Z", "deleted": false }
  ],
  "overrides": [
    { "id": "uuid", "course_id": "uuid", "date": "2026-10-06", "type": "cancelled", "base_rev": 1, "updated_at": "2026-10-20T02:30:00Z" }
  ]
}
```

响应（**凡进入同步流程的请求，HTTP 状态恒为 200**——无论有无冲突，`applied` 与 `conflicts` 可同时存在于同一响应，见 5.6 冲突处理；**请求本身不合法时除外**，如缺 `base_rev`、`base_rev` 非整数、实体 `id`／`semester_id` 引用不存在，按 5.6 第 5 条与 5.8 返回 400 `BAD_REQUEST`，不进入本响应）：

```json
{
  "data": {
    "applied": [ { "entity": "course", "id": "uuid", "rev": 5, "seq": 42 } ],
    "conflicts": [
      {
        "entity": "course",
        "id": "uuid",
        "server_value": { "name": "高等数学", "location": "教三 201" },
        "server_rev": 6,
        "your_value": { "name": "高数（A）", "location": "教三 205" },
        "merged_value": { "name": "高等数学", "location": "教三 201" },
        "losers": ["name", "location"]
      }
    ],
    "cursor": "opaque-cursor"
  },
  "error": null,
  "server_time": "2026-10-20T02:41:00Z"
}
```

字段约定：

- `week_pattern` ∈ `all` / `odd` / `even` / `custom`；为 `custom` 时以 `weeks` 数组为准。
- `slot_start` / `slot_end` 指节次序号（从 1 起），不是时刻。
- `start_minute` / `end_minute` 为当日 0 点起的分钟数（0–1439）。
- **版本字段命名统一**：服务端实体版本字段一律叫 `rev`（响应里的 `applied[].rev`、`items[].rev`、`server_rev` 即实体版本）；客户端提交时表达「我见到的版本」的字段一律叫 `base_rev`。`semester`、`time_slot_sets`、`courses`、`overrides` 四类实体在 `sync/push` 请求中共用同一命名，请求里**只有 `base_rev`，没有 `rev`**：推送是「以我见到的版本为基线提交」，不需要在请求里回传服务端版本号。
- `base_rev` 是客户端最后一次见到的该实体版本号；服务端版本号从 1 起单调递增。新建实体（客户端本地新建、服务端尚无记录）的 `base_rev` 为 `0`，服务端按新增处理，返回 `rev = 1`。
- **四类实体都必须携带 `updated_at`**（`semester`、`time_slot_sets`、`courses`、`overrides` 一致）：它是 5.6 字段级裁决「较新者胜」的比较依据，缺失时按 5.6 第 5 条的 `missing_updated_at` 返回 400，不进入冲突流程。实体间的引用字段同样随请求提交：`semester.time_slot_set_id`（当前选用的节次模板）与 `time_slot_set.semester_id`（模板所属学期），两者可为同一批新建的实体，按 5.6 第 5 条解析。`time_slot_sets[].slots` 按 `index` 整组提交，其 `id`／`set_id` 由服务端按所属模板生成，客户端不提交（见 4.3 的 `time_slot`）。
- **排序字段与版本字段不是一回事**：`seq` 是服务端在每次落库时分配的**全局流序号**，在所有实体之间单调递增，只用于 `GET /v1/sync/pull` 的返回顺序与游标（见 5.9）；`rev` 是逐实体版本号，只用于 `base_rev` 乐观并发与冲突裁决（见 5.6）。客户端提交时不带 `seq`，服务端也不接受客户端指定 `seq`；`sync/push` 的 `applied[]` 与 `sync/pull` 的 `items[]` 都返回 `seq`，客户端只需按 `seq` 顺序应用，不要求持久化每个实体的 `seq`。
- **实体名字段 `entity` 的取值固定为四个**：`semester`（学期）、`time_slot_set`（节次模板）、`course`（课程）、`override`（调休项）——与请求体里的四类字段一一对应（请求中的 `time_slot_sets`／`courses`／`overrides` 为数组字段名，其元素在 `applied[]`／`conflicts[]`／`items[]` 中分别以单数 `entity` 值标识）。四类实体都参与 5.6 的乐观并发与冲突裁决，没有「不参与版本控制」的实体。
- `deleted` 为软删除标记，客户端不得物理删除后静默重传。
- `conflicts[]` 的四层语义：`server_value` 是该实体裁决前的服务端版本（三方合并的共同祖先之后的远端值）；`your_value` 是本次提交中**被裁决掉**的本地值（只含被裁决掉的字段，未落败的字段不出现）；`merged_value` 是服务端最终落库的服务端实体完整状态，也是服务端返回的 `server_rev` 对应的内容；`losers` 列出被裁决掉的字段名。响应示例中 `name` 与 `location` 是两个都被双方改过、且本地值均落败的字段，因此 `losers` 为 `["name", "location"]`，`your_value` 也只含这两个字段；`losers` 里的每个字段名都必须能在 `your_value` 中找到，反之 `your_value` 的每个字段也都必须出现在 `losers` 中（两者一一对应）。
- 客户端处理 `conflicts[]`：用 `merged_value` 更新本地实体（连同 `server_rev`），把 `server_value`／`your_value`／`merged_value`／`losers` 连同 `server_rev` 写入 `conflict_log`（表结构见 4.3，字段名与本节一一对应），并在界面上提示「有字段冲突，可查看／恢复」。不得用 `your_value` 覆盖本地实体，也不得丢弃 `your_value`。用户查看冲突时选择保留服务端版本或恢复本地版本，选择结果写入该条 `conflict_log.resolved_by`（`server`／`local`）；未处理前为 `pending`。
- 同步冲突**不使用 409**：只要 `base_rev` 能对上某一历史版本，服务端必定能按 5.6 的裁决规则给出确定结果，因此永远返回 200 + `conflicts[]`。409 只用于关系状态类冲突（`COUPLE_ALREADY_BOUND`）。

#### 5.4.10 `GET /v1/couple/status`（F2 卡片对方侧状态的服务端数据来源之一）

**`self` 侧与 `peer` 侧的数据来源不同，必须分清楚**：`self` 侧由客户端按本地课表实时推算，本接口返回的 `self` 只是服务端在确有本机副本时的参考值，客户端以自己的本地推算为准；`peer` 侧在对方可见性为 `full` 时有两个等价来源——本接口直接返回推算好的 `peer` 状态，或客户端用 `GET /v1/sync/pull?scope=peer` 拉到对方课表后在本机重算（见 4.7、5.6 拉时序），两者结果一致，客户端取先到者。对方可见性为 `status_only` 时不能拉取对方课表，本接口是 `peer` 侧的唯一来源（只返回 5.3 规则 2 的白名单字段）。**上述推算都建立在「双方同一时区」这一前提上**（见 4.9）：本接口的 `peer` 侧由服务端按注册时登记的 `timezone`（5.4.1）解释对方课表，客户端重算时按本机时区解释；本期不校验双方时区是否一致、也不下发对方时区，双方跨时区时 `peer` 侧状态可能不准，这是本期的范围限定而非缺陷。客户端不因时区差异做额外分支（不报错、不降级为 `no_data`），按现有口径展示。

查询参数：`at`（可选，ISO 8601；不传则取服务端当前时间）。

`at` 的允许窗口与判定规则（用于消除客户端时钟偏差，不用于查询历史或未来状态）：

- 判定基准是服务端的当前时间 `T`。允许区间为 **[T−5 分钟, T+5 分钟]**。
- `at < T−5min` 或 `at > T+5min` → 返回 400 `BAD_REQUEST`，`details.reason = "at_out_of_window"`，`details.allowed_window_seconds = 300`。
- 客户端只能传「本机时间经 `server_time` 校正后的当前时刻」；不得用 `at` 遍历历史或以未来时间探测对方后续课程。
- 请求不带 `at` 时按 `T` 计算，与传 `at = T` 等价；窗口判定针对客户端显式传入 `at` 的情况。

响应 `data`（成功且有数据时带 `ETag`）——**结构为 `self`（本机用户）与 `peer`（对方）两侧，各自独立携带一套状态字段**，对应 F2 卡片的同屏双列：

```json
{
  "self": {
    "state": "in_class",
    "no_data_reason": null,
    "course_name": "大学物理",
    "location": "教二 105",
    "started_at": "2026-10-20T02:00:00Z",
    "ends_at": "2026-10-20T02:50:00Z",
    "next_course_name": "英语",
    "next_starts_at": "2026-10-20T03:00:00Z"
  },
  "peer": {
    "state": "no_data",
    "no_data_reason": "peer_visibility_off",
    "course_name": null,
    "location": null,
    "started_at": null,
    "ends_at": null,
    "next_course_name": null,
    "next_starts_at": null
  },
  "my_visibility": "full",
  "peer_visibility": "off",
  "as_of": "2026-10-20T02:41:00Z",
  "stale_after": 300
}
```

字段语义（`self.*` 与 `peer.*` 内的字段含义一致，按侧解释）：

- 每侧的 `state` ∈ `in_class` / `break` / `free` / `no_data`（与 3.2 的四态一一对应，不允许其他取值；`break` 的含义是「未在上课、今天还有后续课程」，**含当天首节课开始之前**，见 3.2 的状态表）。
- 每侧的 `no_data_reason` 仅在 `state=no_data` 时有值，其余状态下为 `null`。对方侧的取值与判定优先级固定如下（高优先级命中即不再看后面的条件）；本机侧取值见本节末尾。优先级编号只对 `peer_visibility_off` 与 `peer_no_schedule` 生效；`not_linked`／`pending`／`unbound` 是服务端按关系状态返回的取值，双人模式前提不满足时小组件不渲染对方列（见 3.2 的双人模式定义），客户端只把它们用于关系引导，不作为 F2 对方列的原因文案。

| 优先级 | `no_data_reason` | 触发条件（对方侧） | 客户端展示 |
| --- | --- | --- | --- |
| 1 | `peer_visibility_off` | 关系有效但对方 `visibility=off` | 「对方未共享课表」，不提供直接改对方的入口 |
| 2 | `peer_no_schedule` | 关系有效、可见性允许，但对方无已上传的课表 | 「对方还没有课表」 |
| — | `not_linked` | 双方从未建立关系（`link.state=none`） | 双人模式前提不满足，不作 F2 对方列原因；由 3.7 第 (2) 种情形与 F4 承接 |
| — | `pending` | 已发起绑定、等待确认（`link.state=pending`） | 同上；`direction=outgoing`：「等待对方确认」+ 撤回；`direction=incoming`：「{对方} 请求与你建立关系」+ 接受/拒绝（`direction` 由 5.4.12 提供） |
| — | `unbound` | 关系已解除（`link.state=unbound`） | 同上；由 3.7 第 (2) 种情形与 F4 承接 |

- `self` 侧的 `no_data_reason` 只取 `self_no_schedule`（本机无课表）；**未登录不出现在本机侧的原因里**——本机侧是否无数据只由本地课表决定，登录态不影响本机侧展示（本机有课表且未登录时，本机侧照常显示自己的课表状态）。`not_linked`／`pending`／`unbound` 是对方侧的关系状态取值（只用于关系引导，不作 F2 对方列原因，见上表），不出现在本机侧，本机侧也不出现 `peer_visibility_off`／`peer_no_schedule`（这两个原因描述对方视角）。服务端返回的 `self.state` 与 `self.no_data_reason` 由「服务端是否持有本机副本」决定，不是由「本机是否有本地课表」决定，因此**服务端 `self.state=no_data` 只代表服务端没有副本，不代表本机没有课表**（见下条）。
- `self` 侧的推算依据：**本机课表在客户端本地实时推算，不受登录态、可见性与上传开关控制**——服务端不依赖本机上传的课表（本机 `my_visibility = off` 且未开启备份时，本机课表不上传，服务端侧没有本机课表可算）。只要本机有课表，客户端本地 `self` 侧就永远有值（可见性只控制对方能看什么，不控制自己看自己）；本机当天无课时客户端显示 `free`；本机没有任何课表时客户端显示 `no_data` + `self_no_schedule`。服务端侧的 `self` 取值口径与之按同一套语义、但依据不同：**服务端在确有本机已上传副本时返回按副本推算的结果；没有副本时返回 `state=no_data` 且 `no_data_reason=self_no_schedule`（返回 `no_data` 而不是 `free`，避免消费方把「服务端无副本」误读成「今日课程已结束」）**。客户端对 `self` 侧一律以本地推算为准，收到服务端 `self.state=no_data` 时不改变本机侧展示、也不据此判定本机无课表。
- `peer` 侧任何一种 `no_data` 场景下都返回 200，`peer.state` 置 `no_data` 并给出 `no_data_reason`，**接口本身从不返回 404**（无关系时也不报 `COUPLE_NOT_BOUND`，与 5.3 规则 1 补充一致）。
- `no_data_reason` 是展示用的**唯一依据**：客户端不得自行推断原因（例如把「对方无课表」显示成「未共享」），也不得把两侧原因合并成一句「未连接」。`no_data` 时一律不携带任何课程字段，原因本身不泄露课程内容。
- 每侧的 `location` 是**课程地点**（该侧当前这节课的上课地点，取自课表字段），不是用户所在位置。`peer.location` 只在对方对本机的 `peer_visibility = full` 时返回，否则为 `null`；`self.location` 是服务端持有的本机副本中的课程地点，**不按 `my_visibility` 过滤**——`self` 是本机视角的参考值，只回给本机账号，本机最终展示仍以本地课表为准。此字段不属于 1.4／3.5 红线所禁的用户位置类字段。
- 每侧的 `next_course_name` / `next_starts_at` 在该侧 `state` 为 `free` 或 `no_data` 时为 `null`。
- `my_visibility` 是本机用户对对方设置的可见性，`peer_visibility` 是对方对本机设置的可见性；用于展示「你也未共享」这类对称提示，与 5.4.7（`GET`／`PUT /v1/couple/visibility`）同名同义。
- `stale_after` 建议客户端多久后重新校时（秒）；客户端在本机可自推状态（`self` 侧完全本地推算；`peer` 侧在 `full` 时用缓存的对方课表推算，`status_only` 时用本接口返回的状态），此值只影响校时频率，不决定状态展示。

#### 5.4.11 `POST /v1/couple/events`

用途：注册「变化通知」的送达方式（对应 B1）。通道本身**不是**本接口的契约内容，客户端上报的只是一个通道标识与投递凭据，服务端按标识选择投递实现。

请求：

```json
{ "channel": "<channel_id>", "token": "<delivery-token>", "subscribe": ["peer_schedule_changed", "link_state_changed"] }
```

响应 `{ "channel": "<channel_id>", "subscribed": ["peer_schedule_changed", "link_state_changed"], "expires_at": null }`。

| 字段 | 说明 |
| --- | --- |
| `channel` | 通道标识，**开放字符串**，不是枚举。取值由服务端与客户端约定，至少包括：`vendor`（厂商推送通道）、`self_hosted`（自建长连接）、`none`（不注册推送，客户端只靠拉取）。服务端必须接受未知标识并返回 200，只把该设备标记为「无可用通道」，不得返回错误——避免新增通道时出现客户端与服务端版本耦合 |
| `token` | 该通道对应的投递凭据；`channel=none` 时为 `null` |
| `subscribe` | 订阅的事件类型；服务端对未知事件名忽略并在响应中回显实际生效的列表 |
| `expires_at` | 凭据失效时间；无失效概念时为 `null` |

`subscribe` 可订阅的事件类型及其语义（取值固定为这两个，新增事件名按与 5.8 相同的「一经公开不得改语义、只能新增」原则另行追加）：

| 事件名 | 触发时机 | 客户端应做什么 |
| --- | --- | --- |
| `peer_schedule_changed` | 对方的课表发生任何变更（课程增删改、节次模板或学期配置变更、调休项变更）且该变更已落库 | 触发一次 `GET /v1/sync/pull?scope=peer` 拉取对方最新课表；拿到后在本机重算 F2 对方侧状态并刷新小组件 |
| `link_state_changed` | 关系状态或可见性发生变化：绑定成功、对方解绑、对方注销、任一方 `visibility` 档位改变 | 触发一次 `GET /v1/couple/link` 更新关系状态与双方可见性；必要时清空对方数据缓存（解绑时）；解绑或注销时同时退出双人形态，双人卡片回到单列、对方列不再渲染（按 3.2 的双人模式定义，关系引导由 3.7 的入口承接）；仅可见性档位变化时，按 5.4.10 的 `no_data_reason` 更新对方列展示（`peer_visibility_off`／`peer_no_schedule` 两种） |

- 两个事件都只表示「有变化，去取一次」，不承载变更内容；服务端可以在一次通知里同时下发两个事件名，客户端按「拉取一次 + 查一次关系」合并处理，不重复请求。
- 事件名是契约的一部分：客户端只订阅这两个，收到未知事件名时忽略；服务端对未知订阅名忽略并在响应回显实际生效列表（见上表 `subscribe` 行）。

- 候选通道与取舍（具体选型见 8.2 Q7）：

| 候选通道 | 覆盖面 | 代价 |
| --- | --- | --- |
| 厂商推送通道（各 Android 厂商各自的推送服务） | 国内设备覆盖面最好 | 需要逐厂商申请与配置，接入数量随厂商增加 |
| 自建长连接 | 不依赖第三方，自控 | 需要常驻连接，受省电策略影响，耗电与保活是持续成本 |
| 不注册推送（`none`），仅靠拉取 | 无需任何通道依赖 | 变化延迟取决于拉取时机（见 5.10） |

- 明确不采用**依赖 Google 服务的推送通道**作为唯一手段：本应用面向国内高校用户的 Android 设备，该类服务在很多设备上不可用，会把「对方课表变更后尽快看到」变成不可用功能。
- 推送只做「提醒去拉取」，不承载课表内容；客户端收到事件后走 `GET /v1/sync/pull?scope=peer` 或 `GET /v1/couple/status` 取数据。
- 客户端不得假设推送必达：所有展示必须能在只有拉取（或只有本地推算）的情况下自洽。`channel=none` 是合法状态，不是降级异常。
- 注销/换绑：`DELETE /v1/couple/events` 请求 `{ "channel": "<channel_id>", "token": "<delivery-token>" }` 解除注册（注销账号、解绑时调用；设备卸载时客户端已不存在、无法发起请求，该情形下由通道侧的投递失败与凭据过期自然失效，不要求客户端在卸载时调用）。

#### 5.4.12 `GET /v1/couple/link`

有有效关系时（HTTP 200，`data` 内容）：

```json
{
  "link_id": "uuid", "state": "active",
  "peer": { "user_id": "uuid", "qq": "10002", "avatar_url": "https://q1.qlogo.cn/g?b=qq&nk=10002&s=100" },
  "my_visibility": "status_only", "peer_visibility": "full",
  "requested_at": "2026-10-20T02:00:00Z",
  "bound_at": "2026-10-20T02:41:00Z", "unbound_at": null
}
```

无关系或已解绑时（同为 HTTP 200，不用 404，`data` 内容）：

```json
{
  "link_id": null, "state": "none",
  "peer": null,
  "my_visibility": "off", "peer_visibility": "off",
  "requested_at": null, "bound_at": null, "unbound_at": null
}
```

待确认时（HTTP 200，`data` 内容）——`direction` 只在本状态下出现，两种取值各一例：

```json
{
  "link_id": "uuid", "state": "pending", "direction": "outgoing",
  "peer": { "user_id": "uuid", "qq": "10002", "avatar_url": "https://q1.qlogo.cn/g?b=qq&nk=10002&s=100" },
  "my_visibility": "off", "peer_visibility": "off",
  "requested_at": "2026-10-20T02:00:00Z", "bound_at": null, "unbound_at": null
}
```

- `direction=outgoing`（如上例）：本机是发起方，`peer` 是被请求方，界面显示「已发送绑定请求，等待对方确认」+ 撤回入口。
- `direction=incoming`：本机是被请求方，`peer` 是发起方，界面显示「{对方} 请求与你建立课表共享关系」+ 接受／拒绝入口；结构与上例相同，仅 `direction` 不同。
- `pending` 下 `bound_at` 必为 `null`；`my_visibility`／`peer_visibility` 固定为 `off`（待确认期间不产生任何可见性）。

- `state` ∈ `pending` / `active` / `unbound` / `none`，取值与时机见 5.3 规则 1 补充。`pending` 时返回 `link_id`、发起方向、对方 QQ 号与头像，但不返回任何课表内容；无关系时本接口返回 200 + `state=none` 或 `unbound`，不报 `COUPLE_NOT_BOUND`：在「需要关系才能读取或修改对方数据的接口」范围内，它和 `GET /v1/couple/status` 是仅有的两个无关系时返回 200 的接口（见 5.3 规则 1 补充的对照表；该范围之外，`unbind` 与 `DELETE /v1/couple/events` 在无关系时也返回 200，理由见 5.3），且不返回任何对方课表内容。
- 请求参数：`link_id`（可选）。不传时返回当前账号的关系状态；传已失效的 `link_id` 时按当前状态返回，不返回 404。
- **待确认请求的读取**：本机作为被请求方时，`pending` 关系里 `link_id` 是该待确认请求的标识（确认或拒绝时回传），`peer` 是发起方，`direction` 字段标识方向（`incoming` / `outgoing`），用于渲染「某某请求与你建立关系」与「等待对方确认」两种界面。

#### 5.4.13 `GET /api/timetable.php?action=weather`（W1 天气数据）

用途：客户端不持有和风 Key／Token，所有天气与地点数据经 withU 现有课表接口的天气动作获取；服务端持和风凭据（API Key 或 JWT），按 `mode` 转发并做短时缓存。**该动作与 login / bootstrap / partner 同一个 baseUrl、同一套会话（`PHPSESSID` + `withu_device`），不新增域名或路径；未登录 401、非情侣账号 403。** 它是只读 GET，不需要 CSRF token。

请求参数：

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `action` | 是 | 固定 `weather` |
| `mode` | 否 | `now`（默认）／`hourly`／`daily`／`lookup` |
| `lat`、`lng` | `now`／`hourly`／`daily` 必填 | WGS-84，建议 6 位小数；服务端按和风要求转成 `lng,lat` 并四舍五入到 2 位 |
| `q` | `lookup` 二选一 | 城市／地点关键字，例如 `杭州` |
| `number` | 否 | `lookup` 返回条数，示例 `10` |
| `days` | 否 | `daily` 用，默认 7，建议支持 3／7／10／15 |
| `hours` | 否 | `hourly` 用，默认 24，可选 24／72／168（取决于和风套餐） |
| `lang` | 否 | 默认 `zh`，透传和风语言参数 |
| `unit` | 否 | 默认 `m`（摄氏／公制），可选 `i` |
| `label` | 否 | 展示名覆盖，例如情侣双方地标／昵称；服务端用它填充 `location.name` 与 `data.city` |

**响应外层（天气动作专用，不是 5.1 的 `/v1` 信封）**：

```json
{
  "success": true,
  "code": 200,
  "server_time": "2026-10-26 22:10:00",
  "source": "qweather",
  "cached": false,
  "stale": false,
  "location": {
    "name": "杭州市",
    "latitude": 30.29,
    "longitude": 120.15,
    "admin1": "浙江省",
    "country": "中国",
    "district": null,
    "timezone": "Asia/Shanghai",
    "adcode": "101210101"
  },
  "data": { }
}
```

`location` 与 `WeatherLocation.fromJson` 同构（`name`／`latitude`／`longitude`／`admin1`／`country`／`district`／`timezone`／`adcode`）；`adcode` 放和风 LocationID，客户端只当不透明 ID 使用。

**`mode=now` 的 `data`**：同时提供两套字段，客户端优先用 `wmo_code` 归类，缺省回落中文文本。

- `weather`／`temperature`／`humidity`／`winddirection`／`windpower`／`reporttime`（Amap `lives[0]` 兼容字段）；
- `desc`／`temp`／`windDir`／`windScale`／`vis`／`city`／`obsTime`（withU 网页沿用字段）；
- `wmo_code`：服务端由和风图标码映射出的 WMO 码；`icon` 为和风图标码。
- 另有 `feelsLike`／`vis`／`precip`／`pressure`／`cloud`／`dew`／`wind360`／`windSpeed` 等可选字段，客户端当前不消费。

**`mode=hourly` 的 `data`**：

```json
{
  "latitude": 30.29,
  "longitude": 120.15,
  "hourly": {
    "time": ["2026-10-26T23:00", "2026-10-27T00:00"],
    "temperature_2m": [20, 19],
    "precipitation_probability": [10, 5],
    "precipitation": [0.0, 0.0],
    "snowfall": [null, null],
    "weather_code": [2, 1]
  }
}
```

- `time` 是**不带时区偏移的墙钟时间** `YYYY-MM-DDTHH:mm`，与课程时间同语义，直接比较。
- `weather_code` 是 WMO 码（服务端由和风 `icon` 映射）；`precipitation_probability` 取和风 `pop`；`precipitation` 取 `precip`；`snowfall` 和风小时预报不提供，返回 `null`。
- 和风逐小时通常 24h，付费套餐可 72h／168h；客户端按服务端返回的窗口降级显示，不假设一定有 16 天。客户端请求 `hours=168`，若服务端以 `weather_invalid_params` 拒绝则退到 `hours=24` 重试一次。
- 可额外返回 `qweather_hourly` 原始数组，客户端忽略。

**`mode=daily` 的 `data`**：`daily[]`，每条含 `fxDate`、`tempMax`、`tempMin`、`iconDay`、`textDay`、`iconNight`、`textNight`、`windDirDay`、`windScaleDay`、`humidity`、`precip`、`pressure`、`vis`、`uvIndex`、`sunrise`、`sunset`。本期课表页**不消费**逐日预报，契约保留。

**`mode=lookup` 的 `locations[]`**：

- 按关键字：`GET ...&mode=lookup&q=杭州&number=10`。
- 按坐标反查：`GET ...&mode=lookup&lat=30.29&lng=120.15`。
- 每条同时包含 `WeatherLocation.fromJson` 需要的字段（`name`／`latitude`／`longitude`／`admin1`／`country`／`district`／`timezone`／`adcode`）与和风 GeoAPI 原始字段（`id`／`lat`／`lon`／`adm1`／`adm2`／`tz`／`utcOffset`／`type`／`rank`）。
- **和风 GeoAPI 是城市级搜索／反查，不提供街道级逆地理**；`district` 通常为 `null`，客户端展示层已允许。

**认证与凭据（仅服务端可见）**：

- 客户端只用现有会话 Cookie（`PHPSESSID` + `withu_device`），不持有任何和风 Key／Token。
- 服务端支持两种和风认证，客户端无感：API Key（`X-QW-Api-Key`）或 JWT（`Authorization: Bearer`；静态 token 或由 Ed25519 私钥自动签发并缓存）。
- 认证选择顺序建议：静态 `qweather_jwt_token` → `qweather_api_key` → 用 `kid + project_id + private_key` 自动签发 JWT（缓存到过期前）→ 返回 `weather_not_configured`。
- 服务端配置项：`qweather_api_host`、`qweather_auth_type`、`qweather_api_key`、`qweather_jwt_token`、`qweather_jwt_key_id`、`qweather_jwt_project_id`、`qweather_jwt_private_key`、`qweather_lang`、`qweather_unit`。Key、Token、私钥绝不下发客户端。

**服务端缓存**：

| 模式 | TTL |
| --- | --- |
| `now` | 5 分钟 |
| `hourly` | 20–30 分钟 |
| `daily` | 60 分钟 |
| `lookup` | 24 小时 |

- 缓存 key 包含模式、坐标（2 位小数）、`lang`、`unit`、`days/hours`。
- 上游失败时若有旧缓存，返回 `stale: true` 并继续展示；命中新鲜缓存返回 `cached: true`。
- 客户端仍有自己的 3 小时 TTL、15 分钟失败退避与单飞；服务端缓存只是第二层。

**错误响应**：

```json
{ "success": false, "code": 502, "error": "weather_upstream_error", "message": "天气服务暂时不可用", "server_time": "2026-10-26 22:10:00" }
```

| HTTP | `error` | 含义 | 客户端行为 |
| --- | --- | --- | --- |
| 400 | `weather_invalid_params` | 缺坐标／参数非法 | 168h 被拒时退到 24h；其它不重试 |
| 401 | `weather_login_required` | 未登录或会话失效 | 按会话失效处理（清本地会话、引导重新登录） |
| 403 | `weather_couple_required` | 非情侣账号 | 隐藏天气，不弹错误 |
| 429 | `weather_rate_limited` | 服务端限流 | 按 `Retry-After` 退避，不并发重试 |
| 502 | `weather_auth_failed` | 和风 Key／Token 无效 | 静默隐藏天气 |
| 502 | `weather_quota_exceeded` | 和风额度／套餐不足 | 静默隐藏天气 |
| 502 | `weather_upstream_error` | 和风超时／异常 | 静默隐藏天气 |
| 503 | `weather_not_configured` | 后台尚未配置和风 | 静默隐藏天气 |
| 504 | `weather_timeout` | 上游超时 | 静默隐藏天气 |

- 天气错误**不弹错误弹窗**；有缓存时继续展示缓存，没有缓存时天气区/地点搜索入口显示「天气服务暂不可用」而不是空白或崩溃。
- 天气动作使用独立的 `success`／`code`／`error` 字段，不套用 5.8 的 `/v1` 错误码体系；`mode=lookup` 不是分页资源，不适用 5.9。

### 5.5 鉴权方式

- **账号模型：QQ 号是账号 ID，密码是登录凭证**。注册时「QQ 号 + 自设密码」即建号，登录以同一对凭据校验；服务端只存加盐密码哈希。不做手机号登录、不做第三方 OAuth 登录。**该密码是用户为清涵课表自行设置的登录密码，不是 QQ 账号密码**：应用不要求、不接受也不使用 QQ 账号密码，不提供 QQ 账号登录或 QQ 授权登录；QQ 号只承担账号标识与头像来源两个用途。
- **不做邮箱验证**：不发送验证码、不要求邮箱，注册提交即生效；服务端不得基于「未验证」拒绝请求。由此，清涵课表的登录密码是登录的唯一凭证：必须正确存储（加盐哈希）、必须校验（错误密码不得进入账号），并按 5.4.1 的口径以 `401 INVALID_CREDENTIALS` 统一拒绝，不做账号枚举提示。
- **忘记密码由管理员重置**：没有邮箱、手机号或密保问题可用于自助找回，因此密码找回走人工通道——用户联系管理员（即本项目的服务端维护者），由管理员核实身份后为该账号设置一个新密码，再以线下方式告知用户。该通道是运维操作，不是客户端能力：5.2 的 13 条接口不因此增减，客户端不新增「找回密码」页面或接口调用，登录界面只给出一句「忘记密码请联系管理员重置」的说明。管理员重置时的约束：先核实请求者确为该账号的使用者，**核实方式按可用证据择一，并优先采用仍在登录状态的设备**——(1) 用户仍持有已登录设备时，由用户在该设备的登录状态下自行操作并截图/复述账号内可见的信息（如账号头像、已绑定关系、云端课表中的课程），作为持有证据；这一步只用既有的登录态，不新增任何页面或接口；(2) 用户无法使用任何已登录设备时（设备丢失、损坏、换机等，这正是需要重置的常见原因），改用线下核实：至少提供该 QQ 号，并补充仅账号持有者可知的信息（注册时间、近期考勤或课表中的课程与节次、云端备份中的某门课程名称等由管理员在后台比对），比对通过才重置。核实不通过不得重置；只设置新密码、不回显也不告知原密码；重置后该账号的全部已发放令牌作废，需重新登录。管理员不得为其他目的查看或使用用户密码（服务端本就只存加盐哈希，无明文可看）。
- 登录按需发生：仅在用户开启云端备份或使用共享课表功能时引导注册／登录，应用不在首次启动时强制登录；未登录时客户端不携带令牌发起任何请求。
- `access_token` 走 `Authorization: Bearer`，有效期 2 小时；过期返回 401 `UNAUTHENTICATED`，客户端用 `refresh_token` 换新令牌后重放原请求（重放必须复用同一 `Idempotency-Key`）。
- `refresh_token` 有效期 90 天、一次性轮换；`POST /v1/auth/refresh` 失败返回 401 `TOKEN_EXPIRED`，客户端必须回到登录界面（注册与登录共用接口，已有账号的用户重新输入凭据登录即可）并清除本地令牌。
- 共享关系的授权**不体现在令牌里**：令牌只代表「我是谁」，不代表「我能看对方」。每次访问对方数据的权限都由服务端按当时的 `visibility` 与关系状态即时判定（规则 1、规则 3），客户端不得缓存授权结论超过一次请求。
- 需要账号身份或对方数据权限的接口必须同时校验令牌、关系状态、可见性；任一不满足时按 5.8 返回明确错误码，不得返回降级后的空数据（`status` 接口的 `no_data` 除外，见 5.4.10）。5.1 的豁免接口（`register`／`refresh`）按其各自口径处理；天气动作按 5.4.13 的会话 Cookie 与 401／403 处理；5.3 明确无关系时幂等返回 200 的 `unbind`（已 `unbound`）与 `DELETE /v1/couple/events` 不适用本条。

### 5.6 同步时序与冲突处理

**推时序（客户端改动 → 服务端）**

```
1. 本地写库：更新实体 + 写 pending_change（记录 base_rev）
2. 前台时立即尝试 push；离线则排队，联网后按 created_at 升序重放
3. push 正常 → applied 中的实体用返回的 rev 覆盖本地 rev，删除对应 pending_change
4. push 返回 conflicts → 进入冲突流程（见下），不得盲目覆盖
5. 网络 / 5xx / 429 → 保留 pending_change，指数退避重试，复用同一 Idempotency-Key
```

**拉时序（对方改动 → 客户端）**

```
1. 收到 peer_schedule_changed 推送，或进入对方课表页，或轮询到期
2. 用本地 last_cursor 调 GET /v1/sync/pull?scope=peer
3. 按 `seq` 升序逐条应用，用 `rev` 覆盖本地缓存；cursor 前进；has_more 为 true 则继续
4. 写入 status_cache：用最新对方课表在本机重算 F2 对方侧状态（不等待下一次 status 请求）
5. 触发一次小组件数据下发 + updateWidget（本机侧快照不变，只更新对侧）
```

**冲突处理（本应用自行定义，服务端与客户端共同实现）**

同类产品普遍不公开冲突规则（见第 2 章），因此这里给出完整规则：

1. **并发模型**：以实体为粒度做乐观并发，共有四类实体——学期（`semester`）、节次模板（`time_slot_sets`）、课程（`courses`）、调休项（`overrides`）（字段名见 5.4.8）。每个实体带单调递增 `rev`；客户端提交时用 `base_rev` 表达「我见到的版本」，四类实体一律如此（见 5.4.8 的版本字段命名约定）。
2. **接受条件**：`base_rev == 服务端当前 rev` → 直接接受，返回新 `rev = base_rev + 1`，写入 `applied[]`。四类实体走同一条件，没有例外。
3. **`base_rev` 不匹配时做字段级合并**：把 `base_rev` 对应的服务端历史版本作为共同祖先，做三方合并。服务端只要能在历史版本中找到 `base_rev`，就一定能算出结果，因此**返回 200 + `conflicts[]`，不返回 409**。
   - 只有本地改过的字段 → 取本地值。
   - 只有远端改过的字段 → 取远端值。
   - 两边都改过同一个字段且值不同 → **规则化裁决**（不允许服务端静默丢弃任一方）：
     - `deleted=true` 优先于任何字段修改（删除胜过编辑）。
     - 双方都是普通字段修改时，比较 `updated_at`，较新者胜。
     - `updated_at` 完全相同时，比较 `X-Device-Id` 的字典序，较大者胜（保证双方算出同一结果，不会来回覆盖）。
   - 裁决结果写入 `merged_value`，被裁决掉的字段名写入 `losers`，被裁决掉的本地值原样写入 `your_value`（响应形态见 5.4.8）。
4. **冲突落败方的处理**：被裁决掉的本地值不得静默丢弃——服务端在 `conflicts[].your_value` 中原样返回，客户端把 `server_value`／`your_value`／`merged_value`／`losers`／`server_rev` 写入 `conflict_log`（表结构见 4.3），并在本机课表上给出一条「有字段冲突，可查看」的提示（冲突只发生在同一账号的多设备之间；对方课表为只读，不产生本机冲突记录，也不在其上提示）；用户可选择保留服务端版本或恢复本地版本，选择结果写入该条 `conflict_log.resolved_by`。客户端按 `merged_value` + `server_rev` 更新本地实体。
5. **服务端无法给出结果的唯一情形**：请求里缺少 `base_rev` 字段、`base_rev` 不是整数（负值同属非法）、缺少 `updated_at`、或实体 `id`／`semester_id`／`time_slot_set_id` 引用不存在。这些属于请求本身不合法，按 400 `BAD_REQUEST` 处理（`details.reason` 分别为 `missing_base_rev` / `missing_updated_at` / `unknown_entity_ref`），不进入冲突流程。**注意 `base_rev = 0` 是合法值**（表示本机本地新建、服务端尚无该实体，见 5.4.8），按新增处理并返回 `rev = 1`，不属于"缺少 `base_rev`"。**「引用不存在」指既不在服务端已有实体中、也不在本次请求的同一批实体中**：同一请求内新建的学期／节次模板／课程可以互相引用（`semester` 与 `time_slot_set` 互为引用时按同一批解析，不要求先后），服务端先按 `semester` → `time_slot_set` → `course` → `override` 的顺序落库、再统一回填同批引用，不判为 `unknown_entity_ref`。
6. **禁止项**：不得使用「最后写入优先且无记录」的静默覆盖；不得返回 200 但丢弃 `base_rev` 不匹配的实体；不得用 409 表达同步冲突。
7. **幂等**：同一 `Idempotency-Key` 重复提交返回首次结果，不产生第二次 `rev` 自增。

**对方的写入不存在**：客户端不提供写对方数据的通道（与第 2 章所述「写入对方日历」的模型相反）；接口层面也没有任何「写 peer 数据」的路径，因此不存在跨账号写冲突，只存在同一账号多设备冲突。

### 5.7 时间格式

| 场景 | 格式 | 示例 | 说明 |
| --- | --- | --- | --- |
| 交互时间戳（`updated_at`、`bound_at`、`as_of`、`ends_at`…） | ISO 8601 / UTC，带 `Z` | `2026-10-20T02:41:00Z` | 客户端展示时按本机时区转换 |
| 日历日期（`start_date`、调课 `date`） | `YYYY-MM-DD` | `2026-09-01` | 不带时区，语义是「当地日历上的这一天」 |
| 节次时刻（`start_minute` / `end_minute`） | 当日 0 点起的整数分钟 | `480` | 避免夏令时与跨时区歧义 |
| 有效期（`expires_at`） | ISO 8601 / UTC | `2026-10-21T02:41:00Z` | 与交互时间戳一致 |
| 天气实况展示时间（`now.data.reporttime`） | 上游兼容的本地化展示串 `YYYY-MM-DD HH:mm:ss` | `2026-10-26 22:00:00` | 仅用于展示，不参与计算；客户端优先取它，缺失时用 `obsTime`（见 5.4.13） |
| 天气实况机器时间（`now.data.obsTime`） | ISO 8601，带偏移 | `2026-10-26T22:00+08:00` | 客户端不用于计算，只作为 `reporttime` 缺失时的兜底 |
| 天气逐小时时间（`hourly.time`） | 墙钟 `YYYY-MM-DDTHH:mm`，不带偏移 | `2026-10-26T23:00` | 与课程时间同语义，直接比较；不做时区换算 |
| 天气响应 `server_time` | `YYYY-MM-DD HH:mm:ss` | `2026-10-26 22:10:00` | 天气动作的旧式信封字段；客户端**不**用它做 F2 时钟校正 |

约定：除天气动作的上述展示字段外，所有 `/v1` 接口的时间字段一律按上表，不使用本地化字符串、不使用秒级以外精度（毫秒截断为 0）、不使用 Unix 时间戳。`/v1` 接口每次响应带 ISO 8601 的 `server_time`，客户端据此校正本地时钟偏差（偏差超过 2 分钟时以服务端时间为准推算 F2 各侧状态）；**天气动作的 `server_time` 与 `reporttime` 是旧式展示串，不参与该校正**。**F2 各侧状态的推算以「双方同一时区」为前提**（见 4.9）：本期不保证跨时区双方的状态一致性——服务端按各自登记的 `timezone` 解释、客户端按本机时区解释，二者可能不同；本期不校验双方时区、也不向客户端下发对方时区，但不在时区差异上增加额外分支（相关口径见 4.9、5.4.10）。

### 5.8 错误码

| HTTP | `code` | 触发条件 | 客户端行为 |
| --- | --- | --- | --- |
| 400 | `BAD_REQUEST` | 参数缺失／格式错／密码为空或低于最低要求（`invalid_password`，见 5.4.1）／`at` 超出允许窗口（±5 分钟，见 5.4.10）／`base_rev` 缺失或非法／缺少 `updated_at`（`missing_updated_at`，见 5.4.8）／实体引用不存在／`bind_grant` 缺失、不匹配或已使用（`invalid_bind_grant`）／邀请仍为 `issued`、窗口从未打开（`invite_window_not_open`，见 5.4.5）／窗口曾打开但已结束（`invite_window_closed`，见 5.4.5）／邀请未勾选绑定却试图据此绑定（`invite_without_bind`）／非被请求方或非 `pending` 状态执行确认（`invalid_pending_action`） | 修参数，不重试 |
| 401 | `UNAUTHENTICATED` | 未带令牌或令牌无效 | 走 refresh 后重放（复用幂等键） |
| 401 | `INVALID_CREDENTIALS` | 登录时 QQ 号与该 QQ 号对应的清涵课表登录密码不匹配（注册外的登录校验失败；不是 QQ 账号密码） | 提示「QQ 号或密码不正确」，不区分两种原因，不重试 |
| 401 | `TOKEN_EXPIRED` | `refresh_token` 过期或已轮换 | 回到登录界面（注册与登录共用接口）并清本地令牌，已有账号的用户重新输入凭据登录 |
| 403 | `FORBIDDEN_VISIBILITY` | 对方 `visibility` 不足以完成该请求：`off` 或 `status_only` 时拉取对方课表（见 5.3 规则 2） | 按对方档位区分文案：`off` 显示「对方未共享课表」；`status_only` 显示「对方只共享实时状态」，并保留 `status_cache`（状态仍可展示）；两种情形都只清对方课表缓存、不重试 |
| 404 | `USER_NOT_FOUND` | 绑定时提交的 QQ 号未注册 | 提示核对 QQ 号，不重试 |
| 404 | `COUPLE_NOT_BOUND` | 需要关系才能读取或修改对方数据的接口在无关系／已解绑时返回，即 `scope=peer` 的拉取、`GET`／`PUT /v1/couple/visibility`（无关系含 `pending`）、`POST /v1/couple/unbind`（无关系即 `none` 时）。**以下四种不返回本码**：`GET /v1/couple/link` 返回 200 + `state=none`／`unbound`；`GET /v1/couple/status` 返回 200 + `peer.state=no_data`；`POST /v1/couple/unbind` 在已 `unbound` 时幂等返回 200；`DELETE /v1/couple/events` 幂等返回 200（见 5.3 规则 1 补充） | 清共享课表缓存，入口切回未绑定态 |
| 409 | `COUPLE_ALREADY_BOUND` | 邀请人或被邀请人任一方已有 `active` 关系 | 提示先解绑 |
| 429 | `RATE_LIMITED` | 超出限流 | 按 `Retry-After` 退避，不并发重试 |
| 5xx | `SERVER_ERROR` | 服务端异常 | 保留本地队列，指数退避重试；本地功能不受影响 |

约定：错误响应不计入 `data`；`retryable` 明确标记是否可重试；错误码一经公开不得改语义，只能新增。**409 只用于关系状态冲突**（`COUPLE_ALREADY_BOUND`）；同步冲突一律走 200 + `conflicts[]`（见 5.4.8、5.6），因此不设 `REV_CONFLICT` 这类冲突错误码。

**天气动作是例外**：它使用独立的 `success`／`code`／`error` 字段与 `weather_*` 错误串（见 5.4.13），不套用本表的 `/v1` 错误码体系。客户端对 `weather_not_configured`、`weather_auth_failed`、`weather_quota_exceeded`、`weather_upstream_error`、`weather_timeout` 等一律**静默隐藏天气**，不弹错误；401 按会话失效处理，403（非情侣账号）隐藏天气；429 按 `Retry-After` 退避。

### 5.9 分页约定

- 采用**游标分页**，不用页码：请求 `limit`（默认 200，最大 500），响应 `next_cursor` + `has_more`。
- 游标是**不透明字符串**，客户端不得解析或构造；游标与 `scope` 绑定，跨 `scope` 使用返回 400 `BAD_REQUEST`。
- `GET /v1/sync/pull` 的游标只前进：游标内部以服务端分配的全局流序号 `seq` 为位置，即使中间有实体被删除，游标也单调递增；客户端发现本地数据与游标不连续时，以 `has_more` 为 true 连续拉取直到收敛。
- 顺序保证：同一 `scope` 内按 `seq` 升序返回（`seq` 在全部实体间单调递增，见 5.4.8），客户端按序应用，天然处理「先改后删」。逐实体的 `rev` 不参与排序——它每门课各自从 1 开始，无法表达跨实体的先后。
- **天气动作的 `mode=lookup` 不适用本节**：它返回 `locations[]`，不是 `/v1` 的列表资源，也没有游标或页码分页；`number` 只是返回条数上限。除天气动作外，所有 `/v1` 列表响应一律按本节。

### 5.10 客户端侧配额与降级要求（接口使用约定，含服务端配额监控的补充要求）

- `GET /v1/couple/status` 的轮询间隔不短于 60 秒，且优先用 `ETag` 命中 304；小组件的分钟级推进由本地推算完成，不靠缩短轮询周期。
- 对方课表 `sync/pull` 只在收到变更事件、进入对方课表页、或距上次拉取超过 30 分钟时触发；不做高频轮询，最长间隔即 30 分钟（不是「不轮询」，也不是短周期轮询）。
- 所有请求失败都必须落到「本地已有数据继续可用」这一结果上；接口可用性不作为单人功能的依赖。
- **天气动作的调用频率**：客户端按 3 小时 TTL、15 分钟失败退避、单飞与「同一坐标同一日期不重复请求」控制；服务端按 5.4.13 做第二层缓存（`now` 5 分钟、`hourly` 20–30 分钟、`daily` 60 分钟、`lookup` 24 小时）。
- **服务端侧配额监控（不占接口，属 A3 的补充要求）**：和风侧配额消耗集中在服务端（所有和风调用经 5.4.13 的天气动作），因此服务端必须对天气用量做监控——对照和风控制台用量、接近配额阈值时告警，并在代理侧做同参数的短时合并限流；客户端侧的坐标与日期缓存去重只是兜底（见 4.6、5.4.13、8.2 Q5）。`429` 由服务端按 `Retry-After` 统一表达，客户端照前三条处理。
- **客户端不直连和风**：天气动作的所有请求只发往 withU 服务端；客户端不持有和风 Key／Token，也不出现和风域名。

- **验收点（教务导入入口）**：适配脚本按约定的输入／输出格式放入社区仓库后，客户端不重新发版即可加载并使用它；未安装任何适配脚本时，教务导入入口显示为空列表并给出「如何添加适配」的指引，而不是报错或崩溃；导入失败时给出失败原因且不破坏已有课表。

- **验收点（多设备同步）**：同一账号两台设备 A／B，A 改课表后 B 在联网下拉后看到变更。
- **验收点（冲突合并）**：两端同时改同一门课的不同字段后合并结果字段级正确且不丢改动；两端同时改同一字段后套用 5.6 的裁决规则，结果与规则一致，且落败值可在冲突提示中查看并恢复。
- **验收点（幂等与补传）**：断网改动后联网自动补传；同一 `Idempotency-Key` 重复提交（含主动重放一次相同请求）后服务端只产生一次 `rev` 自增、客户端不出现重复课程。
- **验收点（游标管理）**：首次拉取不传 `since` 能拿到全量并按 `has_more` 连续翻页直到 `has_more=false`；之后每次拉取复用上次返回的 `next_cursor` 只拿到增量；本地游标与服务端不连续（如清库重装）时能重新收敛到与服务端一致；跨 `scope` 复用同一游标返回 400 `BAD_REQUEST` 且不写入任何数据。

### 6.6 5.2.0 共享课表功能与开源发布

- **交付物**：邀请码与邀请链接生成（含绑定意向弹窗）与邀请注册；双方同意的绑定流程（邀请路径凭一次性 `bind_grant` + 13 分钟待响应窗口限定在注册流程内，QQ 号路径为注册后唯一绑定路径，见 5.4.5）与单方解绑；可见性三档与权限判定；F1 互相查看对方课表（含界面切换入口）；F2 双人课表桌面卡片与双人模式开关（开关定义见 3.2）；变化通知注册（B1，通道待定）；解绑后的缓存清理；后台授权引导；第 8 章风险清单逐条给出结论或明确的「不做」判定。
- **验收点（邀请注册与绑定意向）**：生成邀请时弹出确认弹窗，默认未勾选；不勾选生成的邀请可用于注册，被邀请人注册成功后**看不到任何绑定提示**；勾选生成的邀请，被邀请人注册成功后看到邀请人的绑定提示，可绑定或暂不；两种情况下凭邀请码注册本身都成功；邀请码过期或已使用时注册仍成功、只是不出绑定提示；被邀请人未点「绑定」前不产生任何关系与数据可见性，且邀请人的勾选不被当作被邀请人的同意（见 1.4）。
- **验收点（绑定与解绑）**：按 QQ 号发起绑定后关系为 `pending`，此时双方都看不到对方任何课表数据；被请求方通过 `POST /v1/couple/bind` 的 `action=accept` 确认后变为 `active`，发起方自行确认被拒绝；`pending` 期间任一方可撤回或拒绝，拒绝后回落到 `none` 而不是 `unbound`；7 天未确认自动失效，失效后重新发起需双方重新同意；解绑后重新绑定同样需双方重新同意；提交未注册的 QQ 号返回「用户不存在」提示。
- **验收点（邀请码的作用范围）**：邀请码只在被邀请人的注册流程内生效——注册流程内可据 `bind_requested` 选择绑定或暂不；**邀请码在该次注册流程内即消费**，消费时点由服务端客观判定：勾选绑定意向的邀请在注册成功后进入 `awaiting_response` 并下发一次性 `bind_grant`，窗口 13 分钟，窗口内绑定成功或窗口到期即消费；未勾选绑定意向的邀请在注册成功时即消费、无窗口。验收点逐项（**判定先状态后凭据，见 5.4.5**）：注册响应含 `bind_grant` 与 `bind_deadline`（注册成功时刻 + 13 分钟）；窗口内带正确 `bind_grant` 调 `bind` 成功后邀请即消费，同一 `bind_grant` 第二次提交（邀请已消费）返回 400 `invite_window_closed`；**邀请处于 `awaiting_response` 内但凭据缺失或带错**返回 400 `invalid_bind_grant`；已注册用户拿**尚未被使用**的邀请码提交（无论带不带凭据）返回 400 `invite_window_not_open`；未勾选绑定意向的邀请在**已被该次注册消费后**再提交返回 400 `invite_without_bind`（尚未被任何新用户使用时按上一条返回 `invite_window_not_open`）；窗口已关闭或用已消费的码提交返回 400 `invite_window_closed`；用它走登录流程不返回 `invite` 字段也不显示任何绑定提示；已注册用户打开 `invite_url` 只提示可直接登录、不建立关系；注册完成后的绑定只能通过「填写对方 QQ 号 → 对方确认」完成。
- **验收点（F1 互相查看对方课表）**：绑定后默认双方都看不到对方课表；只有被查看方打开 `status_only` 或 `full` 后对方才能看到对应范围（`status_only` 时拉取对方课表返回 403 `FORBIDDEN_VISIBILITY`）；任一方改为 `off` 后对方立即无法读取；单方解绑后对方立刻退回未绑定态且本地缓存的对方数据被清除。
- **验收点（共享期间的上传门控，见 4.4）**：已登录且**关闭**云端备份的前提下——本机 `my_visibility = off` 时网络日志中无课表上传；把档位改为 `status_only` 或 `full` 后课表按队列升序补传，对方的 F2 对侧随之可算；改回 `off` 或解除关系后不再上传；备份开关旁存在「共享期间即使关闭备份，课表仍为对方可见范围上传」的说明文案。**另需构造一组对照**：已登录且**开启**云端备份时，无论共享关系处于 `none`／`pending`／`unbound`、或本机可见性为 `off`，课表都照常上传（关闭共享、解除关系、把可见性设为 `off` 都不停止上传），只有关闭备份本身才停止。
- **验收点（双人模式开关）**：设置中存在「双人模式」开关；(a) 未登录、或已登录但无 `active` 关系时开关置灰且点击给出「先登录／先绑定」引导，无法开启；(b) 有 `active` 关系时开关默认为开启（首次进入双人形态前有一次说明，用户确认或跳过），开启后标题区并列显示双方昵称、双人小组件按两列渲染；切换入口在对方可见性为 `full` 时可切换自己／对方（`status_only` 按 3.7 第 (2) 种情形不能切换）；用户关闭开关后回到单人形态（标题区只显示自己、切换入口按 3.7 第 (3) 种情形不列出对方课表、双人小组件回到单列只渲染自己的课表），且**不会因此解除关系或改变可见性**（开关只影响展示形态，不触碰 5.3 的可见性与关系状态，也不上报服务端）；(c) 开关状态只存本地，重装或换设备后回到「有 `active` 关系即默认开启」，且不进入 4.4 的同步范围——因此「同一账号两台设备显示一致」这一验收仅在两台设备的开关状态相同时成立，开关状态不同时各自按本机形态渲染，不算不一致；(d) 开关开启状态下任一方解绑或注销，自动回到单人形态，不残留对方的课表展示。
- **验收点（F2 双人课表桌面卡片）**：小组件同屏显示两人的当日课程；每侧在 `in_class` 时显示课程名与下课时间、跨到下一节后按本地推算切换、`break` 时显示下一节课、当天无课时显示空闲；**当天首节课开始之前显示为 `break` 并给出今天的第一节课名与上课时间**（不是 `free`、也不是空白）；**本机有课表且未登录时本机侧照常显示自己的课表状态**（不因未登录置为无数据）；**任一侧无数据时必须显示具体原因而不是「未连接」**——在双人模式已开启（存在 `active` 关系）的前提下分别构造对方关闭共享、对方无课表、本机无课表三种情形，小组件与课表页对应侧显示的文案各不相同且与原因表一致（本机无课表时给出「导入课表」「登录账号同步课表」两个入口）；另需构造尚未绑定、等待确认、已解除三种前提不满足的情形，验证双人小组件只渲染本机单列、不出现对方列与对方原因文案（这三种关系状态由 3.7 的入口与 F4 承接）；任一原因下都不泄露未授权方的课程内容；同一账号两台设备的开关状态相同时显示一致（开关只存本地，见双人模式开关验收点 (c)，状态不同时各自按本机形态渲染、不算不一致）；对方 `visibility=off` 时对侧推算停止并显示「对方未共享课表」，本侧不受影响；**点击行为与 3.2 的点击行为表逐项一致**——点左半停在自己的课表、点右半在对方可见性为 `full` 时停在对方课表（各一次点击，无需再切；`status_only`／`off` 时按 3.7 第 (2) 种情形不切换）、点课程块先切到该侧课表再展开该课程详情；点对方侧的 `no_data` 原因区域**不切换到对方课表**（该情形下对方课表入口不能用于切换课表），而是打开应用进入共享关系管理界面由原因对应的入口承接；点本机侧 `self_no_schedule` 原因区域停在本机课表界面由「导入课表」「登录账号同步课表」承接；卡片绑定的课表失效时普通打开、课程已不存在时不弹空详情、**双人模式开关未开启时不做静默切换**（改为提示用户手动开启，不擅自替用户开启）；应用未运行／后台／前台三种状态下点击结果一致，且只跳转一次。
- **验收点（B1 变化通知）**：以 `channel=none` 注册也能成功，且此时对方课表变更仍能在 5.10 规定的拉取时机被看到；以任一已支持的 `channel` 注册后，对方改课表能触发一次自动拉取并刷新对方课表页与小组件对侧显示；服务端对未知 `channel` 返回 200 并把该设备标记为无可用通道，客户端不报错；`DELETE /v1/couple/events` 调用后不再收到事件。
- **验收点（关系状态查询 F4）**：`GET /v1/couple/link` 在 `none`、`pending`、`active`、`unbound` 四种状态下都能正确展示关系状态、双方可见性与绑定时间；`pending` 时能显示发起方向（`direction`）与对方 QQ 号、头像，分别渲染「已发送绑定请求，等待对方确认」与「{对方} 请求与你建立关系」两种界面；解绑后再次查询返回 `unbound` 而不是 `none`。
- **验收点（关系接口状态口径）**：`GET /v1/couple/link` 在 `none` / `unbound` 两种状态下均返回 200 且不返回对方数据；`GET /v1/couple/status` 在无关系时返回 200 + `no_data`；`scope=peer` 的拉取在无关系时返回 404 `COUPLE_NOT_BOUND`；`GET`／`PUT /v1/couple/visibility` 在无关系（含 `pending`）时返回 404 `COUPLE_NOT_BOUND`；`POST /v1/couple/unbind` 在 `none` 时返回 404、在 `unbound` 时幂等返回 200、在 `pending` 时返回 200 + `state=none`。（这些接口与关系功能在本里程碑才交付，故验收点从 6.5 移入本节。）
- **验收点（系统集成与厂商授权引导）**：设置页存在「后台运行／自启动／通知权限」引导项，点击能跳到对应系统设置页；未授权时相关功能降级且不崩溃。**本条只验收引导项存在与跳转可达，不验收实际常驻效果**——厂商省电策略下的保活效果不作验收项（见 8.1 R5）。
- **验收点（风险清单收口）**：8.1 的 R1–R12 与 8.2 的 Q1–Q11 在发布时逐条处于三种已收口状态之一——「已按应对措施实现（有对应功能或测试证据）」「已判定不做（写进 3.5 或 6.7 并说明理由）」「已补齐依据（给出官方链接或真机验证记录，并把结论回写到对应章节）」。存在任何仍停留在「待决定」且会影响 5.2.0 范围的条目时，本验收点不通过。
- **验收点（发布）**：仓库含许可证、贡献指南、隐私说明与构建说明；按构建说明在干净环境能构建出可安装包；应用内无法进入任何已列入 Out of scope（3.5）的共享课表附加玩法与单人附加工具。

### 7.3 隐私说明

必须在仓库与应用内同时提供，且内容与实现一致：

- **账号只收 QQ 号与密码**：注册只收集 QQ 号与登录密码作为账号信息，用途限定为账号标识、登录校验与头像展示；不收集邮箱、手机号、通讯录，不申请 QQ 开放平台授权、不读取 QQ 好友与空间数据。除账号信息外，请求另带少量**技术标识**（设备标识 `device_id`、`platform`、`app_version`、`locale`、`timezone`，见 5.4.1），用途是设备识别、最低版本拦截、本地化与时区登记，不用于账号身份判定与用户画像；其中设备标识会进入账号安全日志（见下面的边界条目）。头像由 QQ 头像地址直接加载，客户端只做普通图片缓存。**收集的密码是用户为清涵课表设置的登录密码，不是 QQ 账号密码**：应用不要求、不接受也不使用 QQ 账号密码，不做 QQ 账号登录，界面不得让用户误以为要填写 QQ 密码。忘记密码时由管理员重置（见 5.5），该通道同样不需要用户提供邮箱或手机号，因此不改变本条的收集范围。
- **QQ 号可被他人知道，但登录需要密码**：QQ 号对外可见（头像、绑定交互都会用到），因此界面需说明「QQ 号是账号 ID，不要把清涵课表的登录密码告诉任何人」；服务端只存加盐密码哈希。
- **不采集行为数据**：不上报任何行为数据，包括**用户所在位置**、行踪与用机情况。F2 的状态完全由课表数据与时间推算。这里禁的是用户自身的位置与行为；课表自带的**课程地点**（上课教室）是课表字段，会随课表正常下发（见 5.4.10 的 `location`），两者不是一回事。
- **安全日志与行为数据的边界（两件事，不要混用同一套说法）**：
  - **行为数据**：用户的所在位置、移动轨迹、到达／离开事件、用机状态等——**一律不采集、不上报**（对应 1.4 与 3.5 的永久红线）。
  - **账号安全日志**：为对抗弱口令与撞库，服务端会记录**登录事件**的少量技术信息——**账号 ID、时间、登录结果、设备标识**（`X-Device-Id`／注册时的 `device_id`，见 5.1、5.4.1）。它用于「新设备首次登录」与「失败次数异常」两类判定与安全提示（见 R12），**不含 IP 归属地、不含地理位置、不做异地识别**，不用于任何行为分析或用户画像，也不下发给对方或第三方。安全日志按账号保留、随账号注销一并删除，并在本隐私说明中如实披露。**安全日志只覆盖登录事件，不覆盖天气请求**：天气动作（`action=weather`）与课表接口共用会话，服务端可能据此识别发起账号，但**不得记录坐标、搜索关键字或天气请求日志，不得用于行为分析或用户画像**；服务端只允许按 5.4.13 的 TTL 做短时缓存，且缓存按地点组织、不保留位置历史。这样天气／地点搜索不进入账号安全日志以外的任何持久记录。
- **单人使用默认不联网**：未开启云端备份且未使用共享课表功能时，除以下四类**用户主动触发或必要的数据更新**外不发生任何网络请求：天气取值（经 withU 服务端 `action=weather`；未连接 withU 时不发生）、节假日数据更新、应用内自更新检查，以及**教务导入的适配清单与脚本获取**。不登录也能使用全部单人课表功能；天气需要连接 withU，未连接时只是没有天气。逐项说明：(1) 天气请求只发往 withU 服务端，服务端再持和风凭据取数；请求携带会话 Cookie（因此与账号关联），但不携带课表内容，服务端不得记录坐标／搜索关键字或保留位置历史（见 5.4.13、7.4）；(2) 节假日更新只访问对应公开数据源，不上传课表与身份信息；(3) 自更新检查只访问更新源；(4) **适配脚本获取只发生在用户主动使用教务导入时**——用户不点开教务导入，客户端就不访问镜像地址与 GitHub（见 7.3 末条与 4.2），该请求同样不携带令牌与身份标识。四类请求均可在网络日志核对。
- **云端备份是用户的选择**：开启后课表数据上传到服务端用于备份与多设备同步，可随时关闭；关闭后走备份理由的上传停止（该账号没有共享关系、或可见性为 `off` 时即完全不再上传），已上传副本的删除走注销账号（`POST /v1/auth/delete`）。**需要明确披露的一点：备份关闭时，若存在 `active` 共享关系且本机可见性非 `off`，课表仍会上传**——共享课表需要服务端持有你的课表才能向对方下发状态与课程（见 4.4 的上传门控），此时关闭云端备份不会停止该上传；把可见性设为 `off` 或解除关系，这条上传理由才消失。**反过来说，备份开启时课表一律上传**（这是多设备同步的路径，与共享关系、可见性档位无关），此时关闭共享、把可见性设为 `off`、或解除关系都不会停止上传，要停止上传须关闭备份本身。这两点必须在设置页的备份开关旁与本节同时向用户说明，不得让用户以为关掉备份就已停止一切上传、也不得让用户以为关掉共享就已停止一切上传。
- **授权即撤即停**：可见性三档由被查看方单独设置，随时可改；解绑后对方立即无法读取（对应 5.3 规则 1、规则 3）。
- **最小化下发**：`GET /v1/couple/status` 只返回 F2 展示所需的字段；其中**课程地点**字段里，`peer.location` 只在对方对本机 `full` 时下发给本机，`self.location` 只回给本机账号自己的参考值、不构成向对方的扩权（该字段是课表自带的教室信息，与「用户所在位置」无关）。
- **数据归属与删除**：注销账号删除云端副本并解除关系（`POST /v1/auth/delete`）；解绑后客户端立即清空对方数据缓存。**解绑、把可见性改为 `off`、关闭云端备份都不删除服务端的云端副本**——副本随账号保留，不下发即不可读；删除云端副本的唯一途径是注销账号。用户如需彻底删除服务端课表，走注销账号。
- **耗电披露**：应用内说明后台保活与刷新对续航的影响，并说明不授予后台权限会导致小组件与提醒不准。
- **定位用途最小化**：定位只用于取一次经纬度以查天气，触发时机与天气开关绑定——引导界面开启天气、设置中首次开启天气、用户点击「获取当前位置」，三者之外一律不定位；引导未开启天气就不触发任何定位；不做后台持续定位；用户可完全不用定位，改用地点搜索自行选定地点。**天气坐标的去向只有一处**：坐标或关键字只发给 **withU 服务端的 `action=weather`**，由服务端持和风凭据转发给和风——**客户端不向其他任意第三方发送，也不直连和风／高德／Open-Meteo**。服务端只做短时缓存与转发，不落库坐标、搜索关键字或天气请求日志，不保留位置历史（见 4.6、5.4.13）；这些数据不用于行为分析或用户画像。天气请求使用会话 Cookie，服务端可识别发起账号，但不得把天气／地点数据用于账号安全日志以外的记录。地点搜索需要连接 withU，未连接时不发起。
- **外部 AI 辅助导入由用户自行决定**：应用不在内部发起任何 AI 或 OCR 请求，只在应用内展示可复制的导入提示词与 JSON 格式说明。用户把课表截图或描述粘贴到 DeepSeek、豆包等外部工具时，数据由用户自己选择的服务商处理，适用该服务商的条款；应用内需明确提示这一点，且不得默认替用户发送任何内容。
- **教务适配脚本的获取（仅在用户主动使用教务导入时发生）**：客户端会访问配置的镜像地址（主要路径）与 GitHub 仓库（兜底）以获取适配清单与脚本，**该访问只在用户打开教务导入入口时触发**——用户不点开教务导入，客户端不发起这类请求（这是 7.3 上文「单人使用默认不联网」四类例外之一）；镜像由本项目从规范源同步（同步以规范源为准，这是发布侧义务，客户端不做两源比较，见 4.2）；客户端只下载清单中列明且校验和匹配的脚本（**信任机制是「清单 + 校验和」，无签名**，见 4.2），不上传任何本地数据，请求不携带令牌与身份标识。
- 不做「不可单方解除」的关系绑定。

### 7.4 密钥管理

- **客户端不持有任何第三方服务密钥**：所有天气与地点数据经 withU 服务端的 `action=weather` 获取（见 5.4.13）；客户端不需要和风 API Key、JWT、Ed25519 私钥，`--dart-define` 里也没有任何天气密钥。
- **和风凭据只存服务端**：和风 API Host、API Key、静态 JWT、JWT 的 `kid`／`project_id`／Ed25519 私钥只放在服务端运行环境或加密配置中，**不下发客户端、不写进 APK、不进入客户端构建流程**；客户端代码中不出现任何和风域名或凭据常量。
- 服务端认证选择顺序：静态 `qweather_jwt_token` → `qweather_api_key` → 用 `kid + project_id + private_key` 自动签发 JWT（缓存到过期前）→ 返回 `weather_not_configured`。三种方式对客户端无感，客户端只发会话 Cookie。
- 服务端未配置和风凭据时返回 503 `weather_not_configured`；客户端据此**静默隐藏天气**，地点搜索入口显示「天气服务暂不可用」而不是空白列表，课表主体不受影响（见 4.6、5.4.13 的降级口径）。
- 密钥归属原则：**能放服务端就不放客户端**（已落实：客户端侧零密钥）。若将来确有必要引入必须随包分发的客户端凭据，才走构建期注入，并需在本文与隐私说明中单独说明理由。
- 服务端侧密钥纪律：构建与部署脚本不得回显 Key／Token／私钥明文、不得写进任何输出文件或日志；CI／部署只从加密变量读取；仓库（含服务端仓库）中不出现真实凭据，`.gitignore` 覆盖本地密钥文件，提交前检查不得包含真实 Key。

### 7.5 数据源合规

- **和风天气**（实况、逐小时／逐日预报、GeoAPI 城市搜索）：由**服务端**调用，客户端零密钥（见 7.4）。服务端须按其当前套餐与《使用条款》使用，并在控制台核对 API Host、配额与可用产品档位；**配额监控与合并限流落在服务端**（见 5.4.13、8.2 Q5）。若和风条款要求署名／链接，服务端提供署名文案与链接，客户端在天气区域按契约展示；客户端不再有 Open-Meteo 链接义务。
- **GeoAPI 粒度**：和风 GeoAPI 是城市级搜索与反查，不提供街道级逆地理，也不承诺校区／车站／商圈等 POI 级结果；这一点已在 3.3、4.6、5.4.13 写死，不能按旧 AMap 的地点级验收口径要求本期实现。
- **不再使用 Open-Meteo 或高德**：客户端不直连、服务端也不再把它们作为天气数据源；客户端代码、APK 与构建脚本中不出现 Open-Meteo／高德 API 地址或 Key（规划书与附录中的历史研究记录除外）。若未来恢复 POI 级搜索或更换数据源，须先核对许可、署名与配额要求并回写本节与 5.4.13。
- **定位**：使用 Android 系统定位 API 不涉及第三方数据源许可；客户端只取经纬度用于当次天气查询，不留存位置历史（仅在本地保留当前一个天气坐标，见 4.3 的 `weather_location`）、不做后台定位。
- **两条独立的约束，不要混为一谈**：(1) **产品定位**要求应用内不得出现广告、付费入口或商业化导流（见 1.4、3.5）；(2) **数据源许可**要求服务端按和风套餐与条款使用，配额、署名与可用档位以和风控制台为准。第 (2) 条不是客户端能自行解决的问题，必须由服务端配置与监控兜住。

| R9 | 邀请码／绑定被滥用 | 陌生人建立关系或骚扰 | **绑定关系必须由双方各自同意，任何一方的意向都不代替另一方的同意**（见 1.4、5.4.5）；邀请码一次性、24 小时有效；**绑定意向由邀请人在弹窗中显式勾选且默认不勾选**，不勾选时被邀请人注册后不会看到任何绑定提示；勾选时绑定仍需被邀请人自行确认；按 QQ 号发起绑定必须对方确认；任一方可随时撤回；一个用户同时仅一个 `active` 关系 |
| R10 | 精确闹钟权限被拒或被系统限制 | 提醒不准时 | 运行时用 `canScheduleExactAlarms()` 判断并按非精确降级；系统闹钟写入作为备选通道 |
| R11 | 和风天气套餐／配额与署名要求不匹配 | 服务端天气不可用或合规风险 | 服务端按控制台核对和风套餐、API Host、配额与可用产品档位；配额监控与合并限流落在服务端（见 5.4.13、8.2 Q5）；客户端零密钥（见 7.4）。GeoAPI 仅城市级，POI 级搜索不在本期承诺（见 4.6、7.5）。若和风条款要求署名，服务端提供文案／链接，客户端按契约展示 |
| R12 | 清涵课表登录密码被弱口令或撞库攻破 | 账号被他人登录、课表泄露 | 密码加盐哈希存储；登录失败统一返回「QQ 号或密码不正确」防账号枚举；服务端对同一 QQ 号的异常登录**做记录并在客户端提示**——判定信号只见「新设备首次登录」与「同一时间窗内失败次数异常」两类，**不使用用户所在地理位置或行踪做判定**（不取 IP 归属地、不做异地识别，与 7.3 的「不采集行为数据」一致；这类安全日志与行为数据的边界见 7.3）；把「是否增加第二凭证（设备确认等）」列为 8.2 Q11；密码只能由管理员在核实身份后重置，重置只设新密码、不回显原密码，并作废该账号全部已发放令牌；登录按需发生，不登录即不受该风险影响 |
