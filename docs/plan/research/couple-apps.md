# 情侣／双人协同类产品调研

调研时间：2026-10-20（以下所有来源的访问日期均为 2026-10-20）。
调研目的：为课表 App 的"情侣共享"主线（互相查看对方课表 + 桌面小组件展示对方当前课程）提供事实输入。
调研边界：只记录外部产品事实，不含本项目设计；不做市场规模的推算。

## 调研方法与可信度说明

- 可用工具受限：本环境 `web_search` 接口不可用（返回空结果），DuckDuckGo / Brave / Mojeek 均被拒或被网络拦截，仅 `web_fetch` 与 Apple 官方接口（`itunes.apple.com`）可用；Bing 中文站对产品类查询返回大量无关结果。因此本报告的**事实主源是官方渠道**：产品官网、官方帮助中心、App Store 官方接口返回的应用元数据（版本号、定价条款、评分、权限说明）。
- 取证失败记录（避免把"抓不到"误写成"没有此功能"）：DuckDuckGo、Brave Search 首页抓取直接失败；Mojeek 返回 403 并提示判定为自动化查询；`cn.bing.com` 对中文长尾词返回无关结果，`site:` 与引号运算符无效；百度百科返回 403；腾讯应用宝与酷安等第三方应用市场检索页未取到可解析内容；`support.timetreeapp.com` 的部分文章受 Cloudflare 保护返回 403（仅能取到无保护的文章）。以上均为取证失败，不代表对应功能不存在。
- 未获取到可直接引用的应用商店**用户评论原文**与社区讨论原文，相关部分一律标注"未证实"，不做推测性补全。
- 下文每条结论后附来源编号（见文末"来源清单"）。凡未取得官方或可核验来源的说法，均写"未证实"。

## 一、TimeTree（タイムツリー / TimeTree: Shared Calendar）

- **产品名与平台**：TimeTree，开发商 TimeTree, Inc.；iOS（App Store 评分 4.85／92,774 条）、Android、Web 版；官方称"全球 7500 万用户"（应用描述自述）。App Store 元数据记录版本 15.32.0，更新于 2026-10-13。来源 S1、S2、S3。
- **收费模式**：免费下载 + Premium 订阅，官网标价 4.49 美元/月、44.99 美元/年（首月免费，年付相当于省 2 个月），并注明"价格可能因地区与货币而异"。免费版可用共享日历、通知、相册、备忘、多日历；Premium 增加活动文件附件（免费版仅能在事件评论发照片）、纵向日视图、置顶重要事件、专属客服、去广告。来源 S2、S4。
- **两人绑定方式**：不是"情侣账号"模型，而是**群组日历**模型——任意成员创建日历后通过邀请把对方加入（官方帮助有"For Admins / For Members"两套邀请说明）；情侣只是"两人一组的共享日历"这一用法。来源 S5、S6。
- **共享数据的同步模型**：数据写在**日历**这一共享容器里，写入对全体成员可见。官方《Shared Calendar Guidelines》明确：日历共享后，事件（标题、时间、地点、参与人、备注）、评论、图片，以及为该日历设置的资料信息（头像、名字、生日）对**其他参与者全部可见**；其他参与者还可以再邀请新成员（新成员同样获得全部可见权），也可以经 API 或备份把共享信息带到第三方服务使用，此时该参与者对这部分处理成为独立的控制者（GDPR 第 4(7) 条口径）。**冲突处理机制未证实**（未见官方说明每次编辑的合并或最后写入优先规则）。来源 S6、S7。
- **桌面小组件做法**：iOS 支持锁屏与主屏小组件，Android 另有独立说明；小组件展示的是**所选日历中的事件**，可在"App 设置 → 在其他功能中显示的日历"里勾选要显示的日历，也可在小组件上设置"只显示我自己的事件"。官方明确限制：**iOS 小组件无法显示来自外部日历的事件**，事件不刷新时建议重启设备或重新添加小组件；点小组件启动 App 会进入 Home Calendar。来源 S8、S9。
- **通知与互动玩法**：事件创建／变更或消息会产生通知；每个事件内含聊天（"几点？""在哪？"都在事件里讨论）；共享相册、备忘与待办、事件内贴图、活动（Activity）流。来源 S2、S6、S8。
- **隐私与权限处理**：官方口径是**无需同意任何可选权限也能使用**（"必需权限：无"），可选权限包括日历、位置、照片、相机、广告追踪、通知、麦克风与语音识别，逐项说明用途。共享数据的保留规则：只要日历中还有参与者，日历信息就会被保留使用；退出日历或注销账号后，个人日历资料信息不再对其他参与者可见，并会从日历信息中移除；撤回同意的方式是删除自己的日历数据并退出日历，或通过咨询表单撤回全部共享日历的同意。来源 S1、S7。
- **可借鉴点**：① 以"共享容器 + 成员"抽象双人关系，天然支持未来扩展家庭／小组；② 小组件的"选择显示哪些日历"和"只显示我的事件"两个开关，是把可见性交还给用户的轻量做法；③ 明文的共享数据可见范围条款与撤回路径，比"承诺式隐私文案"更可核验。
- **短板与限制**：广告是其免费版体验的组成部分（Premium 才去广告）；iOS 小组件不支持外部日历事件，说明小组件数据管道与 App 内并非同一条；Web／PC 版存在（对课表类桌面查看是加分项，但也意味着多端一致性成本）。来源 S2、S4、S8。

## 二、Between（비트윈，韩国）

- **产品名与平台**：Between（비트윈），开发／发行商 DLT Partners Inc.；iOS（韩国区评分 4.72／269,112 条）、Android；bundleId `kr.co.vcnc.couple`，App Store 最早发布 2011-11-21，当前版本 5.14.03，最近更新 2026-09-22。来源 S10。
- **收费模式**：免费下载（韩国区显示"무료"），描述中含内购提示但**具体档位与价格未证实**（官方商店文案未列价目）。来源 S10。
- **两人绑定方式**：**未证实**。官方文案与权限说明均未描述配对流程；仅从产品形态可知是"两人一室"的关系型应用（"只有我们两个人的空间"）。来源 S10。
- **共享数据的同步模型**：以"两人专属空间"承载聊天、照片、视频、日记、备忘，官方称**换手机或清空相册后内容仍在**（即数据托管在服务端而非随设备走）。日历为"一起用的日历"，并在权限说明中出现"日历：修改和登记设备日历日程"，即**可与手机系统日历双向打通**。官方称支持"从其他 messenger 导入聊天记录"。冲突处理与字段级可见性**未证实**。来源 S10。
- **桌面小组件做法**：官方文案明确："我们交往了多少天？……**用小组件就能直接看到**，一起用的日历是附带的"——即小组件主打**纪念日／恋爱天数（D-day）**，共享日历是同一入口的附属能力。小组件是否能显示对方日程／状态**未证实**。来源 S10。
- **通知与互动玩法**：以聊天为核心（贴纸、动图、语音留言／对讲机、语音通话），照片／视频／日记／备忘按时间沉淀回忆；官方提供"其他 messenger 聊天记录导入"。来源 S10。
- **隐私与权限处理**：官方列明"必需权限：无"；可选权限为麦克风（语音消息／对讲机／语音通话）、蓝牙（无线音频设备）、相机、相册、日历、Siri（用 Siri 发文本消息）、Face ID（应用锁）。**用 Face ID 给应用加锁**是对"情侣内容不想被旁人看到"这一诉求的正面回应。来源 S10。
- **可借鉴点**：① 小组件首选"关系状态"而非"日程明细"，说明情侣类小组件的默认心智是**轻量、常驻、情感化**；② 应用锁（Face ID）把"私密内容"与"公开状态展示"分开处理；③ 手机系统日历双向同步是共享日程的低成本落地方式。
- **短板与限制**：产品重心在聊天与回忆，官方文案对"日程协同"只作附带描述，课表级共享不是它的能力方向；评分体量与更新活跃度集中在韩国市场。来源 S10。

## 六、横向对比：同步模型与小组件做法

| 产品 | 共享容器模型 | 谁可见 | 写到谁的数据里 | 冲突处理 | 小组件主要内容 | 小组件可自定义性 |
| --- | --- | --- | --- | --- | --- | --- |
| TimeTree | 群组日历（成员制，可 2 人可多人） | 日历内事件／评论／图片／日历资料，对全体参与者可见；新成员加入即获得全部可见权 | 写进共享日历容器，非写入对方个人日历（官方未见"写入对方日历"表述） | 未证实 | 所选日历的事件（日期／日程） | 可选择显示哪些日历；可设"只显示我自己的事件"；iOS 不支持外部日历事件 |
| Between | 两人专属空间 + 一起用的日历 | 两人之间；聊天／照片／日记以"只有我们两个人"表述 | 以服务端保存的两人共享内容为主；日历可与设备系统日历互通 | 未证实 | 纪念日／交往天数（D-day），日历为附带 | 未证实 |
| 小恩爱 | 关系绑定 + 多个共享模块（相册／日记／蜜语／定位／记账） | 相册"共同管理"；蜜语"只有情侣彼此可见" | 未证实（未见写入对方个人数据的表述） | 未证实 | 未证实（官方未提小组件） | 未证实 |
| 心动日常 | 自动上报的状态流（定位、用机记录、到达／离开） + 情侣内容模块 | 双方之间（甜言蜜语"只你可见"） | 状态由客户端自动上报到服务端，再向对方展示 | 未证实 | 未证实 | 未证实 |
| Cupla | 双人共享日历 + 待办清单 | 双方；以"灵活的隐私控制"调节共享范围（粒度未证实） | **可把计划直接加进伴侣的日历** | 未证实 | 官方仅称有小组件，展示内容未证实 | 未证实 |

结论性观察：

1. **主流同步模型是"共享容器"，不是"互相写对方的数据"。** 五个样本中只有 Cupla 的官方文案出现"把计划加进伴侣的日历"，其余都是把数据写进一个双方共同可见的容器（TimeTree 的日历、Between 的两人空间、小恩爱的共享模块）。来源 S6、S7、S10、S13。
2. **可见性控制是产品能力的一部分，且普遍较粗。** TimeTree 把可见范围写成条款（共享日历信息对全体参与者可见）并提供"退出即失去访问权"的边界；Cupla 声称有灵活隐私控制但粒度未公开；小恩爱／心动日常未见字段级可见性说明。来源 S7、S11、S12、S13。
3. **小组件的默认内容分化明显**：时间型产品（TimeTree）展示日程事件，关系型产品（Between）展示纪念日天数。把"对方此刻的状态"放进小组件的做法，在本次调研的五个样本中**没有一个取得官方证据**（TimeTree 的"只显示我自己的事件"是相反的取向）。来源 S8、S10。
4. **五款产品均未公开冲突处理规则**，因此"两人同时改同一节课怎么合并"在市面上没有可抄的公开答案——需要本项目自行定义并在产品内表达。

## 七、专项：情侣场景下"共享课表／查看对方现在在上什么课"的市面做法与公开诉求

### 7.1 市面做法（有来源的部分）

- **用通用共享日历承载课表**。TimeTree 官方商店文案直接点名学校／课程场景（"忘记各种学校活动和任务"、"把学校的通知拍照存进应用"），并把情侣用法描述为"在日历里看到双方的空闲时段，再安排约会"；Web 版可选权限中"日历"用于在 TimeTree 内显示设备日历。也就是说，课程表在现有产品里通常被当作**普通事件**手工录入或从设备日历导入，而不是结构化的"课程"实体。来源 S1、S2、S8。
- **用系统日历双向同步**。Between 的可选权限包含"日历：修改和登记设备日历日程"，说明共享日程可落到手机系统日历。来源 S10。
- **用定位与用机状态代替"现在在干什么"**。心动日常官方把主功能写成"手机使用记录，离开到达自动提示""实时定位，轨迹记录"，即用**自动上报的状态流**回答"对方此刻在哪、在做什么"；同类的 Lookus 官方文案表述为"全自动行程同步功能，会在对方抵达或离开重要地点时自动更新状态，无需反复发消息确认"，并强调"均需双方在知情前提下分别授权方可启用，双向确认"。来源 S12、S14。
- **方案化的课程表 App 侧**：本次未能找到任何有官方来源的、把"情侣课表共享"作为主功能的产品（Apple 中国区检索"情侣课表"返回的结果为共享日历、家庭日历、倒数日类应用，非情侣课表产品）。该条为检索结论，不排除存在未检索到的产品。来源 S15。

### 7.2 公开用户诉求（仅有官方文案层面的证据）

- **要减少反复确认。** TimeTree 商店文案把痛点写成"总担心对方是否知道我的安排？把日程沟通集中到 TimeTree，就不用每次再确认一遍"；Lookus 写成"无需反复发消息确认"。来源 S1、S14。
- **要"知道对方的生活节奏"而非精确轨迹。** Lookus 官方描述"日常作息状态、晚间是否已休息"这类**节律级**信息，并把它与精确定位区分开。来源 S14。
- **要边界感。** Lookus 官方反复强调"双向授权""尊重每一位用户的隐私边界""有关怀，更有边界感"——厂商主动用"边界"作卖点，说明用户对持续共享存在抵触。来源 S14。
- **要低耗电的常驻状态。** 心动日常官方主动披露后台 GPS 持续运行会显著影响续航，是该类功能的公认代价。来源 S12。

### 7.3 明确未证实、需要本项目自行决策的部分

- 五个样本的 **App Store 用户评论原文与社区讨论原文均未取得**（本环境无法访问评论页面与社区站点），因此"用户对课表共享的具体抱怨"没有可引用的一手证据。凡涉及评论内容的判断，本报告不作陈述。
- 是否存在以"情侣课表 / 对方当前课程"为卖点的产品，未证实。

## 八、风险提示（隐私、绑定关系解除、数据归属）

1. **隐私：状态共享会被用户读成监控。** 心动日常把"用机记录""离开到达自动提示"作为卖点，而 Lookus 把"双方分别授权、双向确认"写成宣传语，两者指向同一个张力：持续共享越自动，越需要显式的授权与撤回机制。课表类功能若展示"对方此刻在上什么课"，其信息敏感度低于定位，但仍应给出可关闭、可粒度化的开关。来源 S12、S14。
2. **绑定关系解除：市面上存在"不可单方解绑"的先例。** 小恩爱官方功能清单写明"虚拟结婚登记：一旦一对情侣成功登记，将无法单方面解除绑定"。这是明确的产品级锁定，对用户是不可逆风险；课表共享功能不宜复制这类设计。来源 S11。
3. **解绑后的访问权与数据保留需要明确规则。** TimeTree 的官方条款给出了一种可参考的写法：只要日历仍有参与者，日历信息就继续被保留使用；成员退出日历或注销账号后，其个人资料不再对其他参与者可见，并从日历信息中移除；撤回同意的路径是删除自己的数据并退出日历（或对全部共享日历提出申请）。来源 S7。
4. **数据归属：共享内容的"二次流转"不可控。** TimeTree 条款明确指出其他参与者可经 API 或备份把共享信息带到第三方服务，此时该参与者对这部分处理成为独立的控制者；新邀请的成员也自动获得全部共享信息的访问权。这意味着**"共享给一个人"实际等于"共享给这个容器当前及未来的所有成员"**。来源 S7。
5. **第三方 AI／广告使用共享数据的可能性。** TimeTree 条款说明可以用 AI 处理共享日历信息（如提醒、后续行动建议，含广告用途），但需用户明示同意，且不作为法律或类似重大影响的依据。来源 S7。
6. **厂商自述数据的可信度边界。** 用户量、降压力百分比等均为厂商自述（TimeTree"7500 万用户"、Cupla"50 万+ 情侣、大学背书调研"），本报告未找到独立来源复核，引用时应标注为自述而非事实。来源 S1、S13。
