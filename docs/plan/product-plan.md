# 清涵课表 产品规划书

- 产品名：**清涵课表**。全文「本应用」均指清涵课表。
- Android 包名（applicationId）：**`vip.qinghan.withu`**。
- 定位：**开源、免费、无广告**的 Android 课表软件；开源许可 GPL-3.0-or-later（见 7.1）；Android only；客户端技术栈 Flutter。

---

## 1. 产品定位与目标用户

### 1.1 一句话定位

清涵课表是一款**开源、免费、无广告的 Android 课程表应用**：单人可以完整地管理自己的课表；两人在双方分别授权后可以互相查看课表，**桌面卡片能同时显示两个人的课表，课表界面可以便捷地切换两个人的课表**。

### 1.2 产品主张

- **单人是完整可用的基础功能**，不是共享课表功能的前置任务。单人课表功能不登录、不依赖服务端即可全部使用；是否把课表上传到服务器由用户决定，云端备份默认关闭（见 3.4）。
- **共享课表是主线特色，且只做两件事**：互相查看对方课表（界面可一键切换自己／对方的课表）；桌面卡片同时显示两个人的课表。
- **差异化落点是「双人同屏」**：桌面卡片同屏显示两人的课表与当前课程状态，应用内便捷切换两个课表。课表共享在同类产品里已有先例，把「两人课表同屏 + 便捷切换」做成默认体验是本应用的差异点。
- **免费、无广告是产品承诺**：应用内不出现广告、付费入口与商业化导流（见 1.4、3.5、7.5）。

### 1.3 目标用户

| 用户 | 特征 | 主要诉求 |
| --- | --- | --- |
| 高校在读学生 | 每学期课表固定、按周次循环、有节次时间模板，需要经常看课表；手机以 Android 为主 | 免去反复打开教务系统查看课表的烦恼：低成本录完课表、看得清今天和本周、课前有提醒、桌面能看到下一节课 |
| 查看好朋友课表的一方或双方 | 两人在同一所学校或不同学校；想减少「你几点下课」「你现在有课吗」这类反复确认 | 不用问就知道对方当前状态；桌面一眼看到两人课表；同时不被持续监视 |

### 1.4 非目标与红线

- 不做社交关系链、不做公开课表广场、不做陌生人匹配。
- 不做任何监视性功能。对方状态只由课表数据与时间推算，不采集任何行为数据。此类功能是**永久红线**：不进入候选、不进入任何里程碑，也不因版本演进重新讨论（范围界定见 3.5）。
- 不把共享关系做成可以单方面建立的关系：**绑定关系必须由双方各自明确同意**。任何一方表达意向都不代替另一方的同意，不存在默认同意、推定同意，也不存在由一方代另一方确认的路径；一次同意只对当次绑定有效，`pending` 失效后重发、解绑后再绑都需双方重新同意。
- 不把共享关系做成不可解除的强绑定：任何一方都能单方解绑，且解绑后对方的跨账号读取立即失效。解除关系不需要对方同意，与上一条的「建立关系需双方同意」不矛盾。
- 「免费、无广告」是产品承诺：本应用自身不引入付费、广告、内购与商业化导流，并只使用与该定位兼容的数据源（见 7.1、7.5）。这不构成对使用者的许可限制——本项目以 GPL-3.0-or-later 发布，他人可依该许可商用。

## 3. 功能范围

范围分四块：单人基础功能（3.1）、共享课表功能（3.2）、天气功能（3.3）、账号与服务端数据能力（3.4）。每条给出**用户价值**与**验收点**（验收点写成可观察现象，不依赖实现细节）。范围之外的内容集中在 3.5，功能与服务端接口的对应关系集中在 3.6；界面设计特色不属于上述四块范围，单列于 3.7。

### 3.1 单人基础功能（In scope）

| 功能 | 用户价值 | 验收点（可观察现象） |
| --- | --- | --- |
| 课表录入与展示 | 一次录入整学期可用 | 能新建学期并录入多门课程；周视图按当前周正确渲染课程块；左右滑动可切换周次；今日视图只显示当天课程 |
| 课程字段 | 课程信息完整且贴近真实上课场景 | 每门课可设名称、教师、地点、周次、节次范围、颜色；同一时段可存在两门并行课程且都被显示 |
| 节次时间模板 | 不同学校／不同学期节次不同，不必每学期重录 | 可保存多套节次时间模板并在学期间切换；可对单个节次覆盖起止时间（不必所有节次等长）；支持按课程地点关键词自动匹配对应节次时间方案 |
| 周次表达 | 单双周、指定周是高校真实排课方式 | 周次支持「全部／单周／双周／指定周」四种表达；修改周次后周视图立即反映 |
| 调休与临时调整 | 法定调休、临时换课不需要改坏原课表 | 可对某个具体日期做调课／停课标记，且该调整只影响该日期，不影响周期模板 |
| 学期配置 | 当前周与开学日期对齐 | 可设开学日期、学期总周数、每周起始日、当前周；跨周后当前周自动推进 |
| 课表导入／导出 | 降低录入门槛，避免数据被锁死 | 支持教务导入、JSON 导入导出、ICS 导出、分享码导入、外部 AI 辅助导入、表格导入六条通道；导出的 JSON 可被本应用重新导入并还原为等价课表；ICS 导出文件可被系统日历识别；外部 AI 辅助通道提供可复制的导入提示词与 JSON 格式说明，用户用 DeepSeek、豆包等外部工具生成 JSON 后导入成功，应用自身不发起任何 AI 请求；教务适配脚本从配置的镜像源获取、镜像不可达时回退规范源（见 4.2） |
| 课前提醒 | 不漏课 | 可为某门课开启课前提醒并设置提前量；到点产生系统可见的提醒 |
| 桌面小组件（单人） | 不打开应用就能看到今天／下一节课 | 桌面添加小组件后显示今日课程；重启手机、修改系统时间、修改时区后小组件内容仍然正确；点击卡片直接打开应用并停在该卡片绑定的课表上，无需再手动切换（点击口径见 3.2） |
| 本地数据与备份 | 换机不丢课表 | 课表可导出为文件备份；导入备份文件后课表与备份前一致 |
| 深色模式与多尺寸小组件 | 桌面与系统外观一致 | 系统切换深色模式后应用与小组件同步变化；小组件提供至少紧凑型与列表型两种尺寸 |
| 考试与考试倒计时 | 除上课外，考试时间也是必须盯的信息 | 可录入考试（名称、日期时间、地点、关联课程）；考试列表按时间倒序展示并显示剩余天数；考试小组件可在桌面显示最近一场考试倒计时；可为考试设置提醒 |
| 课表统计与周报 | 看得见这周上了多少课、时间花在哪 | 统计页展示课程数、学时分布等汇总图表；生成周报摘要并支持分享；统计小组件可在桌面展示统计概览 |
| 任务与日程项 | 作业、杂项与日程不止「课程」一种 | 可创建任务（可关联到某节课程）；日程项支持独立于课程的重复规则；任务列表按状态管理 |

| 首次使用引导 | 一次性把关键选择做完，之后不再打扰 | 首次启动出现引导界面：引导「是否开启天气」——开启则当场请求定位权限并取一次定位（或改用地点搜索），不开启则**不发起任何定位**，后续用户自行开启天气时再触发定位；引导可跳过，跳过与拒绝都不阻塞进入课表主界面；引导完成后不再自动出现 |
| 表格导入 | 教务之外还有以表格形式流传的课表 | 支持从 HTML／表格文件解析课程并导入；导入前可预览并确认；解析失败给出原因且不破坏已有课表 |
| 应用内自更新 | 官网 APK 分发场景下不必手动重装 | 可检查更新、下载 APK 并校验哈希后唤起安装；更新源支持镜像配置 |

### 3.2 共享课表功能（In scope，仅以下两条）

| 功能 | 说明 | 用户价值 | 验收点（可观察现象） |
| --- | --- | --- | --- |
| F1 互相查看对方课表（界面切换） | 双方各自授权后，可在应用内查看对方当前学期的课表（周视图／今日视图），只看不改；课表界面提供便捷的切换入口，可在自己与对方的课表之间一键切换 | 不再需要反复要课表截图；对方课表变化后看到的是最新版本 | 未建立关系时入口不可用；建立关系并双方都授权后，能通过切换入口打开对方课表并看到与对方本机一致的课程；切换后视图形态（周／日）与操作方式与本机课表一致；对方修改课表后，本机下拉刷新能看到变更；任一方关闭授权后对方立即无法查看且切换入口退回不可用态 |
| F2 双人课表桌面卡片 | 桌面小组件**同时显示两个人的课表**：各自当天的课程块／当前课程与下一节课，同屏分列或分区呈现；数据由服务端按需下发双方峰值状态；卡片可点击——课表区域点开后直接停在对应一侧的课表，课程块点开后显示该课程详情（见下方点击行为） | 不用打开应用，桌面一眼看到两个人现在在上什么课、接下来是什么 | 添加小组件后同屏显示两人的当日课程与当前课程名；任一方课程结束进入下一节后，小组件在刷新周期内更新；某一方当天无课时该侧显示空闲状态；某一侧无数据时**显示具体原因**（尚未绑定／等待确认／已解除／对方未共享／对方没有课表，见下方原因表），而不是只显示「未连接」或空白，也不显示他人数据；点卡片课表区域与点课程块的结果与下方点击行为表一致 |

**F2 中每个人侧的状态口径（必须实现为这四种之一，不允许出现第五种含义）**：

| 状态 | 含义 | 展示要点 |
| --- | --- | --- |
| `in_class` | 正在上课 | 课程名、下课时间；可选地点（受 5.3 可见性控制） |
| `break` | 在两节课之间 | 下一节课名与上课时间 |
| `free` | 今天已无后续课程 | 今日课程已结束 |
| `no_data` | 该侧没有可展示的课表数据 | 该侧的**具体原因必须显示出来**，不得只说「未连接」或留空；原因取值固定为下表 `no_data_reason` 的五种之一，展示时给出对应的独立文案与下一步操作入口 |

**`no_data` 的原因口径（必须区分，不得合并成一句「未连接」）**：

| `no_data_reason` | 含义 | 展示文案与操作 |
| --- | --- | --- |
| `not_linked` | 双方尚未建立关系 | 「尚未绑定，绑定后可看到对方课表」+ 「绑定」入口 |
| `pending` | 已发起绑定，等待对方确认 | 「已发送绑定请求，等待对方确认」+ 「撤回」入口 |
| `unbound` | 曾经绑定，现已解除 | 「关系已解除」+ 「重新绑定」入口 |
| `peer_visibility_off` | 对方把可见性设为不共享 | 「对方未共享课表」+ 提示「请对方在其设置中开启共享」，不提供直接修改对方的入口 |
| `peer_no_schedule` | 关系有效且可见性允许，但对方尚未上传课表 | 「对方还没有课表」+ 提示「可提醒对方录入课表」 |

- 这五种原因**互斥且必须按优先级判定**：`not_linked` > `pending` > `unbound` > `peer_visibility_off` > `peer_no_schedule`。
- `no_data` 与原因同样适用于本机侧的异常情形：本机未登录、本机无课表时，本机侧显示对应原因而不是空白（本机侧原因取值见 3.2 与 5.4.10 的 `no_data_reason` 定义）。
- 无论哪种原因，都不得借该状态泄露任何未授权方的课程内容。

**F2 只读取课表推算的状态**：状态完全由课表数据与时间推算，不采集任何行为数据。自己的侧由本地课表推算；对方的侧只在授权范围内由服务端下发数据推算。

**F2 卡片点击行为（点哪里、进到哪，必须一一对应）**：

| 点击位置 | 打开后的结果 |
| --- | --- |
| 卡片的课表区域（某一侧的任意空白或状态区域） | 打开应用并**直接停在该侧对应的课表**上：单人卡片停在卡片绑定的那份课表；双人卡片左半停在自己的课表、右半停在对方课表，无需再手动切换 |
| 课程块（某一侧的具体一节课） | 打开应用、先切到该侧课表，再**展开该课程的详情**（课程名、教师、地点、周次、节次与当周该次课的时间）；对方侧的课程详情只读，且仅在对方可见性允许时可得 |
| 某一侧处于 `no_data` 的原因区域 | 仍切到该侧课表，由该侧原因对应的下一步操作入口承接（如「绑定」「重新绑定」「请对方开启共享」），不弹空详情 |

- **切换先于详情**：点击课程块时先完成课表切换再展开详情，避免在错误的课表上打开同名课程。
- **降级一律回落到普通打开，不猜目标课表**：卡片绑定的课表已被删除或失效时普通打开；课程在该课表中已不存在时只完成切换、不弹空详情；双人卡片在双人模式未开启时不做静默切换，改为在应用内提示用户手动开启（与 3.2 F1 的「入口不可用」口径一致）。
- **冷启动与热启动结果一致**：应用未运行、已在后台、已在前台三种情形下，点击同一位置得到相同结果；点击只触发一次跳转，不产生重复弹窗或重复切换。
- **不额外采集数据**：卡片点击只用于确定「打开哪份课表、展开哪门课」，不上报点击行为，也不因点击扩大任何一侧的可见范围。

### 3.3 天气功能（In scope）

| 功能 | 用户价值 | 验收点（可观察现象） |
| --- | --- | --- |
| 课表页天气呈现 | 出门前知道要不要带伞、穿多少 | 已有位置（地点搜索结果或定位坐标）时课表页显示本地天气（温度、天气现象、降水概率）；没有位置时天气区显示「暂无天气」且不阻塞课表使用 |
| 天气随日期变化 | 看课表时能直接看到当天的天气 | 切换到其他日期时，天气跟着该日期的预报变化 |
| 数据来源与署名 | 合规使用开放数据 | 每一处展示 Open-Meteo 数据的位置旁均有指向 open-meteo.com 的链接；无链接的天气展示视为验收不通过 |
| 位置来源（地点搜索优先） | 不必开启系统定位也能拿到天气，也不需要每次看课表都重新定位 | 提供地点搜索入口，输入关键字后按地点级粒度返回结果（校区、园区、车站、商圈、小区、建筑等，与地图应用搜同名关键字的结果类型一致），选中后立即出天气；选中地点在用户再次更新前保持不变；**不强制开启系统定位（GPS）**，拒绝定位权限时地点搜索通道仍完整可用 |
| 系统定位（按需，由引导与手动触发） | 定位只用于确定天气坐标，不常驻、不轮询 | 定位用 Android 系统定位（`LocationManager`，GPS／网络 provider，不依赖 GMS 与任何第三方定位 SDK），只取经纬度；**仅在引导界面选择开启天气时自动取一次**（或由用户在该步改用地点搜索），此后仅在用户点击「获取当前位置」时取一次；引导未开启天气时**不发起任何定位**，直到用户后续自行开启天气；除上述触发外不发起点位请求（无后台持续定位、无定位类前台服务）；仅授予粗略定位（Android 12+「大致位置」）仍能出天气；定位服务关闭／无可用 provider 时不取点、不报错，天气区显示「暂无天气」或沿用已有位置，课表全部功能可用 |
| 实况与地名（可选增强） | 当前天气与地点名可读 | 高德 Key 已配置且请求成功时，天气区显示实况与地名；Key 未配置或请求失败时退化为只显示预报，不报错、不崩溃（本条不作硬验收点） |

约定：**位置来源为「地点搜索优先 + 系统定位按需」；预报取 Open-Meteo（按经纬度，无需密钥）；实况、地点搜索与经纬度反查地名取高德 Web 服务（需 Key）**；定位取系统 API（`LocationManager`），不引入任何第三方定位 SDK，也不引入地图 SDK。客户端持有的唯一第三方密钥是高德 Web 服务 Key，按 7.4 的构建期注入治理（详见 4.6）。数据源许可与免费无广告约束落在第 7 章。

### 3.4 账号与服务端数据能力（In scope）

第 5 章的接口按本节与 3.1、3.2 的功能条目划分，编号如下：`A` 为账号与服务端基础能力（A1 账号与设备、A2 云端课表副本、A3 服务端配额与限流反馈），`B` 为变化通知能力（B1），`F` 为共享课表功能（F1–F4）。

**登录与上传规则（约束本节全部服务端能力）**：

1. **注册方式：QQ 号 + 自设密码**。QQ 号是账号的唯一标识（账号 ID），注册时同时设置登录密码；登录以「QQ 号 + 密码」完成鉴权。注册过程不需要邮箱验证、不发验证码，填写 QQ 号、设置密码、提交即完成注册（见 5.4.1）。QQ 号同时用于换取 QQ 头像作为账号头像。**这里的密码是用户注册时为清涵课表自行设置的登录密码，与 QQ 账号密码无关**：应用不要求、不接受也不使用 QQ 账号密码，不提供 QQ 账号登录；注册界面的密码输入框需就地注明「设置清涵课表的登录密码（不是 QQ 密码）」。
2. **账号的用途边界**：QQ 号只用于「标识账号 + 取头像 + 建立唯一的共享关系」，不用作第三方登录授权、不读取 QQ 空间／好友关系、不申请任何 QQ 开放平台权限。
3. **单人不强制登录**：全部单人功能在未登录状态下完整可用；登录时用户主动以「QQ 号 + 清涵课表登录密码」注册或登录。
4. **单人云端备份默认关闭**：是否把课表上传到服务器由用户在设置中决定，默认不上传；开启后自动完成登录并上传，关闭后停止上传与自动拉取（本地课表不受影响）。单人场景（无共享关系）下，未开启备份就不向服务端上传课表数据；存在共享关系期间的上传条件见 4.4 的上传门控。
5. **双人必须登录才能同步**：共享课表的绑定、互相查看、双人卡片与变化通知，以双方各自持有服务端身份为前提；未登录时共享课表入口不可用，单人功能不受影响。

**邀请注册的交互规则（约束 F3 与注释册流程）**：

1. **邀请码是注册入口**：已注册用户可生成邀请码／邀请链接，被邀请人凭码完成注册；邀请码不带绑定意向时，它只用于注册。
2. **绑定意向由邀请人在生成时决定，默认不勾选**：点「生成邀请」时弹出确认弹窗，弹窗内含一个默认**未勾选**的选项「同时与被邀请人建立课表共享关系」；用户勾选后生成带绑定意向的邀请，不勾选则生成纯注册邀请。弹窗不做记忆：每次生成都回到未勾选状态。
3. **被邀请人是否看到绑定提示，完全取决于邀请人的勾选**：
   - 邀请人勾选过：被邀请人注册成功后看到「{邀请人} 请求与你建立课表共享关系」的提示，可自行选择「绑定」或「暂不」，选择后不再提示。
   - 邀请人未勾选：**被邀请人注册成功后看不到任何绑定提示**，也不应出现关系相关的引导文案。
4. **绑定必须双方各自同意，没有默认同意**：这是适用于全部绑定路径的无条件规则（见 1.4 与 5.4.5）。邀请人勾选只是表达自己愿意绑定的意向，不代替被邀请人的同意，必须由被邀请人在提示中点「绑定」才建立关系；反过来，被邀请人同意也不代替邀请人。按 QQ 号发起同理：发起方的提交只是意向，要等对方确认。一次同意只对当次绑定有效，`pending` 失效后重发、解绑后再绑都要双方重新同意。
5. **被邀请人始终有权拒绝**：即使邀请人勾选，绑定也不自动成立；被邀请人点「暂不」后不再提示，也不产生任何关系。
6. **邀请码只用于注册，不承担授权**：凭邀请码注册不产生任何课表可见性；可见性仍由绑定后的三档独立设置（5.3 规则 1、规则 2）。

| 功能（编号 + 名称） | 用户价值 | 验收点（可观察现象） |
| --- | --- | --- |
| A1 账号与设备 | 一个 QQ 号就是一个账号，换设备可用同一账号继续；头像自动取 QQ 头像，不必自己设置 | 首次开启云端备份或首次使用共享课表时引导注册：填写 QQ 号并设置清涵课表的登录密码（不是 QQ 账号密码）即完成注册，不需要邮箱验证、不发送验证码；再次登录输入同一 QQ 号与密码即回到同一账号与同一份云端数据；密码错误时登录失败并提示，不会创建或进入他人账号；登录界面写明忘记密码需联系管理员重置、不提供任何自助找回入口；头像显示为该 QQ 号的 QQ 头像（取不到时显示默认占位图，不报错）；应用重启不需要重新输入凭据；令牌过期时自动续期且用户无感知；注销后本机令牌与云端副本一并清除 |
| A2 云端课表副本 | 用户开启后课表有云端副本，换机与多设备之间可对齐（单人离线使用不依赖它，默认不开启） | 云端备份默认关闭：未开启时不向服务端上传课表数据，关闭后上传停止且本地课表不受影响；已登录并开启备份时，同一账号两台设备能通过同步得到一致课表，断网期间的改动在联网后自动补传，重新开启后按本地队列补传 |

| B1 变化通知（客户端注册订阅） | 对方课表变更后本机尽快看到最新版本，而不是靠长时间轮询 | 注册订阅成功后对方改课表，本机在收到通知后自动拉取并刷新展示（通道待定，见 8.2 Q7） |
| F1 互相查看对方课表 | 见 3.2 | 见 3.2 |
| F2 双人课表桌面卡片 | 见 3.2 | 见 3.2 |
| F3 共享关系管理 | 建立与解除关系由用户自己掌控，且随时能调整对方可见范围 | 点「生成邀请」时弹出确认弹窗，其中「同时与被邀请人建立课表共享关系」默认未勾选，每次生成都回到未勾选；不勾选生成纯注册邀请，凭该邀请注册的新用户看不到任何绑定提示；勾选生成的邀请，注册成功后看到邀请人的绑定提示并可选择绑定或暂不；绑定在任何路径下都需双方各自同意，任一方未同意即不建立关系（见 1.4）；按 QQ 号发起绑定只是意向，对方确认后才建立关系；绑定后双方默认互不可见；可见性三档可随时切换且立即生效；任一方可单方解绑 |

### 3.7 界面设计特色

主界面的结构性入口只有两处：右上角一个隐藏入口承担全部设置与管理，顶栏标题区承担课表切换。主界面默认不叠加任何常驻功能栏，课表占满可用高度。

| 设计特色 | 做法与用户价值 | 验收点（可观察现象） |
| --- | --- | --- |
| 默认不设常驻底栏（dock），设置收进右上角隐藏入口 | 常见的课表类应用把设置、统计、管理等功能做成课表下方的常驻底栏（dock），占掉一整条课表高度，也在视觉上与课表内容争夺注意力。本应用主界面的默认形态**不设常驻底部导航栏**：课表区域从顶栏下沿延伸到屏幕底部（只避让系统手势条／导航条）；全部设置与管理入口收进右上角一个入口，点开后是锚定在该按钮旁的弹层，按功能、数据、偏好、关于分组列出，选中进入对应页面。用户价值：课表可视面积最大，主界面只呈现课表本身。 | 首次进入（未改动任何设置）时，主界面课表下方不存在常驻功能栏；右上角入口点开后可看到全部分组入口，**不存在只能从常驻栏进入的功能**——即使某个常驻栏形态被用户主动开启，它也只是重复入口，不得成为唯一入口；从任一入口返回后，当前周次、当前日期与滚动位置保持不变；在常见屏幕比例与手势／三键导航下，课表最后一行不被遮挡。 |
| 课表顶部一键切换课表 | 切换课表在同类产品里通常要先进入设置或课表管理，再点选目标课表，多步跳转。本应用把顶栏的标题区本身做成切换入口：点一次弹出课表列表，选一次即完成切换，全程**不超过两次点击**。双人模式下标题区并列显示双方昵称并高亮当前一侧，点一下即在自己与对方的课表之间切换，切回同样只需一次点击。用户价值：切换课表是最高频操作之一，代价降到最低。 | 从主界面切换到另一份课表不超过两次点击；双人模式下在自己与对方课表之间切换为一次点击；切换后标题区高亮侧、周次与课表内容同时更新，无需进入设置页；关系未建立、对方未授权或已解绑时，切换入口不可用（与 3.2 F1 的验收点一致），不出现可点进去却无内容的入口。 |

### 4.2 分层与模块划分

分为五层。依赖方向单向向下：**上一层可以调用／依赖下一层，下一层不得反向依赖上一层**。

```
presentation（页面与小组件展示模型）
        ↓ 调用
application（用例：录入课表、切换周次、测算双人状态、同步编排）
        ↓ 调用
domain（纯 Dart：课程/节次模板/学期/可见性/状态推算，无平台依赖）
        ↓ 调用
data（本地数据库 + 远端服务端客户端 + 平台能力桥接）
        ↓ 调用
platform（Android 原生：小组件 Provider、通知、闹钟、定位、广播接收器）
```

读法：箭头方向就是**调用方向**（上层调下层）。`platform` 是被调用方，因此在图上排在 `data` 之下、列表末端。`domain` 不接受任何平台符号，`platform` 不包含业务规则，两者的边界就是「消息与数据结构」。

**本文档约束的是依赖方向，不是目录名。** 层与模块是逻辑边界；目录如何组织以实现为准，不因本文档的命名而重排代码。判定是否合规只看三条硬约束，不看文件名。

**三条硬约束（可机器校验）**：

1. **依赖单向**：`data`／`application`／`domain` 不得导入 `presentation` 的任何模块。唯一的例外是调试专用入口（如深链直达某个页面），它必须与业务代码隔离、并在发布构建中可剔除。
2. **`domain` 纯度**：`domain` 只依赖 Dart 核心库与自身数据模型，**不导入任何 Flutter 包**（`flutter/foundation.dart` 也不例外）。这条不成立，`domain` 与 `platform` 的边界就只是纸面约定，`domain` 的单元测试也必须跑在 Flutter 测试环境里。
3. **application 收口**：`presentation` 不得直接构造 `data` 层服务实例，也不得直接发起数据层调用，一律经 `application` 暴露的用例方法。这是「改动数据层不波及界面」与「界面可被独立测试」的共同前提；绕过这一层会同时失去这两项保障。

**强制机制**：上述三条必须落成静态检查（`analysis_options.yaml` 的导入规则或 `custom_lint`），在 CI 中作为构建期错误拦截。只写在文档里、靠评审记忆维持的边界，会在两个迭代内失效。

**application 层的组织方式**：按用例划分控制器，一个控制器只承担一组相关用例（例如「周次切换」「导入应用」「设置合并」「小组件数据下发」各一个），不得出现单个控制器同时承担多个无关用例的形态。判定标准是：一个控制器的方法集合能否用一句话概括。

模块清单（**逻辑模块，不是目录**：一个模块可横跨多个目录，一个目录也可能承载多个模块的一部分；跨模块只经 domain 的数据结构通信）：

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| `timetable` | 课程、周次、学期、节次模板的领域模型与本地读写；考试、任务、日程项、节假日数据模型 | 网络、UI |
| `schedule_view` | 周视图／今日视图的布局与时间轴渲染 | 数据来源 |
| `import_export` | 教务导入、JSON／ICS 导入导出、表格导入、分享码解析、外部 AI 辅助导入的提示词与格式校验 | 解析器的学校适配内容（社区仓库维护） |
| `exam_stats` | 考试录入与倒计时、课表统计与周报的计算与展示模型 | 网络 |
| `weather` | 位置来源（地点搜索／按需系统定位）→ 预报（Open-Meteo）＋实况／地名反查（高德）→ 缓存与署名渲染 | 任何后台位置采集、位置留存、定时轮询定位、地图控件 |
| `reminder` | 课前提醒、考试提醒与系统闹钟的本地调度 | 同伴状态 |
| `couple` | 绑定关系、可见性、对方课表读取、状态推算与缓存 | 对方数据的写权限 |
| `sync` | 本地变更队列、版本号、冲突合并、拉取游标 | 业务语义判断 |
| `app_platform` | 应用内自更新（检查、下载、哈希校验、唤起安装）、节假日数据在线更新 | 课表业务逻辑 |
| `platform_bridge` | 小组件数据下发与刷新、通知、广播重排、系统定位封装 | 业务规则 |

**适配脚本的分发与加载边界**：教务适配脚本是从远端获取并执行的代码，分发源与执行边界都必须显式约束，不能当普通配置对待。

- **静态清单随包内置，脚本体不内置**：客户端安装包里只带一份内置的适配清单骨架（用于「一个脚本都没有时也不空白」），适配脚本本体一律从远端获取，不打包进 APK——否则适配更新就必须重新发版，社区化维护失去意义。
- **规范源为 GitHub 独立仓库；本项目另做服务器镜像分发**：仓库托管在 GitHub，本项目把同一份内容同步到自有服务器作为镜像，供国内网络访问。客户端按「镜像优先、GitHub 兜底」的顺序取同一份清单，两者都不可达时教务导入入口显示为空列表并给出添加指引。
- 客户端只加载清单中声明、且校验和匹配的脚本；校验和不符、清单缺失或来源不在配置的源列表内时拒绝加载并提示原因，不执行来源不明的脚本。
- 镜像与规范源不一致时以规范源为准；客户端不做脚本签名以外的信任假设，脚本运行在受限环境，只能产出既定格式的课程数据，不得读取本地课表、令牌或其他应用数据。
- 镜像地址是可配置项而非写死的常量：官方镜像失效时用户可改配置，不因单一镜像不可用而失去教务导入能力。

### 4.3 本地数据模型

以「课程实体 / 节次时间表 / 学期周次」三者解耦为原则（同类开源项目的公开数据模型也是这一形状，见附录 C.1）。本地表：

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `semester` | `id`、`name`、`start_date`(YYYY-MM-DD)、`total_weeks`、`week_start_day`(1–7)、`current_week`、`time_slot_set_id`、`updated_at` | 学期配置；`current_week` 由 `start_date` 推算并可手动纠正 |
| `time_slot_set` | `id`、`name`、`semester_id` | 一套节次时间模板 |
| `time_slot` | `id`、`set_id`、`index`(从 1 起)、`start_minute`、`end_minute` | 节次时间；`*_minute` 为「当日 0 点起的分钟数」（0–1439），不用裸时刻字符串 |
| `course` | `id`、`semester_id`、`name`、`teacher`、`location`、`color`、`week_pattern`、`weeks`(JSON 数组)、`day_of_week`(1–7)、`slot_start`、`slot_end`、`rev`、`updated_at`、`deleted` | 课程实体；`week_pattern` ∈ `all`/`odd`/`even`/`custom`；`weeks` 与 `custom` 配合使用；节次范围用 `slot_start`/`slot_end` 表达 |

| `conflict_log` | `id`、`entity`、`entity_id`、`server_value`(JSON)、`local_value`(JSON)、`resolved_by` | 冲突落败方的可追溯副本，供用户手动恢复 |
| `status_cache` | `peer_user_id`、`state`、`no_data_reason`、`course_name`、`ends_at`、`next_course_name`、`next_starts_at`、`fetched_at`、`expires_at`、`etag` | 对方状态缓存（卡片对侧的 `peer` 数据源），只缓存白名单字段；`no_data_reason` 必须一并缓存，否则断网或未刷新时小组件无法显示具体原因；本机自己的侧由本地课表实时推算，不入此表 |

模型约定：

- 课程的唯一身份是本地的课程 `id`；同步到服务端后由服务端返回同一 `id`（客户端生成 UUID 并以 `upsert` 语义提交，见 5.6）。
- 所有时间字段分两类：**日期类**用 `YYYY-MM-DD`（学期开始日期、调课日期）；**时刻类**用「当日 0 点起的分钟数」（节次时间），避免夏令时与跨时区歧义。与外部交互的时间戳用 ISO 8601（见 5.7）。
- 「对方状态」不落永久表，只进 `status_cache`，且只保存 F2 展示所需的字段；本机自己的状态不入缓存，由本地课表直接推算。

### 4.4 本地优先与服务端边界

- **本地优先**：单人功能全部离线可用；任何网络失败都不得阻塞课表读写与展示。
- **上传门控（默认不上传）**：客户端向服务端提交课表数据的条件是「已登录，且（用户开启了云端备份或存在共享关系）」。单人场景未开启备份时，`pending_change` 队列只入不出，不发生任何课表上传；存在共享关系期间，为支撑 F1／F2，课表上传不因关闭云端备份而停止；解除关系且未开启备份时回到不上传状态。关闭云端备份不删除已上传的云端副本，副本删除走注销账号（5.4.3）。
- **服务端边界**：服务端只承担三件事——账号与设备、课表云端副本、共享关系的可见性判定与对方数据下发。它**不是**课表的主存储，客户端始终以本地库为准。
- **写权限边界**：共享关系下**只读**对方的课表数据。客户端不得提供「编辑对方课表」的入口；接口层面也不申请任何写对方数据的路径（见 5.2、5.3）。
- **可见性判定在服务端**：客户端不做「对方能不能看我」的假设，一律以服务端返回的 `peer_visibility` 与接口返回 403 为准，防止本地状态被篡改导致越权读取。
- **同步范围**：只同步课表域数据（课程、节次模板、学期、调休）与可见性设置；不同步天气缓存、不同步本地提醒设置、不同步对方状态缓存。

### 4.5 同步架构

- 本地每次变更写入 `pending_change` 队列；满足 4.4 的上传门控时提交给服务端（`POST /v1/sync/push`），携带 `base_rev` 做乐观并发；冲突按 5.6 处理；门控未满足时队列只入不出，联网也不上传，待门控满足后按 `created_at` 升序补传。
- 拉取用游标（`GET /v1/sync/pull?since=`），客户端维护 `last_cursor`；游标只前进不后退。
- 对方课表按需拉取并缓存，缓存键为 `(peer_user_id, semester_id, cursor)`；本地缓存是展示来源，服务端是权威来源。
- 所有推送到服务端的请求带 `Idempotency-Key`，重试不会造成重复课程。

### 4.6 天气链路（位置来源 + Open-Meteo 预报 + 高德实况）

数据分工：**位置来源为「城市／地点搜索 + 系统定位按需」；预报走 Open-Meteo（按经纬度，无需密钥）；实况、地点搜索与地名反查走高德 Web 服务（需要 Key）。**

位置来源有两条，用户可任选，二者产出的都是同一个「当前坐标」：

1. **地点搜索（主路径）**：输入关键字搜索并选定一个地点，立即作为当前坐标，无需任何定位权限。
2. **系统定位（按需）**：触发点与天气开关绑定——引导界面选择开启天气时自动取一次（或用户在该步改用地点搜索）；之后由用户点击「获取当前位置」时取一次；用户在引导时未开启天气，则**完全不发起定位**，直到其后续自行开启天气那一刻。除上述触发外不发起定位请求。

```
当前坐标（地点搜索 / 系统定位）
   ├→ Open-Meteo /v1/forecast（按经纬度取 temperature_2m、weather_code、
   │   precipitation_probability 等）→ 本地缓存 + 每处展示旁带 open-meteo.com 链接
   └→ 高德 /v3/geocode/regeo（经纬度 → 地名／adcode）
         └→ 高德 /v3/weather/weatherInfo?extensions=base（实况）
```

**地点搜索的粒度要求（与地图搜索结果同级）**：

- 用高德输入提示接口 `GET /v3/assistant/inputtips`（参数 `keywords`、`city`、`types`、`datatype=all`），返回 POI 与地址两类结果，每条结果带 `name`、`district`、`adcode`、`location`（「经度,纬度」）。**该接口的参数名与返回字段本次未逐字取证**（附录 C.4.2、8.2 Q5），动工前须补齐官方文档核对，以核对结果为准。
- **搜索必须做到地点级，不能只到城市级**：结果列表要能出现校区、园区、车站、商圈、小区、村、具体建筑名这类条目，与地图应用搜同名关键字得到的结果类型一致；只返回「某市」一条的实现视为不达标。
- 列表每项展示「名称 + 所属区县 + 地址」以便区分同名地点（如两个校区）；选中后以其 `location` 作为当前坐标。
- 选中项若无 `location`（部分地址类结果），回落 `GET /v3/geocode/geo`（`address` + `city`）取坐标；两者都取不到坐标时不写入，提示重新选择。
- 搜索不限制在输入提示默认返回条数：需要翻页或延长关键字时按接口支持的分页/`keywords` 组合实现，保证常见地点能被搜到。
- 坐标反查：选中已有 `adcode` 时直接用于实况；缺失时用 `/v3/geocode/regeo` 由坐标反查 `adcode` 与结构化地名。
- 输入提示与坐标转换都只在高德 Web 服务侧完成，客户端不引入地图 SDK、不嵌入地图控件；**地图选点本期不做**（见 3.5）。

无定位能力且用户未选点时的兜底：可选 `高德 /v3/ip` 做网络位置估算（必要时用 `/v3/geocode/geo` 把地名转成坐标），结果仅作初始默认值，用户一旦手动选定即不再覆盖。

实现约束：

- **位置是持久状态，不是每次打开都重算**：当前坐标存本地，地点搜索或系统定位取得后写入；后续打开应用直接沿用，直到用户再次选定地点或点击「获取当前位置」。
- **不强制开启 GPS**：应用不得把定位权限或定位服务可用作为天气功能的前置条件；拒绝权限、关闭定位服务、无可用 provider 时，地点搜索通道完整可用，天气照常显示。
- 定位只用系统 API，**不引入任何第三方定位 SDK**，也不依赖 GMS：经 `Context.getSystemService(LOCATION_SERVICE)` 拿 `LocationManager`，按 provider 可用性选择 GPS／网络 provider，取一次坐标即停止。
- 单次取点的写法按 API 等级分档：**API 26–29** 用 `requestLocationUpdates` 拿到首个有效结果后立即 `removeUpdates`；**API 30+** 优先用 `getCurrentLocation`（可直接回调单次结果）。两条路径都必须保证「取到即停」。
- 权限：运行时申请 `ACCESS_COARSE_LOCATION`（或 `ACCESS_FINE_LOCATION`）。**仅授予粗略定位时也必须能出天气**，不得把精确定位作为前置条件。引导界面的自动取点必须先取得权限；用户拒绝时不重复弹窗，该步可改用地点搜索完成设置。
- 可用性判定：先查 `LocationManager.isProviderEnabled(...)` 与 `getProviders(true)`；无可用 provider 或定位服务被关闭时不取点、不报错，沿用已有坐标或显示「暂无天气」，课表全部功能照常可用，不崩溃、不弹错误弹窗。
- **触发时机由天气开关驱动**：引导界面开启天气、用户点击「获取当前位置」，以及用户在设置中首次开启天气，三者之外一律不发起定位。**不做后台持续定位**、不注册定位类前台服务、不在进入课表页或切换日期时发起定位。
- **预报**（Open-Meteo）只依赖经纬度，不需要密钥；**实况与地点搜索／地名反查**（高德）需要 `adcode` 或关键字，由经纬度反查得到。两条链路任一失败时只降级对应部分，不得互相阻塞。
- 地名显示：地名由高德逆地理编码提供；地点搜索时地名取选中结果的 `name` 与 `district`；Key 未配置或请求失败时可退化为只显示天气不显示地名，不阻塞天气主体（地名**不作验收点**），也可回落平台 `Geocoder` best-effort（无 GMS／部分国产 ROM 可能不可用，同样不作验收点）。
- 天气请求的自变量数量与时间跨度要控制（请求变量数 >10 或跨度 >2 周会被折算成多次调用），只取课表页真正展示的字段。
- 缓存与去重：同一坐标同一日期不重复请求；失败时展示「暂无天气」而不是阻塞。
- 署名是硬义务：**Open-Meteo 数据的每一处展示旁都带 `https://open-meteo.com/` 链接**（CC BY 4.0 要求），这条写进第 7 章的治理条目与 3.3 验收点。
- **客户端持有一个第三方密钥（高德 Web 服务 Key）**：只用于实况／地点搜索／地名反查，不用于预报；它由构建期注入、不入库、不写进任何入库文件，按 **7.4 第三方密钥治理**执行；Key 未配置时这三项功能优雅降级（不可用但不报错），预报与课表页主体不受影响。**地点搜索依赖该 Key**：未配置 Key 时地点搜索入口需明确提示"未配置高德 Key，地点搜索不可用"，仅保留系统定位与网络位置估算，不得静默失败。

### 4.7 桌面小组件实现路径

小组件是「Flutter 数据层 + Android 原生 RemoteViews／AppWidgetProvider」的**双份实现**，不是 Flutter 直写：

```
Dart 侧：算出本机与对方两侧的最新状态快照
   → HomeWidget.saveWidgetData('<key>', value)      // 数据下发
   → HomeWidget.updateWidget(name: '<Provider>')     // 通知刷新
   ↓
原生侧：<receiver> 声明 android.appwidget.action.APPWIDGET_UPDATE
        + android:appwidget.provider 元数据指向 AppWidgetProviderInfo XML
   → AppWidgetProvider.onUpdate() 读 SharedPreferences 快照 → RemoteViews 渲染
```

- `home_widget` 只提供**数据下发、读取与刷新通知**的统一接口；Flutter 不能直接渲染原生小组件。
- 小组件分为单人小组件（今日课程／下一节课）与双人课表卡片（同屏显示两人课表与当前状态），各自独立的 Provider，不要一个 Provider 用开关切换（避免刷新逻辑耦合）。
- **刷新分层**：
  1. 小组件刷新本身受系统后台限制，不保证分钟级；两侧状态在小部件上的**分钟级推进由本地推算完成**（本机侧用本地课表、对方侧用 `status_cache` 里已有的下课时间与下一节课时间，`in_class → break → free` 均可在本机按时间自推），不依赖每次刷新都联网。
  2. 联网校时走后台执行插件（如 `flutter_workmanager` 一类后台执行方案）与 `GET /v1/couple/status`，返回 304 时不重绘。
  3. 变更驱动：通过 `POST /v1/couple/events` 注册的变化通知（通道待定，见 8.2 Q7）收到对方课表变更时，立即触发一次数据下发与刷新。未注册任何通道（`channel=none`）时，本条缺失，改为依赖下一次拉取时机（见 5.10）。
- **重排刷新**：必须监听并处理开机、修改系统时间、修改时区三类事件后的小组件重排（`RECEIVE_BOOT_COMPLETED` + `TIME_SET` + `TIMEZONE_CHANGED` 广播，并让小组件 Provider 也响应 `APPWIDGET_UPDATE`），否则设备重启或跨时区后小组件内容与当前周错位。
- **点击直达**：卡片的点击由原生侧用 `PendingIntent` 携带「卡片实例标识」以及可选的「侧别」「课程标识」启动主界面，Flutter 侧在启动流程中读取并消费一次，完成课表切换与课程详情展开后再清空，保证冷启动与热启动只生效一次（对应 3.2 的点击行为表）。双人卡片的行点击通过 `PendingIntentTemplate` + fill-in intent 区分左右两侧，避免每一行单独注册 PendingIntent。
- 小组件主题跟随系统深色模式，样式常量放在应用侧 style，原生与 Dart 侧共用同一套色值定义。
- 小组件的后台刷新周期上限与 Doze 下的行为，官方文档本次取证失败，需在 5.2.0-1 动工前补齐官方依据（见 8.2 Q1、Q10）。

### 4.9 与「超范围」的架构隔离

- 共享课表相关的所有网络能力集中在 `couple` 与 `sync` 两个模块，单人功能不依赖它们，保证「不登录也能用」。
- 云端备份是 `sync` 模块内的可选路径，由用户开关门控且默认关闭；门控未满足时 `sync` 模块不发起任何课表上传（见 4.4）。
- 状态推算在 `domain` 层纯函数实现（输入：课表 + 当前时间 + 时区；输出：F2 四种状态之一），便于单元测试与后续复用；这条同时是 4.2「`domain` 纯度」约束的直接应用——纯函数实现的前提就是 `domain` 不碰平台符号。
- **跨模块不得绕过 `application`**：任一模块要读取另一模块的数据或触发其用例，只能经 `application` 暴露的方法；模块之间不直接持有对方的 `data` 层实现（对应 4.2 第 3 条硬约束）。
- 后续候选功能（6.7）不得在第 4 章的模块边界内预留半成品入口。

## 5. 客户端对服务端的接口口径

本章规定客户端与服务端之间的接口契约：能力、路径、字段、错误码、鉴权、同步时序与冲突处理、时间格式、分页约定。

> **声明（非规范性）**：本章是**能力需求说明**，不是对既有服务端或既有客户端实现的描述。本文不宣称任何一条已经实现；实际实现形态以本地代码为准。

### 5.1 通用约定

- 传输：HTTPS + JSON（`application/json; charset=utf-8`）。
- 路径前缀：`/v1`。版本升级不兼容时提升前缀版本号，不做同一路径下的破坏性变更。
- 请求头（除注册接口外全部必带）：

| 头 | 必填 | 说明 |
| --- | --- | --- |
| `Authorization: Bearer <access_token>` | 是 | 见 5.5 |
| `X-Client-Version` | 是 | 客户端版本号，服务端据此做最低版本拦截 |
| `X-Device-Id` | 是 | 设备标识，用于冲突裁决的确定性排序（见 5.6） |
| `Idempotency-Key` | 写接口必填 | 客户端生成的 UUID，重试复用同一值 |
| `If-None-Match` | 读接口可选 | 携带上次响应的 `ETag`，用于省流 |

- 响应体统一信封：

```json
{ "data": { }, "error": null, "server_time": "2026-10-20T02:41:00Z" }
```

失败时 `data` 为 `null`，`error` 为：

```json
{ "code": "COUPLE_NOT_BOUND", "message": "对方还未与你建立关系", "retryable": false, "details": {} }
```

- 列表响应统一分页字段：`{ "items": [], "next_cursor": "…", "has_more": false }`（见 5.9）。

| --- | --- | --- | --- | --- |
| 1 | 注册／登录 | `POST /v1/auth/register` | A1 账号与设备 | QQ 号 + 自设密码（清涵课表的登录密码，非 QQ 账号密码）：未注册则建号，已注册则校验密码登录；可带邀请码；返回令牌对、头像地址与邀请绑定意向 |
| 2 | 令牌续期 | `POST /v1/auth/refresh` | A1 账号与设备 | 刷新 `access_token` |

| 4 | 生成邀请 | `POST /v1/couple/invite` | F3 共享关系管理 | 生成一次性邀请码与链接，并固化邀请人的绑定意向「是否与被邀请人绑定」（默认否；仅邀请人单方意向，不构成对方同意，见 5.4.4） |

| 7 | 读取／设置可见性 | `GET`/`PUT /v1/couple/visibility` | F3 共享关系管理 | 双方各自的可见性权级 |

| 10 | 双方状态点查 | `GET /v1/couple/status` | F2 双人课表桌面卡片 | 返回双方峰值状态与 ETag |

### 5.3 共享关系与可见性规则（服务端必须实现的三条硬规则）

**规则 1：绑定不产生任何默认可见权限。**

- 新建关系后，双方的 `visibility` 默认都是 `off`。绑定成功时对方的课表不可见。
- 「我能看对方」的充分必要条件是**对方**的 `visibility != off`；不是「我设了就能看」。可见性由被查看方单方面决定并可随时刻修改。
- 字段命名固定为 `my_visibility`（我允许对方看到什么）与 `peer_visibility`（对方允许我看到什么），两者都是 `off` / `status_only` / `full` 三档之一。任何响应中都不用嵌套的 `peer.visibility` 形式。

**规则 1 补充：关系状态的取值与取值时机。**

| 取值 | 含义 | 何时返回 |
| --- | --- | --- |
| `none` | 从未建立过关系 | 仅由 `GET /v1/couple/link` 返回；本机从未发起或接受过绑定，或对方提交的 QQ 号从未被确认 |
| `pending` | 一方已提交对方 QQ 号，等待对方确认 | `POST /v1/couple/bind` 提交后、对方确认前；双方都能看到，不产生任何数据可见性 |
| `active` | 关系有效 | 双方各自明确同意后（接受带绑定意向的邀请，或按 QQ 号发起并经对方确认），直到任一方解绑或任一方注销 |
| `unbound` | 曾经建立、现已解除 | 任一方 `POST /v1/couple/unbind` 之后、或任一方 `POST /v1/auth/delete` 之后，直到本机建立新关系 |

- `state=none` 与 `state=unbound` 的分工：`none` 是「从来没有」，`unbound` 是「有过但已解除」。客户端对两者的处理一致（都显示未绑定、都清空对方数据缓存），区别只用于「上次已解除」这类提示文案。
- `pending` 不是关系：处于 `pending` 时对方课表、状态、可见性一律不可读（按无关系处理），且不占用「一个 `active` 关系」的名额；`pending` 超过 7 天未确认自动失效并回落到 `none`。
- 无关系（`none` / `unbound`）时各接口的返回码分两类，规则固定如下：

| 接口 | 无关系时的返回 |
| --- | --- |
| `GET /v1/couple/link` | 200，`link_id` 为 `null`、`peer` 为 `null`、双方可见性为 `off`、`state` 为 `none` 或 `unbound` |
| `GET /v1/couple/status` | 200，`peer.state=no_data`（`self` 侧仍正常返回；**不报 404**，避免小组件走异常分支，见 5.4.10） |
| `GET /v1/sync/pull?scope=peer` | 404 `COUPLE_NOT_BOUND`（不返回部分数据） |

- 上表的兜底只针对**读取对方数据的接口**：`scope=peer` 的拉取在无关系时返回 404 `COUPLE_NOT_BOUND`；`link` 与 `status` 是仅有的两个在无关系时返回 200 的接口（见上表）。`state=pending` 按无关系处理（等待确认期间不可读对方数据），`link` 接口例外地返回 200 并带 `direction`。
- 另外三类接口在无关系时的行为单独规定，不适用上面的读取口径：
  - `GET`／`PUT /v1/couple/visibility`：无关系（含 `pending`）时返回 404 `COUPLE_NOT_BOUND`（没有关系就没有可读写的可见性权级）。
  - `POST /v1/couple/unbind`：无关系时返回 404 `COUPLE_NOT_BOUND`；`pending` 时可调用，语义为撤回或拒绝，响应 `state=unbound`；已解绑（`unbound`）时幂等返回 200 + `state=unbound`，便于客户端重试。
  - `DELETE /v1/couple/events`：**幂等**，无关系或已解绑时也返回 200（只做「解除该设备的通知注册」，不依赖关系状态），便于解绑流程无条件调用。

**规则 2：可见性三档，语义固定。**

| 值 | 含义 | 允许下发的内容 |
| --- | --- | --- |
| `off` | 不共享 | 除关系状态外不下发任何课表内容；`GET /v1/couple/status` 的 `peer.state` 为 `no_data` |
| `status_only` | 只共享实时状态 | 只允许 `GET /v1/couple/status` 的 `peer` 侧返回白名单字段；`GET /v1/sync/pull?scope=peer` 必须返回 403 `FORBIDDEN_VISIBILITY` |
| `full` | 共享完整课表 | 允许 F2 对方侧完整状态，且允许按 5.4 的字段白名单拉取对方课表 |

**规则 3：解绑与撤回立即生效。**

- 任一方 `POST /v1/couple/unbind` 后，`GET /v1/sync/pull?scope=peer` 立即返回 404 `COUPLE_NOT_BOUND`；`GET /v1/couple/status` 则返回 200 + `peer.state=no_data`（不报 404，见规则 1 补充与 5.4.10）；`GET /v1/couple/link` 返回 200 + `state=unbound`。客户端必须清空 `status_cache` 与对方课表缓存。
- 任一方把 `visibility` 改为 `off` 时，对方的读取立即返回 403 `FORBIDDEN_VISIBILITY`（状态接口则降级为 `no_data`，不报错，避免小组件异常）。
- 解绑后落败方已缓存的对方数据不做远程擦除承诺（技术上不可保证），但客户端在解绑后必须立即删除本地缓存；服务端在解绑后不得再向任一方下发对方数据。

### 5.4 请求／响应字段

#### 5.4.1 `POST /v1/auth/register`

注册与登录共用本接口：QQ 号未注册时创建账号（注册），已注册时校验密码后登录。服务端以 QQ 号作为账号唯一标识，以密码作为登录凭证。**密码是用户在注册时为本应用设置的登录密码，不是 QQ 账号密码**：接口不接受、不校验、不转发 QQ 账号密码，也不存在用 QQ 账号密码登录的路径；QQ 号仅作为账号 ID 与头像来源（见 3.4、5.5）。

请求：

```json
{ "qq": "10001", "password": "…", "invite_code": "8F3K2Q7M", "device_id": "uuid", "platform": "android", "app_version": "0.1.0", "locale": "zh-CN", "timezone": "Asia/Shanghai" }
```

- `qq` 必填，账号 ID；`password` 必填，本应用的登录凭证——由用户在注册时自行设置，与 QQ 账号密码无关，客户端不得在任何文案中暗示需要 QQ 账号密码。
- `invite_code` 可选：不带时为普通注册；带有效邀请码时，服务端在注册成功后按该邀请的绑定意向返回 `invite` 字段（见下）。

语义与错误口径：

- **QQ 号未注册**（新账号）：校验通过后创建账号并直接登录，`is_new_account=true`。密码为空或低于最低要求时返回 400 `BAD_REQUEST`（`details.reason = "invalid_password"`）。
- **QQ 号已注册**（登录）：校验密码；密码正确则发放令牌，`is_new_account=false`；密码错误返回 401 `INVALID_CREDENTIALS`，客户端提示「QQ 号或密码不正确」，**不得区分两种失败原因**（避免账号枚举）。
- 鉴权强度由密码承担：QQ 号本身不是凭证，仅凭 QQ 号无法登录任何账号；该密码是清涵课表的登录密码，不是 QQ 账号密码，应用也不提供「用 QQ 账号登录」的方式。
- 不做邮箱验证、不发验证码：注册不经邮箱或短信确认即生效，没有待验证状态；密码找回不依赖邮箱，忘记密码时联系管理员重置（口径见 5.5）。

响应 `data`：

```json
{
  "user_id": "uuid",
  "qq": "10001",
  "avatar_url": "https://q1.qlogo.cn/g?b=qq&nk=10001&s=100",
  "is_new_account": true,
  "invite": {
    "inviter_user_id": "uuid",
    "inviter_qq": "10002",
    "inviter_avatar_url": "https://q1.qlogo.cn/g?b=qq&nk=10002&s=100",
    "bind_requested": true
  },
  "access_token": "…",
  "refresh_token": "…",
  "expires_in": 7200,
  "refresh_expires_in": 7776000
}
```

约定：

- **QQ 号是账号标识，密码是登录凭证**：服务端以 QQ 号作为账号 ID 并在响应中回显；一个 QQ 号对应一个账号，不做多账号合并。同一 QQ 号在另一台设备以正确密码登录即回到同一账号，`user_id` 与云端课表副本不变。**这里的密码是用户为清涵课表设置的登录密码，与 QQ 账号密码无关**：应用不要求、不接受也不使用 QQ 账号密码，不做 QQ 账号登录，也不引导用户到 QQ 侧授权。
- **不做邮箱验证、不发验证码**：提交即生效，没有待验证状态。
- **密码要求**：长度与复杂度下限由服务端定义并在客户端注册界面明示；密码仅用于本接口的登录校验，服务端只存加盐哈希，任何响应与日志不得回显密码明文。该密码由用户在注册时自行设置，不是 QQ 账号密码；注册界面必须就地说明这一点。
- `avatar_url` 由服务端按 QQ 号生成（`https://q1.qlogo.cn/g?b=qq&nk=<qq>&s=100`），客户端只当作普通图片 URL 使用并自行缓存；该地址不可用时客户端显示默认头像，不阻塞任何流程（该端点为腾讯未公开文档的地址，见附录 C.4.3）。
- `expires_in` 单位秒：`access_token` 2 小时，`refresh_token` 90 天。
- **`invite` 字段只在该次注册使用了有效邀请码时出现**（见 5.4.4）。`bind_requested` 原样反映邀请人生成邀请时的勾选结果：
  - `bind_requested=true`：客户端在注册成功后显示「{inviter_qq} 请求与你建立课表共享关系」的提示，用户选择「绑定」→ 调 `POST /v1/couple/bind`（带 `invite_code`）完成绑定；选择「暂不」则不建立任何关系，邀请视为已消费。
  - `bind_requested=false`：**不显示任何绑定提示**，注册流程直接结束；该邀请只用于注册，不建立也不提示建立关系。
  - 邀请码无效／过期／已使用时，注册仍然成功，但响应不含 `invite` 字段，客户端不应因此报错（见 5.4.4 的失效口径）。
- 已注册用户再用邀请码登录时，同样返回 `invite` 并可据 `bind_requested` 决定是否提示绑定。

#### 5.4.2 `POST /v1/auth/refresh`

请求 `{ "refresh_token": "…" }`；响应同 5.4.1 的令牌字段（不含 `is_new_account`）。`refresh_token` 一次性轮换，旧的立即失效。

#### 5.4.3 `POST /v1/auth/delete`

请求 `{ "confirm": true }`；响应 `{ "deleted_at": "…" }`。语义：注销账号、解除关系、删除云端课表副本；客户端一并清空本地共享课表相关缓存。

#### 5.4.4 `POST /v1/couple/invite`

请求：

```json
{ "bind_on_accept": false }
```

响应：

```json
{
  "invite_code": "8F3K2Q7M",
  "invite_url": "https://<host>/invite/8F3K2Q7M",
  "bind_on_accept": false,
  "expires_at": "2026-10-22T02:41:00Z"
}
```

约定：

- **两件事一次完成**：邀请码同时承担「注册入口」与「是否表达绑定意向」两个语义，但后者由邀请人在生成时显式选择，且只是邀请人单方的意向、不构成对方的同意；关系仍须被邀请人本人同意后才成立（见 1.4）。
- `bind_on_accept` 是生成时固化的意向，**默认 `false`**，必须由客户端弹窗明确询问，用户勾选才传 `true`；未传时服务端按 `false` 处理，不得默认绑定。
- 生成后该意向不可修改：要改变意向需重新生成邀请码（新码使旧码失效）。
- 邀请码 8 位大写字母与数字，一次性使用，24 小时有效；同一用户同时只有一个有效邀请码。
- `invite_url` 是带邀请码的落地链接，客户端分享出去的内容用它；链接被打开时若能唤起应用则携带邀请码进入注册流程。
- 邀请码无效／过期／已使用时：**注册本身不受影响**，`POST /v1/auth/register` 仍返回 200，只是响应不带 `invite` 字段。不为此设独立错误码，避免「邀请码失效导致新用户注册失败」这种放大后果。
- 邀请码只在注册时消费；已注册用户输入邀请码等价于「登录并看到该邀请的绑定意向」。

#### 5.4.5 `POST /v1/couple/bind`

有两种调用方式，共用同一接口：

**方式一：接受邀请（注册时或注册后）**

请求 `{ "invite_code": "8F3K2Q7M" }`。仅当该邀请的 `bind_on_accept=true` 且邀请人未与被邀请人存在其他 `active` 关系时成功；否则返回 400 `BAD_REQUEST`（`details.reason = "invite_without_bind"`）。

**方式二：按 QQ 号发起绑定（需对方确认）**

请求 `{ "peer_qq": "10002" }`。提交后关系为 `pending`，对方确认后转 `active`（见 5.3 规则 1 补充）。

响应（两种方式一致）：

```json
{
  "link_id": "uuid",
  "state": "active",
  "peer": { "user_id": "uuid", "qq": "10002", "avatar_url": "https://q1.qlogo.cn/g?b=qq&nk=10002&s=100" },
  "my_visibility": "off",
  "peer_visibility": "off",
  "requested_at": "2026-10-20T02:00:00Z",
  "bound_at": "2026-10-20T02:41:00Z",
  "unbound_at": null
}
```

约定：

- **两种方式都需双方同意，区别只在同意的收集时机**：接受邀请时，邀请人生成邀请时勾选 `bind_on_accept` 是其本人对本次绑定的同意，被邀请人点「绑定」是另一方本人的同意，两方各自表达后即 `active`；按 QQ 号发起时，发起方的提交只是意向、不构成对方的同意，必须等对方确认后才 `active`。任何一方的意向都不代替另一方的同意（见 1.4、3.4 邀请规则 4）。
- 同意只对当次绑定有效：`pending` 7 天未确认失效后重新发起、解绑后重新绑定，都需要双方各自重新表达同意；邀请码一次性使用，不能复用为他人的同意。
- 一个用户同时只能有一个 `active` 关系；任一已有 `active` 关系时返回 409 `COUPLE_ALREADY_BOUND`。
- 绑定（`active`）成功后双方的 `my_visibility` 与 `peer_visibility` 都为 `off`（规则 1）。`peer` 对象只含身份信息（`user_id`、`qq`、`avatar_url`），可见性一律用同级的 `peer_visibility` 表达。
- `pending` 请求 7 天未确认自动失效，失效后可重新发起。

#### 5.4.6 `POST /v1/couple/unbind`

请求 `{ "link_id": "uuid" }`；响应 `{ "state": "unbound", "link_id": "uuid", "unbound_at": "…" }`。单方即可调用，无对方同意要求。解绑后 `GET /v1/couple/link` 持续返回 `state=unbound`（见 5.3 规则 1 补充）。

#### 5.4.7 `GET`／`PUT /v1/couple/visibility`

`GET` 响应：

```json
{ "link_id": "uuid", "state": "active", "my_visibility": "status_only", "peer_visibility": "full", "updated_at": "…" }
```

`PUT` 请求 `{ "my_visibility": "status_only" }`，取值 ∈ `off` / `status_only` / `full`；响应同 `GET`。语义：只改「我允许对方看到什么」，不影响对方对我的可见性。

#### 5.4.8 `POST /v1/sync/push`

请求：

```json
{
  "semester": { "id": "uuid", "name": "2026 秋", "start_date": "2026-09-01", "total_weeks": 20, "week_start_day": 1, "rev": 3 },
  "time_slot_sets": [
    { "id": "uuid", "name": "夏季作息", "rev": 1,
      "slots": [ { "index": 1, "start_minute": 480, "end_minute": 530 } ] }
  ],
  "courses": [
    { "id": "uuid", "semester_id": "uuid", "name": "高等数学", "teacher": "…", "location": "教三 201",
      "color": "#3B82F6", "week_pattern": "custom", "weeks": [1,2,3,5,7], "day_of_week": 1,
      "slot_start": 1, "slot_end": 2, "base_rev": 4, "updated_at": "2026-10-20T02:30:00Z", "deleted": false }
  ],
  "overrides": [
    { "id": "uuid", "course_id": "uuid", "date": "2026-10-06", "type": "cancelled", "base_rev": 1 }
  ]
}
```

响应（**HTTP 状态恒为 200**；`applied` 与 `conflicts` 同时存在于同一响应，见 5.6 冲突处理）：

```json
{
  "applied": [ { "entity": "course", "id": "uuid", "rev": 5 } ],
  "conflicts": [
    {
      "entity": "course",
      "id": "uuid",
      "server_value": { "name": "高等数学", "location": "教三 201" },
      "server_rev": 6,
      "your_value": { "name": "高数（A）", "location": "教三 201" },
      "merged_value": { "name": "高等数学", "location": "教三 201" },
      "losers": ["name"]
    }
  ],
  "cursor": "opaque-cursor",
  "server_time": "2026-10-20T02:41:00Z"
}
```

字段约定：

- `week_pattern` ∈ `all` / `odd` / `even` / `custom`；为 `custom` 时以 `weeks` 数组为准。
- `slot_start` / `slot_end` 指节次序号（从 1 起），不是时刻。
- `start_minute` / `end_minute` 为当日 0 点起的分钟数（0–1439）。
- `base_rev` 是客户端最后一次见到的该实体版本号；服务端版本号从 1 起单调递增。
- `deleted` 为软删除标记，客户端不得物理删除后静默重传。
- `conflicts[]` 的四层语义：`server_value` 是该实体裁决前的服务端版本（三方合并的共同祖先之后的远端值）；`your_value` 是本次提交中**被裁决掉**的本地值；`merged_value` 是服务端最终落库的服务端实体完整状态，也是服务端返回的 `server_rev` 对应的内容；`losers` 列出被裁决掉的字段名。
- 客户端处理 `conflicts[]`：用 `merged_value` 更新本地实体（连同 `server_rev`），把 `your_value` + `losers` 写入 `conflict_log`，并在界面上提示「有字段冲突，可查看／恢复」。不得用 `your_value` 覆盖本地实体，也不得丢弃 `your_value`。
- 同步冲突**不使用 409**：只要 `base_rev` 能对上某一历史版本，服务端必定能按 5.6 的裁决规则给出确定结果，因此永远返回 200 + `conflicts[]`。409 只用于关系状态类冲突（`COUPLE_ALREADY_BOUND`）。

#### 5.4.10 `GET /v1/couple/status`（F2 双人课表桌面卡片的唯一服务端数据来源）

查询参数：`at`（可选，ISO 8601；不传则取服务端当前时间）。

`at` 的允许窗口与判定规则（用于消除客户端时钟偏差，不用于查询历史或未来状态）：

- 判定基准是服务端的当前时间 `T`。允许区间为 **[T−5 分钟, T+5 分钟]**。
- `at < T−5min` 或 `at > T+5min` → 返回 400 `BAD_REQUEST`，`details.reason = "at_out_of_window"`，`details.allowed_window_seconds = 300`。
- 客户端只能传「本机时间经 `server_time` 校正后的当前时刻」；不得用 `at` 遍历历史或以未来时间探测对方后续课程。
- 请求不带 `at` 时按 `T` 计算，与传 `at = T` 等价；窗口判定针对客户端显式传入 `at` 的情况。

响应 `data`（成功且有数据时带 `ETag`）——**结构为 `self`（本机用户）与 `peer`（对方）两侧，各自独立携带一套状态字段**，对应 F2 卡片的同屏双列：

```json
{
  "self": {
    "state": "in_class",
    "no_data_reason": null,
    "course_name": "大学物理",
    "location": "教二 105",
    "started_at": "2026-10-20T02:00:00Z",
    "ends_at": "2026-10-20T02:50:00Z",
    "next_course_name": "英语",
    "next_starts_at": "2026-10-20T03:00:00Z"
  },
  "peer": {
    "state": "no_data",
    "no_data_reason": "peer_visibility_off",
    "course_name": null,
    "location": null,
    "started_at": null,
    "ends_at": null,
    "next_course_name": null,
    "next_starts_at": null
  },
  "my_visibility": "full",
  "peer_visibility": "off",
  "as_of": "2026-10-20T02:41:00Z",
  "stale_after": 300
}
```

字段语义（`self.*` 与 `peer.*` 内的字段含义一致，按侧解释）：

- 每侧的 `state` ∈ `in_class` / `break` / `free` / `no_data`（与 3.2 的四态一一对应，不允许其他取值）。
- 每侧的 `no_data_reason` 仅在 `state=no_data` 时有值，其余状态下为 `null`。取值与判定优先级固定如下（高优先级命中即不再看后面的条件）：

| 优先级 | `no_data_reason` | 触发条件（以 `peer` 侧为例） | 客户端展示 |
| --- | --- | --- | --- |
| 1 | `not_linked` | 双方从未建立关系（`link.state=none`） | 「尚未绑定」+ 绑定入口 |
| 2 | `pending` | 已发起绑定、等待确认（`link.state=pending`） | 「等待对方确认」+ 撤回入口 |
| 3 | `unbound` | 关系已解除（`link.state=unbound`） | 「关系已解除」+ 重新绑定入口 |
| 4 | `peer_visibility_off` | 关系有效但对方 `visibility=off` | 「对方未共享课表」，不提供直接改对方的入口 |
| 5 | `peer_no_schedule` | 关系有效、可见性允许，但对方无已上传的课表 | 「对方还没有课表」 |

- `self` 侧的 `no_data_reason` 取值只用 `self_no_schedule`（本机无课表）与 `not_linked`／`pending`／`unbound` 中与自身状态一致的那一种；本机侧不出现 `peer_visibility_off` 与 `peer_no_schedule`（这两个原因描述的是对方视角）。
- `self` 侧由本机已上传的课表推算，**只要本机有课表就永远有值**（不受任何可见性控制——可见性只控制对方能看什么，不控制自己看自己）；本机当天无课时为 `free`。
- `peer` 侧任何一种 `no_data` 场景下都返回 200，`peer.state` 置 `no_data` 并给出 `no_data_reason`，**接口本身从不返回 404**（无关系时也不报 `COUPLE_NOT_BOUND`，与 5.3 规则 1 补充一致）。
- `no_data_reason` 是展示用的**唯一依据**：客户端不得自行推断原因（例如把「对方无课表」显示成「未共享」），也不得把五种原因合并成一句「未连接」。`no_data` 时一律不携带任何课程字段，原因本身不泄露课程内容。
- 每侧的 `location` 只在该侧用户对查看方的可见性为 `full` 时返回（`self.location` 由本机 `my_visibility` 决定是否下发给对方——对称接口下服务端返回的是「本机侧在对方端会看到的字段」；本机本地渲染自己的地点不受此限制）；否则为 `null`。
- 每侧的 `next_course_name` / `next_starts_at` 在该侧 `state` 为 `free` 或 `no_data` 时为 `null`。
- `my_visibility` 是本机用户对对方设置的可见性，`peer_visibility` 是对方对本机设置的可见性；用于展示「你也未共享」这类对称提示，与 5.4.6 同名同义。
- `stale_after` 建议客户端多久后重新校时（秒）；客户端在本机可自推状态（`self` 侧完全本地推算、`peer` 侧用缓存的对方课表推算），此值只影响校时频率，不决定状态展示。

#### 5.4.11 `POST /v1/couple/events`

用途：注册「变化通知」的送达方式（对应 B1）。通道本身**不是**本接口的契约内容，客户端上报的只是一个通道标识与投递凭据，服务端按标识选择投递实现。

请求：

```json
{ "channel": "<channel_id>", "token": "<delivery-token>", "subscribe": ["peer_schedule_changed", "link_state_changed"] }
```

响应 `{ "channel": "<channel_id>", "subscribed": ["peer_schedule_changed", "link_state_changed"], "expires_at": null }`。

| 字段 | 说明 |
| --- | --- |
| `channel` | 通道标识，**开放字符串**，不是枚举。取值由服务端与客户端约定，至少包括：`vendor`（厂商推送通道）、`self_hosted`（自建长连接）、`none`（不注册推送，客户端只靠拉取）。服务端必须接受未知标识并返回 200，只把该设备标记为「无可用通道」，不得返回错误——避免新增通道时出现客户端与服务端版本耦合 |
| `token` | 该通道对应的投递凭据；`channel=none` 时为 `null` |
| `subscribe` | 订阅的事件类型；服务端对未知事件名忽略并在响应中回显实际生效的列表 |
| `expires_at` | 凭据失效时间；无失效概念时为 `null` |

`subscribe` 可订阅的事件类型及其语义（取值固定为这两个，新增事件名按 5.8 的「错误码只能新增」原则另行追加）：

| 事件名 | 触发时机 | 客户端应做什么 |
| --- | --- | --- |
| `peer_schedule_changed` | 对方的课表发生任何变更（课程增删改、节次模板或学期配置变更、调休项变更）且该变更已落库 | 触发一次 `GET /v1/sync/pull?scope=peer` 拉取对方最新课表；拿到后在本机重算 F2 对方侧状态并刷新小组件 |
| `link_state_changed` | 关系状态或可见性发生变化：绑定成功、对方解绑、对方注销、任一方 `visibility` 档位改变 | 触发一次 `GET /v1/couple/link` 更新关系状态与双方可见性；必要时清空对方数据缓存（解绑时），并按 5.4.10 的 `no_data_reason` 更新为对应的具体原因展示 |

- 两个事件都只表示「有变化，去取一次」，不承载变更内容；服务端可以在一次通知里同时下发两个事件名，客户端按「拉取一次 + 查一次关系」合并处理，不重复请求。
- 事件名是契约的一部分：客户端只订阅这两个，收到未知事件名时忽略；服务端对未知订阅名忽略并在响应回显实际生效列表（见上表 `subscribe` 行）。

- 候选通道与取舍（具体选型见 8.2 Q7）：

| 候选通道 | 覆盖面 | 代价 |
| --- | --- | --- |
| 厂商推送通道（各 Android 厂商各自的推送服务） | 国内设备覆盖面最好 | 需要逐厂商申请与配置，接入数量随厂商增加 |
| 自建长连接 | 不依赖第三方，自控 | 需要常驻连接，受省电策略影响，耗电与保活是持续成本 |
| 不注册推送（`none`），仅靠拉取 | 无需任何通道依赖 | 变化延迟取决于拉取时机（见 5.10） |

- 明确不采用**依赖 Google 服务的推送通道**作为唯一手段：本应用面向国内高校用户的 Android 设备，该类服务在很多设备上不可用，会把「对方课表变更后尽快看到」变成不可用功能。
- 推送只做「提醒去拉取」，不承载课表内容；客户端收到事件后走 `GET /v1/sync/pull?scope=peer` 或 `GET /v1/couple/status` 取数据。
- 客户端不得假设推送必达：所有展示必须能在只有拉取（或只有本地推算）的情况下自洽。`channel=none` 是合法状态，不是降级异常。
- 注销/换绑：`DELETE /v1/couple/events` 请求 `{ "channel": "<channel_id>", "token": "<delivery-token>" }` 解除注册（设备卸载、注销账号、解绑时调用）。

#### 5.4.12 `GET /v1/couple/link`

有有效关系时（HTTP 200）：

```json
{
  "link_id": "uuid", "state": "active",
  "peer": { "user_id": "uuid", "qq": "10002", "avatar_url": "https://q1.qlogo.cn/g?b=qq&nk=10002&s=100" },
  "my_visibility": "status_only", "peer_visibility": "full",
  "requested_at": "2026-10-20T02:00:00Z",
  "bound_at": "2026-10-20T02:41:00Z", "unbound_at": null
}
```

无关系或已解绑时（同为 HTTP 200，不用 404）：

```json
{
  "link_id": null, "state": "none",
  "peer": null,
  "my_visibility": "off", "peer_visibility": "off",
  "requested_at": null, "bound_at": null, "unbound_at": null
}
```

- `state` ∈ `pending` / `active` / `unbound` / `none`，取值与时机见 5.3 规则 1 补充。`pending` 时返回发起方向、对方 QQ 号与头像，但不返回任何课表内容；无关系时本接口返回 200 + `state=none` 或 `unbound`，不报 `COUPLE_NOT_BOUND`：它是仅有的两个在无关系时返回 200 的接口之一（另一个是 `GET /v1/couple/status`，见 5.3 规则 1 补充的对照表），且不返回任何对方课表内容。
- 请求参数：`link_id`（可选）。不传时返回当前账号的关系状态；传已失效的 `link_id` 时按当前状态返回，不返回 404。
- **待确认请求的读取**：本机作为被请求方时，`pending` 关系里 `peer` 是发起方，`direction` 字段标识方向（`incoming` / `outgoing`），用于渲染「某某请求与你建立关系」与「等待对方确认」两种界面。

### 5.5 鉴权方式

- **账号模型：QQ 号是账号 ID，密码是登录凭证**。注册时「QQ 号 + 自设密码」即建号，登录以同一对凭据校验；服务端只存加盐密码哈希。不做手机号登录、不做第三方 OAuth 登录。**该密码是用户为清涵课表自行设置的登录密码，不是 QQ 账号密码**：应用不要求、不接受也不使用 QQ 账号密码，不提供 QQ 账号登录或 QQ 授权登录；QQ 号只承担账号标识与头像来源两个用途。
- **不做邮箱验证**：不发送验证码、不要求邮箱，注册提交即生效；服务端不得基于「未验证」拒绝请求。由此，清涵课表的登录密码是登录的唯一凭证：必须正确存储（加盐哈希）、必须校验（错误密码不得进入账号），并按 5.4.1 的口径以 `401 INVALID_CREDENTIALS` 统一拒绝，不做账号枚举提示。
- **忘记密码由管理员重置**：没有邮箱、手机号或密保问题可用于自助找回，因此密码找回走人工通道——用户联系管理员（即本项目的服务端维护者），由管理员核实身份后为该账号设置一个新密码，再以线下方式告知用户。该通道是运维操作，不是客户端能力：5.2 的 12 条接口不因此增减，客户端不新增「找回密码」页面或接口调用，登录界面只给出一句「忘记密码请联系管理员重置」的说明。管理员重置时的约束：先核实请求者确为该账号的使用者（至少能提供该 QQ 号并能通过已绑定设备的既有登录状态佐证），核实不通过不得重置；只设置新密码、不回显也不告知原密码；重置后该账号的全部已发放令牌作废，需重新登录。管理员不得为其他目的查看或使用用户密码（服务端本就只存加盐哈希，无明文可看）。
- 登录按需发生：仅在用户开启云端备份或使用共享课表功能时引导注册／登录，应用不在首次启动时强制登录；未登录时客户端不携带令牌发起任何请求。
- `access_token` 走 `Authorization: Bearer`，有效期 2 小时；过期返回 401 `UNAUTHENTICATED`，客户端用 `refresh_token` 换新令牌后重放原请求（重放必须复用同一 `Idempotency-Key`）。
- `refresh_token` 有效期 90 天、一次性轮换；`POST /v1/auth/refresh` 失败返回 401 `TOKEN_EXPIRED`，客户端必须回到注册流程并清除本地令牌。
- 共享关系的授权**不体现在令牌里**：令牌只代表「我是谁」，不代表「我能看对方」。每次访问对方数据的权限都由服务端按当时的 `visibility` 与关系状态即时判定（规则 1、规则 3），客户端不得缓存授权结论超过一次请求。
- 所有接口都必须同时校验令牌、关系状态、可见性；任一不满足时按 5.8 返回明确错误码，不得返回降级后的空数据（`status` 接口的 `no_data` 除外，见 5.4.10）。

### 5.6 同步时序与冲突处理

**推时序（客户端改动 → 服务端）**

```
1. 本地写库：更新实体 + 写 pending_change（记录 base_rev）
2. 前台时立即尝试 push；离线则排队，联网后按 created_at 升序重放
3. push 正常 → applied 中的实体用返回的 rev 覆盖本地 rev，删除对应 pending_change
4. push 返回 conflicts → 进入冲突流程（见下），不得盲目覆盖
5. 网络 / 5xx / 429 → 保留 pending_change，指数退避重试，复用同一 Idempotency-Key
```

**拉时序（对方改动 → 客户端）**

```
1. 收到 peer_schedule_changed 推送，或进入对方课表页，或轮询到期
2. 用本地 last_cursor 调 GET /v1/sync/pull?scope=peer
3. 逐条按 rev 覆盖本地缓存；cursor 前进；has_more 为 true 则继续
4. 写入 status_cache：用最新对方课表在本机重算 F2 对方侧状态（不等待下一次 status 请求）
5. 触发一次小组件数据下发 + updateWidget（本机侧快照不变，只更新对侧）
```

**冲突处理（本应用自行定义，服务端与客户端共同实现）**

同类产品普遍不公开冲突规则（见第 2 章），因此这里给出完整规则：

1. **并发模型**：以实体（课程／节次模板／学期／调休项）为粒度做乐观并发，每个实体带单调递增 `rev`。
2. **接受条件**：`base_rev == 服务端当前 rev` → 直接接受，返回新 `rev = base_rev + 1`，写入 `applied[]`。
3. **`base_rev` 不匹配时做字段级合并**：把 `base_rev` 对应的服务端历史版本作为共同祖先，做三方合并。服务端只要能在历史版本中找到 `base_rev`，就一定能算出结果，因此**返回 200 + `conflicts[]`，不返回 409**。
   - 只有本地改过的字段 → 取本地值。
   - 只有远端改过的字段 → 取远端值。
   - 两边都改过同一个字段且值不同 → **规则化裁决**（不允许服务端静默丢弃任一方）：
     - `deleted=true` 优先于任何字段修改（删除胜过编辑）。
     - 双方都是普通字段修改时，比较 `updated_at`，较新者胜。
     - `updated_at` 完全相同时，比较 `X-Device-Id` 的字典序，较大者胜（保证双方算出同一结果，不会来回覆盖）。
   - 裁决结果写入 `merged_value`，被裁决掉的字段名写入 `losers`，被裁决掉的本地值原样写入 `your_value`（响应形态见 5.4.8）。
4. **冲突落败方的处理**：被裁决掉的本地值不得静默丢弃——服务端在 `conflicts[].your_value` 中原样返回，客户端写入 `conflict_log`，并在对方课表／本机课表上给出一条「有字段冲突，可查看」的提示；用户可选择保留服务端版本或恢复本地版本。客户端按 `merged_value` + `server_rev` 更新本地实体。
5. **服务端无法给出结果的唯一情形**：请求里缺少 `base_rev`、`base_rev` 不是整数、或实体 `id`／`semester_id` 引用不存在。这些属于请求本身不合法，按 400 `BAD_REQUEST` 处理（`details.reason` 分别为 `missing_base_rev` / `unknown_entity_ref`），不进入冲突流程。
6. **禁止项**：不得使用「最后写入优先且无记录」的静默覆盖；不得返回 200 但丢弃 `base_rev` 不匹配的实体；不得用 409 表达同步冲突。
7. **幂等**：同一 `Idempotency-Key` 重复提交返回首次结果，不产生第二次 `rev` 自增。

**对方的写入不存在**：客户端不提供写对方数据的通道（与第 2 章所述「写入对方日历」的模型相反）；接口层面也没有任何「写 peer 数据」的路径，因此不存在跨账号写冲突，只存在同一账号多设备冲突。

### 5.7 时间格式

| 场景 | 格式 | 示例 | 说明 |
| --- | --- | --- | --- |
| 交互时间戳（`updated_at`、`bound_at`、`as_of`、`ends_at`…） | ISO 8601 / UTC，带 `Z` | `2026-10-20T02:41:00Z` | 客户端展示时按本机时区转换 |
| 日历日期（`start_date`、调课 `date`） | `YYYY-MM-DD` | `2026-09-01` | 不带时区，语义是「当地日历上的这一天」 |
| 节次时刻（`start_minute` / `end_minute`） | 当日 0 点起的整数分钟 | `480` | 避免夏令时与跨时区歧义 |
| 有效期（`expires_at`） | ISO 8601 / UTC | `2026-10-21T02:41:00Z` | 与交互时间戳一致 |

约定：所有接口的时间字段一律按上表，不使用本地化字符串、不使用秒级以外精度（毫秒截断为 0）、不使用 Unix 时间戳。服务端每次响应带 `server_time`，客户端据此校正本地时钟偏差（偏差超过 2 分钟时以服务端时间为准推算 F2 各侧状态）。

### 5.8 错误码

| HTTP | `code` | 触发条件 | 客户端行为 |
| --- | --- | --- | --- |
| 400 | `BAD_REQUEST` | 参数缺失／格式错／`at` 超出允许窗口（±5 分钟，见 5.4.10）／`base_rev` 缺失或非法／实体引用不存在／邀请未勾选绑定却试图据此绑定（`invite_without_bind`） | 修参数，不重试 |
| 401 | `UNAUTHENTICATED` | 未带令牌或令牌无效 | 走 refresh 后重放（复用幂等键） |
| 401 | `INVALID_CREDENTIALS` | 登录时 QQ 号与该 QQ 号对应的清涵课表登录密码不匹配（注册外的登录校验失败；不是 QQ 账号密码） | 提示「QQ 号或密码不正确」，不区分两种原因，不重试 |
| 401 | `TOKEN_EXPIRED` | `refresh_token` 过期或已轮换 | 回注册流程，清本地令牌 |
| 403 | `FORBIDDEN_VISIBILITY` | 对方 `visibility` 不足以完成该请求 | 展示「对方未共享课表」，清对方课表缓存，不重试 |
| 404 | `USER_NOT_FOUND` | 绑定时提交的 QQ 号未注册 | 提示核对 QQ 号，不重试 |
| 404 | `COUPLE_NOT_BOUND` | 无关系／已解绑（`GET /v1/couple/link` 与 `GET /v1/couple/status` 除外，两者返回 200） | 清共享课表缓存，入口切回未绑定态 |
| 409 | `COUPLE_ALREADY_BOUND` | 己方已有 `active` 关系 | 提示先解绑 |
| 429 | `RATE_LIMITED` | 超出限流 | 按 `Retry-After` 退避，不并发重试 |
| 5xx | `SERVER_ERROR` | 服务端异常 | 保留本地队列，指数退避重试；本地功能不受影响 |

约定：错误响应不计入 `data`；`retryable` 明确标记是否可重试；错误码一经公开不得改语义，只能新增。**409 只用于关系状态冲突**（`COUPLE_ALREADY_BOUND`）；同步冲突一律走 200 + `conflicts[]`（见 5.4.8、5.6），因此不设 `REV_CONFLICT` 这类冲突错误码。

### 5.9 分页约定

- 采用**游标分页**，不用页码：请求 `limit`（默认 200，最大 500），响应 `next_cursor` + `has_more`。
- 游标是**不透明字符串**，客户端不得解析或构造；游标与 `scope` 绑定，跨 `scope` 使用返回 400 `BAD_REQUEST`。
- `GET /v1/sync/pull` 的游标只前进：即使中间有实体被删除，游标也单调递增；客户端发现本地数据与游标不连续时，以 `has_more` 为 true 连续拉取直到收敛。
- 顺序保证：同一 `scope` 内按 `rev` 升序返回，客户端按序应用，天然处理「先改后删」。

### 5.10 客户端侧配额与降级要求（接口使用约定）

- `GET /v1/couple/status` 的轮询间隔不短于 60 秒，且优先用 `ETag` 命中 304；小组件的分钟级推进由本地推算完成，不靠缩短轮询周期。
- 对方课表 `sync/pull` 只在收到变更事件、进入对方课表页、或距上次拉取超过 30 分钟时触发，不做定时常驻轮询。
- 所有请求失败都必须落到「本地已有数据继续可用」这一结果上；接口可用性不作为单人功能的依赖。

里程碑按功能划分，不绑定日期。版本号沿用应用自身的语义化版本序列：6.1–6.5 是 `5.2.0` 的预发布里程碑（`5.2.0-1` 至 `5.2.0-5`），6.6 是 `5.2.0` 正式发布。每个里程碑的「验收点」都是可观察现象；前一个里程碑的验收点全部通过才进入下一个。

### 6.1 5.2.0-1 单人课表可用

- **交付物**：本地课表数据模型与数据库；周视图／今日视图；课程与节次模板维护；周次四态；学期配置；调休与临时调整。
- **验收点**：离线（飞行模式）下能完成「新建学期 → 建两套节次模板 → 录入 5 门课（含单双周与并行课）→ 切换周次 → 标记一天停课」全过程，且重启应用后数据与操作后一致。

### 6.2 5.2.0-2 导入导出与备份

- **交付物**：JSON 导入导出；ICS 导出（可带提醒参数）；分享码生成与解析；外部 AI 辅助导入（可复制的导入提示词 + JSON 格式说明 + 导入校验）；教务导入的插件式入口、社区适配脚本仓库骨架（适配内容由社区贡献）、适配仓库的镜像分发与清单校验；文件备份与恢复。
- **验收点（数据通道）**：导出的 JSON 重新导入后课表等价；同一条分享码在本机另一台设备上导入得到同一课表；导出的 ICS 能被系统日历应用打开；备份文件在使用后可完整恢复。
- **验收点（外部 AI 辅助导入）**：应用内可一键复制导入提示词与 JSON 格式说明，内容自包含（含字段含义、周次表达、节次序号与时间的对应关系），复制后可粘贴到 DeepSeek、豆包等外部工具使用；把外部工具按提示词生成的 JSON 导入本应用能得到可用的课表；JSON 不符合格式或字段越界时给出具体错误位置与原因，且不破坏已有课表；全过程中应用不发起任何 AI 或 OCR 请求、不内置任何 AI 账号或额度（可在网络请求记录中核对）。
- **验收点（适配仓库骨架与镜像分发）**：适配脚本的规范源为 GitHub 仓库，本项目把同一份清单与脚本同步到自有服务器镜像；客户端从配置的镜像地址获取适配清单与脚本，镜像不可达时回退到 GitHub，两者都不可达时教务导入入口显示为空列表并给出「如何添加适配」的指引；**适配脚本本体不在 APK 内**（安装包解包后检索不到脚本文件，仅有内置清单骨架）；适配清单带版本号与校验和，脚本内容与校验和不符时拒绝加载并提示，不执行来源不明的脚本；镜像与规范源内容不一致时以规范源为准；镜像新增或更新脚本后，已安装的客户端不重新发版即可获取并使用新脚本。
- **验收点（教务导入入口）**：适配脚本按约定的输入／输出格式放入社区仓库后，客户端不重新发版即可加载并使用它；未安装任何适配脚本时，教务导入入口显示为空列表并给出「如何添加适配」的指引，而不是报错或崩溃；导入失败时给出失败原因且不破坏已有课表。
- **验收点（适配仓库骨架内容）**：规范源仓库含适配脚本的格式说明、示例适配脚本与运行说明；示例适配脚本能在客户端里走通一次导入。

### 6.3 5.2.0-3 天气与定位

- **验收点（定位触发时机）**：全新安装走引导界面——选择**不开启**天气时，全程不出现定位权限申请、不发起任何定位；选择**开启**天气时，当场申请定位权限并只发起一次定位（或在同一步改用地点搜索）；之后进入课表页、切换日期、切换周次均不发起定位；点击「获取当前位置」或在设置中首次开启天气才发起下一次定位（可在系统权限/耗电面板与网络日志核对，全程无后台持续定位、无定位类前台服务）；仅授予粗略定位（Android 12+「大致位置」）时仍能出天气；拒绝定位权限后不重复弹窗，课表功能完全可用且不出现空白报错；系统定位服务关闭或无可用 provider 时不取点、不崩溃，沿用已有坐标或显示「暂无天气」；**每一处 Open-Meteo 天气展示旁都有指向 open-meteo.com 的链接**；仓库中检索不到任何真实 key（高德 Key 只从构建期变量注入）；Key 未配置时实况／地点搜索／地名降级不报错；随 APK 分发的依赖中不含任何第三方定位 SDK、地图 SDK 或闭源二进制组件。

### 6.5 5.2.0-5 账号与同步

- **交付物**：QQ 号注册与令牌刷新（按需触发，见 5.5）；QQ 头像获取与默认占位；云端备份开关（默认关闭）与上传门控；本地变更队列与幂等重试（`Idempotency-Key` 语义）；`sync/push`、`sync/pull`；游标管理；5.6 的冲突合并与 `conflict_log` 提示界面。
- **验收点（账号与令牌）**：填写 QQ 号并设置清涵课表的登录密码（不是 QQ 账号密码，界面就地注明）即完成注册，不需要邮箱与验证码；密码错误时登录失败且提示统一（不泄露账号是否存在）；登录界面写明忘记密码需联系管理员重置，且界面上没有任何自助找回入口；同一 QQ 号与密码在另一台设备登录后得到同一账号、同一份云端数据；账号头像显示为该 QQ 号的 QQ 头像，头像地址不可用时显示默认占位图且不报错；令牌过期后自动续期并重放原请求，用户无感知。
- **验收点（上传门控）**：全新安装后未开启云端备份、未使用共享课表时，客户端不产生注册、不向服务端发送任何课表数据（通过网络日志或服务端记录核对）；开启备份后完成注册并上传；关闭备份后上传停止、本地课表与全部单人功能不受影响；重新开启后按本地队列补传。
- **验收点（多设备同步）**：同一账号两台设备 A／B，A 改课表后 B 在联网下拉后看到变更。
- **验收点（冲突合并）**：两端同时改同一门课的不同字段后合并结果字段级正确且不丢改动；两端同时改同一字段后套用 5.6 的裁决规则，结果与规则一致，且落败值可在冲突提示中查看并恢复。
- **验收点（幂等与补传）**：断网改动后联网自动补传；同一 `Idempotency-Key` 重复提交（含主动重放一次相同请求）后服务端只产生一次 `rev` 自增、客户端不出现重复课程。
- **验收点（关系状态口径）**：`GET /v1/couple/link` 在 `none` / `unbound` 两种状态下均返回 200 且不返回对方数据；`GET /v1/couple/status` 在无关系时返回 200 + `no_data`；`scope=peer` 的拉取在无关系时返回 404 `COUPLE_NOT_BOUND`。
- **验收点（游标管理）**：首次拉取不传 `since` 能拿到全量并按 `has_more` 连续翻页直到 `has_more=false`；之后每次拉取复用上次返回的 `next_cursor` 只拿到增量；本地游标与服务端不连续（如清库重装）时能重新收敛到与服务端一致；跨 `scope` 复用同一游标返回 400 `BAD_REQUEST` 且不写入任何数据。

### 6.6 5.2.0 共享课表功能与开源发布

- **交付物**：邀请码与邀请链接生成（含绑定意向弹窗）与邀请注册；双方同意的绑定流程（邀请路径与 QQ 号路径，见 5.4.5）与单方解绑；可见性三档与权限判定；F1 互相查看对方课表（含界面切换入口）；F2 双人课表桌面卡片；变化通知注册（B1，通道待定）；解绑后的缓存清理；后台授权引导；第 8 章风险清单逐条给出结论或明确的「不做」判定。
- **验收点（邀请注册与绑定意向）**：生成邀请时弹出确认弹窗，默认未勾选；不勾选生成的邀请可用于注册，被邀请人注册成功后**看不到任何绑定提示**；勾选生成的邀请，被邀请人注册成功后看到邀请人的绑定提示，可绑定或暂不；两种情况下凭邀请码注册本身都成功；邀请码过期或已使用时注册仍成功、只是不出绑定提示；被邀请人未点「绑定」前不产生任何关系与数据可见性，且邀请人的勾选不被当作被邀请人的同意（见 1.4）。
- **验收点（绑定与解绑）**：按 QQ 号发起绑定后关系为 `pending`，此时双方都看不到对方任何课表数据；对方确认后变为 `active`；`pending` 期间任一方可撤回，7 天未确认自动失效，失效后重新发起需双方重新同意；解绑后重新绑定同样需双方重新同意；提交未注册的 QQ 号返回「用户不存在」提示。
- **验收点（F1 互相查看对方课表）**：绑定后默认双方都看不到对方课表；只有被查看方打开 `status_only` 或 `full` 后对方才能看到对应范围（`status_only` 时拉取对方课表返回 403 `FORBIDDEN_VISIBILITY`）；任一方改为 `off` 后对方立即无法读取；单方解绑后对方立刻退回未绑定态且本地缓存的对方数据被清除。
- **验收点（F2 双人课表桌面卡片）**：小组件同屏显示两人的当日课程；每侧在 `in_class` 时显示课程名与下课时间、跨到下一节后按本地推算切换、`break` 时显示下一节课、当天无课时显示空闲；**任一侧无数据时必须显示具体原因而不是「未连接」**——分别构造尚未绑定、等待确认、已解除、对方关闭共享、对方无课表五种情形，小组件与课表页对侧显示的文案各不相同且与原因表一致；任一原因下都不泄露未授权方的课程内容；同一账号两台设备显示一致；对方 `visibility=off` 时对侧推算停止并显示「对方未共享课表」，本侧不受影响；**点击行为与 3.2 的点击行为表逐项一致**——点左半停在自己的课表、点右半停在对方课表（各一次点击，无需再切）、点课程块先切到该侧课表再展开该课程详情；卡片绑定的课表失效时普通打开、课程已不存在时不弹空详情、双人模式未开启时不静默切换；应用未运行／后台／前台三种状态下点击结果一致，且只跳转一次。
- **验收点（B1 变化通知）**：以 `channel=none` 注册也能成功，且此时对方课表变更仍能在 5.10 规定的拉取时机被看到；以任一已支持的 `channel` 注册后，对方改课表能触发一次自动拉取并刷新对方课表页与小组件对侧显示；服务端对未知 `channel` 返回 200 并把该设备标记为无可用通道，客户端不报错；`DELETE /v1/couple/events` 调用后不再收到事件。
- **验收点（关系状态查询 F4）**：`GET /v1/couple/link` 在 `none`、`active`、`unbound` 三种状态下都能正确展示关系状态、双方可见性与绑定时间；解绑后再次查询返回 `unbound` 而不是 `none`。
- **验收点（系统集成与厂商授权引导）**：设置页存在「后台运行／自启动／通知权限」引导项，点击能跳到对应系统设置页；未授权时相关功能降级且不崩溃。**本条只验收引导项存在与跳转可达，不验收实际常驻效果**——厂商省电策略下的保活效果不作验收项（见 8.1 R5）。
- **验收点（风险清单收口）**：8.1 的 R1–R12 与 8.2 的 Q1–Q11 在发布时逐条处于三种已收口状态之一——「已按应对措施实现（有对应功能或测试证据）」「已判定不做（写进 3.5 或 6.7 并说明理由）」「已补齐依据（给出官方链接或真机验证记录，并把结论回写到对应章节）」。存在任何仍停留在「待决定」且会影响 5.2.0 范围的条目时，本验收点不通过。
- **验收点（发布）**：仓库含许可证、贡献指南、隐私说明与构建说明；按构建说明在干净环境能构建出可安装包；应用内无法进入任何已列入 Out of scope（3.5）的共享课表附加玩法与单人附加工具。
- **验收点（架构约束）**：4.2 的三条硬约束已落成静态检查并在 CI 中作为构建期错误拦截——`data`／`application`／`domain` 不导入 `presentation`（调试入口除外且发布构建中可剔除）；`domain` 不导入任何 Flutter 包；`presentation` 不直接构造数据层服务。人为引入一条违规导入时，CI 必须失败。

- 新增平台权限、新增网络出口、新增第三方依赖必须单独说明理由与隐私影响。

### 7.3 隐私说明

必须在仓库与应用内同时提供，且内容与实现一致：

- **账号只收 QQ 号与密码**：注册只收集 QQ 号与登录密码，用途限定为账号标识、登录校验与头像展示；不收集邮箱、手机号、通讯录，不申请 QQ 开放平台授权、不读取 QQ 好友与空间数据。头像由 QQ 头像地址直接加载，客户端只做普通图片缓存。**收集的密码是用户为清涵课表设置的登录密码，不是 QQ 账号密码**：应用不要求、不接受也不使用 QQ 账号密码，不做 QQ 账号登录，界面不得让用户误以为要填写 QQ 密码。忘记密码时由管理员重置（见 5.5），该通道同样不需要用户提供邮箱或手机号，因此不改变本条的收集范围。
- **QQ 号可被他人知道，但登录需要密码**：QQ 号对外可见（头像、绑定交互都会用到），因此界面需说明「QQ 号是账号 ID，不要把清涵课表的登录密码告诉任何人」；服务端只存加盐密码哈希。
- **不采集行为数据**：不上报任何行为数据，包括位置、行踪与用机情况。F2 的状态完全由课表数据与时间推算。
- **单人使用默认不联网**：未开启云端备份且未使用共享课表功能时，除天气取值、节假日数据更新与应用内自更新检查外不发生任何网络请求；不登录也能使用全部单人功能。后两者的请求只访问更新源／节假日数据源，不上传课表与身份信息，可在网络日志核对。
- **云端备份是用户的选择**：开启后课表数据上传到服务端用于备份与多设备同步，可随时关闭；关闭后停止上传，已上传副本的删除走注销账号（`POST /v1/auth/delete`）。
- **授权即撤即停**：可见性三档由被查看方单独设置，随时可改；解绑后对方立即无法读取（对应 5.3 规则 1、规则 3）。
- **最小化下发**：`GET /v1/couple/status` 只返回 F2 展示所需的字段；地点字段只在 `full` 档下发。
- **数据归属与删除**：注销账号删除云端副本并解除关系（`POST /v1/auth/delete`）；解绑后客户端立即清空对方数据缓存。
- **耗电披露**：应用内说明后台保活与刷新对续航的影响，并说明不授予后台权限会导致小组件与提醒不准。
- **定位用途最小化**：定位只用于取一次经纬度以查天气，触发时机与天气开关绑定——引导界面开启天气、设置中首次开启天气、用户点击「获取当前位置」，三者之外一律不定位；引导未开启天气就不触发任何定位；不做后台持续定位；用户可完全不用定位，改用地点搜索自行选定地点。预报坐标只发给 Open-Meteo；坐标会发给高德用于实况、地点搜索与地名反查，**不向其他任意第三方发送**，不发往自有服务端，不留存位置历史。
- **外部 AI 辅助导入由用户自行决定**：应用不在内部发起任何 AI 或 OCR 请求，只在应用内展示可复制的导入提示词与 JSON 格式说明。用户把课表截图或描述粘贴到 DeepSeek、豆包等外部工具时，数据由用户自己选择的服务商处理，适用该服务商的条款；应用内需明确提示这一点，且不得默认替用户发送任何内容。
- **教务适配脚本的获取**：客户端会访问配置的镜像地址（主要路径）与 GitHub 仓库（兜底）以获取适配清单与脚本；镜像由本项目从规范源同步，内容不一致时以规范源为准；客户端只下载清单中列明且校验和匹配的脚本，不上传任何本地数据，请求不携带令牌与身份标识。
- 不做「不可单方解除」的关系绑定。

### 7.4 密钥管理

- **客户端只持有一个第三方服务密钥：高德 Web 服务 Key**。它只用于天气实况、地点搜索与经纬度反查地名；定位用系统 API、预报取 Open-Meteo 免费档，两者不需要密钥。
- **该 Key 必须构建期注入、绝不入库**：仅通过 `--dart-define=AMAP_KEY=...` 或等价的构建期变量传入，缺省为空；仓库不含任何真实 Key，`.gitignore` 覆盖本地密钥文件，提交前检查不得包含真实 key。
- **风险披露（不回避）**：构建期常量会写入二进制，可被反编译提取；因此它只能当普通配置看待，**不得把任何敏感能力挂在它下面**，也不得把它当作「秘密」。它必须绑定应用 SHA1／包名（Android Key），未绑定的 Web 服务 Key 使提取后果更严重。
- 密钥归属原则：**能放服务端就不放客户端**。属服务端凭据的 Key 只应放在自有服务端，不下发客户端、不写进 App；只有必须随包分发的客户端凭据才走构建期注入。
- Key 未配置时必须**优雅降级**：实况／地点搜索／地名反查不可用且不报错，预报与课表页主体不受影响；地点搜索入口需显示明确提示而不是空白列表。
- 构建脚本不得回显 Key 明文、不得把它写进任何输出文件；CI 只从加密变量读取密钥；PR 中禁止出现真实 key。

### 7.5 数据源合规

- **Open-Meteo**（预报）：免费档明确不允许商用，限流 600 次/分、5,000 次/时、10,000 次/日、300,000 次/月；数据为 CC BY 4.0，要求署名、给出许可链接，且**任何展示 Open-Meteo 数据的位置旁必须给出 `https://open-meteo.com/` 链接**。本应用免费、无广告、不商业化，与该免费档一致；一旦涉及商用必须改用付费档。
- **高德开放平台**（实况、地点搜索、地名反查）：使用 Web 服务 API 与 Web 服务 Key，Key 只用于自己的应用；官方《使用条款》对未购技术服务许可的使用范围有限制（仅限短期、少量测试），分发上架前需核对自己的使用情形。本应用**免费、无广告**且不向公众收费，不引入商业化导流（见 1.4、3.5），与该定位一致。**高德定位 SDK（闭源二进制）不采用**（见 7.1）。
- **定位**：使用 Android 系统定位 API 不涉及第三方数据源许可；客户端只取经纬度用于当次天气查询，不留存位置、不做后台定位。
- 不引入第三类数据源；新增数据源前先核对其许可与免费无广告条款，并回写本节。
- 由于所用免费数据源不允许商用，应用内不得出现广告、付费入口或商业化导流。
