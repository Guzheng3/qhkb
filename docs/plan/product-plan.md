## 1. 产品定位与目标用户

### 1.1 一句话定位

本应用是一款**非商用、开源、Android 端的课程表应用**：单人可以完整地管理自己的课表，情侣在双方分别授权后可以把课表共享给对方，并把**「对方现在在上什么课」**常驻在桌面小组件上。

### 1.2 产品主张

- **单人是完整可用的基础功能**，不是情侣功能的前置任务。不建立情侣关系、不联网、不使用服务端，单人课表功能全部可用。
- **情侣共享是主线特色，且只做两件事**：互相查看对方课表；把「对方现在在上什么课」放进桌面小组件。
- **差异化落点是实时状态，而不是「能看到对方课表」。** 课表共享在同类产品里已有先例，本应用的差异点是把对方**此刻**的课程状态做成默认常驻、不需要对方动手更新的桌面信息。

### 1.3 目标用户

| 用户 | 特征 | 主要诉求 |
| --- | --- | --- |
| 主要用户：高校在读学生（单人） | 每学期课表固定、按周次循环、有节次时间模板；手机以 Android 为主 | 低成本录完课表、看得清今天和本周、课前有提醒、桌面能看到下一节课 |
| 主要用户：情侣中的一方或双方 | 两人在同一所学校或不同学校；想减少「你几点下课」「你现在有课吗」这类反复确认 | 不用问就知道对方当前状态；同时不被持续监视 |
| 次要用户：乐于贡献的开源使用者 | 习惯读文档、提 issue、写教务适配 | 能自己加学校适配、能自建服务端、能自行构建签名 |

### 1.4 目标用户不包含

- 学校／机构等组织客户（本应用不做集中管理、不做后台报表）。
- 以商业变现为目的的分发方（非商用定位，见第 7 章）。
- iOS 用户（本版本 Android only）。

### 1.5 非目标与红线

- 不做社交关系链、不做公开课表广场、不做陌生人匹配。
- 不做定位轨迹、不做「对方在哪里」、不做用机记录（状态由课表数据推算，不采集行为数据）。
- 不把情侣关系做成不可解除的强绑定：任何一方都能单方解绑，且解绑后对方的跨账号读取立即失效。
- 不做后端实现规划：本文档只规定客户端对服务端的能力要求（第 5 章）。

## 2. 竞品与设计启示

本章是结论摘要，全部事实、来源 URL、访问日期与「未证实」标注见附录 [A 课表竞品](research-appendix.md#a-课表类-app-竞品)、[B 情侣协同](research-appendix.md#b-情侣双人协同类产品)、[C 开源与技术方案](research-appendix.md#c-开源实现与技术方案)。

### 2.1 结论一：课表共享不是差异化，「对方此刻状态」才是

同类课表产品已经覆盖了共享与多人比对：

- **星链课表**官网明示「情侣课表」（首页可看两人同一天的课）与「多人比对，找共同空闲」，并有分享码导入生态——开源项目**拾光课程表**内置了「星链课表分享码导入」通道，说明课表数据已经存在跨应用的分享码互通。
- **星课程表**官网卖点含「好友同步」「好友课表绑定」。
- 其余产品（WakeUp课程表、极简课程表）停留在一次性分享码／课表分享导入。

因此：

> **本应用不把「能看到对方课表」当作卖点。** 该类产品普遍已经提供这一能力。本应用的差异化必须落在**「对方此刻在上什么课」的实时状态呈现**，并且以**桌面小组件**作为默认入口。

### 2.2 结论二：情侣类产品的通用模型是「共享容器」，没有可抄的冲突规则

对 TimeTree、Between、小恩爱、心动日常、Cupla、Lookus 六个样本的调研结论：

- 主流同步模型是**共享容器**（两人加入同一个日历／空间，写入对全体成员可见），只有 Cupla 的官方文案出现「把计划直接加进伴侣的日历」这种写入对方数据的表述；Lookus 走的是「自动上报状态流 + 双向授权」，同样不是写入对方数据。
- **六个样本全部没有公开冲突处理规则**（并发编辑怎么合并、是否最后写入优先，均无官方说明）。
- **六个样本没有一个把「对方此刻的状态」放进小组件**：TimeTree 的小组件展示日程事件并允许设置「只显示我自己的事件」（取向相反），Between 的小组件展示纪念日天数，心动日常／小恩爱／Lookus 的小组件有无都未证实。

因此：

> **可见性规则与并发编辑冲突策略必须由本应用自行定义**，并落成第 5 章的具体接口规则，不能留给实现阶段临时决定。本应用选择**互相同意的对称可见性**与**字段级合并 + 版本号乐观并发**（见 5.3、5.6），而不是「共享容器内全员可见」。

### 2.3 结论三：状态类功能必须自带隐私边界与耗电披露

- 心动日常以「自动上报状态」（定位、用机记录、离开到达自动提示）回答「对方此刻在做什么」，并在官方文案里主动披露后台 GPS 持续运行会显著影响续航。
- Lookus 把「双向授权」「有关怀，更有边界感」写成官方宣传语，并用「节律级状态」（日常作息、是否已休息）而非精确定位来描述共享内容（附录 B.6，来源 S14）。

因此：

> 本应用的「对方此刻状态」必须**由课表数据推算**，不采集任何行为数据；双方各自独立授权、可随时关闭、可按粒度降级；状态缓存要说明电量代价并走低功耗路径（见 4.7、5.6）。

### 2.4 结论四：小组件是标配，「岛」级集成只能作为待验证目标

- 有来源的课表产品普遍提供桌面小组件，且多为多尺寸多样式（WakeUp课程表 Android 4 种、拾光课程表含 2×1 微型到双日型、星链课表一周／今日／近日／概览）。
- 拾光课程表把适配脚本拆成独立社区仓库、支持 JSON/ICS 导入导出与 WebDAV 备份、提供多尺寸小组件，是**Apache-2.0 许可**的公开参考。
- 「岛」类集成的可核实系统能力只有 Android 自身的 promoted ongoing notifications（API 36 起，`POST_PROMOTED_NOTIFICATIONS` 在 API 36.1）；**小米 HyperOS 焦点通知／超级岛没有官方开发者文档**（详见 4.8 与第 8 章）。

### 2.5 结论五：录入通道要多条并行，教务适配要社区化

- 同类产品的教务覆盖数字对外口径互不一致（WakeUp 四处数字从 1200+ 到 3000+ 并存、超级课程表以版本说明给出 3618 所），说明这是持续维护成本项而非一次性功能。
- 拾光课程表用「社区适配脚本独立仓库 + 专用测试器仓库」摊薄适配成本，并支持 JSON 课程文件与 ICS 导出（ICS 可带提醒时间参数）。
- 星链课表用 AI 截图／网页识别把「教务适配」从硬依赖降级为兜底。

### 2.6 对功能范围与架构的直接约束

| 启示 | 落到本规划书的条目 |
| --- | --- |
| 共享本身不构成差异 | 3.2 情侣功能只保留「互相查看课表」与「对方此刻状态小组件」两条 |
| 缺少可抄的冲突规则 | 5.3 可见性规则、5.6 同步时序与冲突处理必须写死 |
| 状态功能必须有授权与撤回 | 3.2、5.4 的权限与解绑规则 |
| 小组件必须原生实现 | 4.7 的小组件实现路径与刷新对齐 |
| 岛类集成证据不足 | 4.8、8 章写成待验证适配目标与风险 |
| 录入通道要多条并行 | 3.1 的教务导入／JSON／ICS／分享码通道与社区适配仓库 |

## 3. 功能范围

范围分三块：单人基础功能、情侣特色功能、天气功能。每条给出**用户价值**与**验收点**（验收点写成可观察现象，不依赖实现细节）。范围之外的内容集中在 3.4。

### 3.1 单人基础功能（In scope）

| 功能 | 用户价值 | 验收点（可观察现象） |
| --- | --- | --- |
| 课表录入与展示 | 一次录入整学期可用 | 能新建学期并录入多门课程；周视图按当前周正确渲染课程块；左右滑动可切换周次；今日视图只显示当天课程 |
| 课程字段 | 课程信息完整且贴近真实上课场景 | 每门课可设名称、教师、地点、周次、节次范围、颜色；同一时段可存在两门并行课程且都被显示 |
| 节次时间模板 | 不同学校／不同学期节次不同，不必每学期重录 | 可保存多套节次时间模板并在学期间切换；可对单个节次覆盖起止时间（不必所有节次等长） |
| 周次表达 | 单双周、指定周是高校真实排课方式 | 周次支持「全部／单周／双周／指定周」四种表达；修改周次后周视图立即反映 |
| 调休与临时调整 | 法定调休、临时换课不需要改坏原课表 | 可对某个具体日期做调课／停课标记，且该调整只影响该日期，不影响周期模板 |
| 学期配置 | 当前周与开学日期对齐 | 可设开学日期、学期总周数、每周起始日、当前周；跨周后当前周自动推进 |
| 课表导入／导出 | 降低录入门槛，避免数据被锁死 | 支持教务导入、JSON 导入导出、ICS 导出、分享码导入四条通道；导出的 JSON 可被本应用重新导入并还原为等价课表；ICS 导出文件可被系统日历识别 |
| 课前提醒 | 不漏课 | 可为某门课开启课前提醒并设置提前量；到点产生系统可见的提醒 |
| 桌面小组件（单人） | 不打开应用就能看到今天／下一节课 | 桌面添加小组件后显示今日课程；重启手机、修改系统时间、修改时区后小组件内容仍然正确 |
| 本地数据与备份 | 换机不丢课表 | 课表可导出为文件备份；导入备份文件后课表与备份前一致 |
| 深色模式与多尺寸小组件 | 桌面与系统外观一致 | 系统切换深色模式后应用与小组件同步变化；小组件提供至少紧凑型与列表型两种尺寸 |

### 3.2 情侣特色功能（In scope，仅以下两条）

| 功能 | 说明 | 用户价值 | 验收点（可观察现象） |
| --- | --- | --- | --- |
| F1 互相查看对方课表 | 双方各自授权后，可查看对方当前学期的课表（周视图／今日视图），只看不改 | 不再需要反复要课表截图；对方课表变化后看到的是最新版本 | 未建立关系时入口不可用；建立关系并双方都授权后，能打开对方课表并看到与对方本机一致的课程；对方修改课表后，本机下拉刷新能看到变更；任一方关闭授权后对方立即无法查看 |
| F2「对方现在在上什么课」桌面小组件 | 桌面小组件显示对方**此刻**的状态：上什么课、几点下课、是否在课间／已放学；数据由服务端按需下发峰值状态 | 不用问也不用打开应用，抬头就知道对方现在忙不忙 | 添加小组件后显示对方当前课程名与下课时间；对方课程结束并进入下一节后，小组件在刷新周期内更新；对方当天没有课时显示空闲状态；未授权或已解绑时小组件显示未连接状态而不是空白或他人数据 |

**F2 的状态口径（必须实现为这四种之一，不允许出现第五种含义）**：

| 状态 | 含义 | 展示要点 |
| --- | --- | --- |
| `in_class` | 对方正在上课 | 课程名、下课时间；可选地点（受 5.3 可见性控制） |
| `break` | 对方在两节课之间 | 下一节课名与上课时间 |
| `free` | 对方今天已无后续课程 | 今日课程已结束 |
| `no_data` | 未建立关系／未授权／对方未上传课表／已解绑 | 显示为未连接，不得显示任何他人课程内容 |

**F2 只读取课表推算的状态**：不读取对方位置轨迹、不读取对方用机行为、不读取对方是否打开了应用。

### 3.3 天气功能（In scope）

| 功能 | 用户价值 | 验收点（可观察现象） |
| --- | --- | --- |
| 课表页天气呈现 | 出门前知道要不要带伞、穿多少 | 定位成功后课表页显示本地天气（温度、天气现象、降水概率）；定位失败或未授权时不显示天气且不阻塞课表使用 |
| 天气随日期变化 | 看课表时能直接看到当天的天气 | 切换到其他日期时，天气跟着该日期的预报变化 |
| 数据来源与署名 | 合规使用开放数据 | 每一处展示 Open-Meteo 数据的位置旁均有指向 open-meteo.com 的链接；无链接的天气展示视为验收不通过 |
| 定位与地理编码 | 用最少的定位调用换到正确的城市 | 定位只用高德定位 SDK，一次定位同时取得经纬度与逆地理编码结果（含 `getAdCode`）；天气取值只用经纬度，adcode 用于城市级展示与核对；不因为天气功能而持续后台定位 |

约定：天气数据取 Open-Meteo，定位与地理编码走高德（详见 4.6）。两者的许可与非商用约束落在第 7 章。

### 3.4 账号与服务端数据能力（In scope）

第 5 章的接口按本节与 3.1、3.2 的功能条目划分，编号如下：`A` 为账号与服务端基础能力，`B` 为服务端数据能力（配额与限流反馈），`F` 为情侣特色功能。

| 编号 | 功能 | 用户价值 | 验收点（可观察现象） |
| --- | --- | --- | --- |
| A1 账号与设备 | 不需要注册账号体系即可建立归属，换设备可继续使用同一份云端数据 | 首次进入情侣功能前自动完成设备注册；应用重启不需要重新输入任何凭据；令牌过期时自动续期且用户无感知；注销后本机令牌与云端副本一并清除 |
| A2 云端课表副本 | 课表有云端副本，多设备之间可对齐（单人离线使用不依赖它） | 同一账号两台设备能通过同步得到一致课表；断网期间的改动在联网后自动补传 |
| A3 服务端配额与限流反馈 | 请求被限流时行为可预期，不会反复打服务端 | 触发限流时客户端按服务端给出的退避时间重试，且界面上单人功能与本地展示均不受影响 |
| B1 变化通知（客户端注册订阅） | 对方课表变更后本机尽快看到最新版本，而不是靠长时间轮询 | 注册订阅成功后对方改课表，本机在收到通知后自动拉取并刷新展示（通道待定，见 8.2 Q9） |
| F1 互相查看对方课表 | 见 3.2 | 见 3.2 |
| F2「对方现在在上什么课」桌面小组件 | 见 3.2 | 见 3.2 |
| F3 情侣关系管理 | 建立与解除关系由用户自己掌控，且随时能调整对方可见范围 | 能生成邀请码并完成绑定；绑定后双方默认互不可见；可见性三档可随时切换且立即生效；任一方可单方解绑 |
| F4 关系状态查询 | 能确认当前是否已绑定、双方各自可见到什么程度 | 关系未建立、已绑定、已解绑三种状态均可查看；显示双方各自的可见性权级与绑定时间 |

### 3.5 Out of scope（本次明确不做）

**情侣玩法中本次不做的部分**（统一进「后续候选」，见 6.7，任何一条都不得写入 v1 范围）：

- 共同空档对比（双人空闲时段比对／找共同空闲）。
- 双人共同事件（共同日程、约会事件、共同待办与指派）。
- 互动提醒（远程叫起床、提醒对方、戳一戳、"想你"类互动）。
- 纪念日与倒数日、恋爱天数（D-day）。
- 共享相册、共享日记、聊天／留言（含冰箱贴类留言）。
- 定位共享、轨迹、到达离开提醒、用机状态上报。

**单人附加工具中本次不做的部分**（统一进「后续候选（单人附加工具）」，见 6.7）：

- 成绩／绩点。
- 考试倒计时。
- 空教室查询。

**其他明确不做**：

- iOS／桌面端／Web 端客户端。
- 公开课表广场、陌生人社交、组织／社团管理后台。
- 付费、订阅、广告、内购（与「非商用」定位冲突）。
- 教务适配的服务端集中托管：适配脚本按社区贡献方式维护，本应用不承诺任何学校的适配覆盖率。
- AI 截图识别导入（同类产品有此能力，本应用本期不做，见 6.7）。
- 自建服务端的部署与运维方案（第 5 章只规定客户端需要服务端提供什么）。

### 3.6 功能与接口的对应关系（自检口径）

口径：**第 5 章的每个接口都必须能追溯到本章的一个功能条目**；反之，本章中标注「无服务端接口」的功能不得在实现时偷偷引入接口。表内为空的一方就是「无」，不需要接口。

| 功能条目 | 依赖的服务端能力 | 接口（见 5.2） |
| --- | --- | --- |
| 3.1 单人课表全部功能 | 无（离线可完整使用） | — |
| 3.1 课表导入／导出、备份 | 无（本地文件与分享码） | — |
| 3.1 课前提醒、系统闹钟 | 无（客户端本地调度） | — |
| 3.3 天气与定位 | 无（客户端直连 Open-Meteo 与高德） | — |
| A1 账号与设备 | 设备注册、令牌续期、注销 | `POST /v1/auth/device`、`POST /v1/auth/refresh`、`POST /v1/auth/delete` |
| A2 云端课表副本 | 课表上传与增量拉取、双方各自拉取自己的副本 | `POST /v1/sync/push`、`GET /v1/sync/pull`（`scope=self`） |
| A3 服务端配额与限流反馈 | 限流应答与退避时间 | 不单独占用接口：`429 RATE_LIMITED` 由各接口共用（见 5.8、5.10） |
| B1 变化通知 | 注册推送通道 | `POST /v1/couple/events` |
| F1 互相查看对方课表 | 拉取对方课表副本 | `GET /v1/sync/pull`（`scope=peer`） |
| F2 对方此刻状态小组件 | 峰值状态点查 + 校时 | `GET /v1/couple/status` |
| F3 情侣关系管理 | 邀请码、绑定、解绑、可见性读写 | `POST /v1/couple/invite`、`POST /v1/couple/bind`、`POST /v1/couple/unbind`、`GET`／`PUT /v1/couple/visibility` |
| F4 关系状态查询 | 关系状态与可见性读取 | `GET /v1/couple/link` |

反向核对：5.2 的 12 条接口在上表全部出现，且每条都挂在 A1–A3、B1、F1–F4 之一；上表中标注「—」的功能条目在 5.2 中没有任何对应接口。

### 4.1 技术栈与版本基线

### 4.2 分层与模块划分

分为五层。依赖方向单向向下：**上一层可以调用／依赖下一层，下一层不得反向依赖上一层**。

```
presentation（页面与小组件展示模型）
        ↓ 调用
application（用例：录入课表、切换周次、测算对方状态、同步编排）
        ↓ 调用
domain（纯 Dart：课程/节次模板/学期/可见性/状态推算，无平台依赖）
        ↓ 调用
data（本地数据库 + 远端服务端客户端 + 平台能力桥接）
        ↓ 调用
platform（Android 原生：小组件 Provider、通知、闹钟、定位、广播接收器）
```

读法：箭头方向就是**调用方向**（上层调下层）。`platform` 是被调用方，因此在图上排在 `data` 之下、列表末端。`domain` 不接受任何平台符号，`platform` 不包含业务规则，两者的边界就是「消息与数据结构」。

模块清单（每个模块只负责一件事，跨模块只经 domain 的数据结构通信）：

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| `timetable` | 课程、周次、学期、节次模板的领域模型与本地读写 | 网络、UI |
| `schedule_view` | 周视图／今日视图的布局与时间轴渲染 | 数据来源 |
| `import_export` | 教务导入、JSON／ICS 导入导出、分享码解析 | 解析器的学校适配内容（社区仓库维护） |
| `weather` | 定位→地理编码→天气取值→缓存与署名渲染 | 任何后台位置采集 |
| `reminder` | 课前提醒与系统闹钟的本地调度 | 同伴状态 |
| `couple` | 绑定关系、可见性、对方课表读取、状态推算与缓存 | 对方数据的写权限 |
| `sync` | 本地变更队列、版本号、冲突合并、拉取游标 | 业务语义判断 |
| `platform_bridge` | 小组件数据下发与刷新、通知、广播重排、定位 SDK 封装 | 业务规则 |

### 4.3 本地数据模型

以「课程实体 / 节次时间表 / 学期周次」三者解耦为原则（同类开源项目的公开数据模型也是这一形状，见附录 C.1）。本地表：

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `semester` | `id`、`name`、`start_date`(YYYY-MM-DD)、`total_weeks`、`week_start_day`(1–7)、`current_week`、`time_slot_set_id`、`updated_at` | 学期配置；`current_week` 由 `start_date` 推算并可手动纠正 |
| `time_slot_set` | `id`、`name`、`semester_id` | 一套节次时间模板 |
| `time_slot` | `id`、`set_id`、`index`(从 1 起)、`start_minute`、`end_minute` | 节次时间；`*_minute` 为「当日 0 点起的分钟数」（0–1439），不用裸时刻字符串 |
| `course` | `id`、`semester_id`、`name`、`teacher`、`location`、`color`、`week_pattern`、`weeks`(JSON 数组)、`day_of_week`(1–7)、`slot_start`、`slot_end`、`rev`、`updated_at`、`deleted` | 课程实体；`week_pattern` ∈ `all`/`odd`/`even`/`custom`；`weeks` 与 `custom` 配合使用；节次范围用 `slot_start`/`slot_end` 表达 |
| `course_override` | `id`、`course_id`、`date`(YYYY-MM-DD)、`type`(`moved`/`cancelled`)、`new_slot_start`、`new_slot_end`、`rev`、`updated_at` | 调休与临时调整，只作用于具体日期 |
| `couple_link` | `link_id`、`state`(`active`/`unbound`/`none`)、`peer_user_id`、`peer_display_name`、`my_visibility`、`peer_visibility`、`bound_at`、`unbound_at` | 情侣关系与双方各自的可见性权级，本地缓存；`state` 的取值与时机见 5.3 规则 1 补充，两端字段名与 5.4 完全同名 |
| `pending_change` | `id`、`entity`、`entity_id`、`base_rev`、`patch`(JSON)、`created_at`、`attempts` | 本地变更队列（离线可用与冲突重放） |
| `conflict_log` | `id`、`entity`、`entity_id`、`server_value`(JSON)、`local_value`(JSON)、`resolved_by` | 冲突落败方的可追溯副本，供用户手动恢复 |
| `status_cache` | `peer_user_id`、`state`、`course_name`、`ends_at`、`next_course_name`、`next_starts_at`、`fetched_at`、`expires_at`、`etag` | 对方状态缓存，只缓存白名单字段 |

模型约定：

- 课程的唯一身份是本地的课程 `id`；同步到服务端后由服务端返回同一 `id`（客户端生成 UUID 并以 `upsert` 语义提交，见 5.6）。
- 所有时间字段分两类：**日期类**用 `YYYY-MM-DD`（学期开始日期、调课日期）；**时刻类**用「当日 0 点起的分钟数」（节次时间），避免夏令时与跨时区歧义。与外部交互的时间戳用 ISO 8601（见 5.7）。
- 「对方状态」不落永久表，只进 `status_cache`，且只保存 F2 展示所需的字段。

### 4.4 本地优先与服务端边界

- **本地优先**：单人功能全部离线可用；任何网络失败都不得阻塞课表读写与展示。
- **服务端边界**：服务端只承担三件事——账号与设备、课表云端副本、情侣关系的可见性判定与对方数据下发。它**不是**课表的主存储，客户端始终以本地库为准。
- **写权限边界**：情侣关系下**只读**对方的课表数据。客户端不得提供「编辑对方课表」的入口；接口层面也不申请任何写对方数据的路径（见 5.2、5.3）。
- **可见性判定在服务端**：客户端不做「对方能不能看我」的假设，一律以服务端返回的 `peer_visibility` 与接口返回 403 为准，防止本地状态被篡改导致越权读取。
- **同步范围**：只同步课表域数据（课程、节次模板、学期、调休）与可见性设置；不同步天气缓存、不同步本地提醒设置、不同步对方状态缓存。

### 4.5 同步架构

- 本地每次变更写入 `pending_change` 队列并提交给服务端（`POST /v1/sync/push`），携带 `base_rev` 做乐观并发；冲突按 5.6 处理。
- 拉取用游标（`GET /v1/sync/pull?since=`），客户端维护 `last_cursor`；游标只前进不后退。
- 对方课表按需拉取并缓存，缓存键为 `(peer_user_id, semester_id, cursor)`；本地缓存是展示来源，服务端是权威来源。
- 所有推送到服务端的请求带 `Idempotency-Key`，重试不会造成重复课程。

### 4.6 天气链路（Open-Meteo + 高德）

数据分工：**定位与地理编码走高德，天气取值走 Open-Meteo**。

```
高德定位 SDK（一次性定位，前台触发）
   → 经纬度 + 逆地理编码 getAdCode / getCity
   → Open-Meteo /v1/forecast（按经纬度取 temperature_2m、weather_code、
      precipitation_probability 等）
   → 本地缓存（按 (经纬度取整, 日期) 缓存）
   → 课表页渲染 + 每处展示旁带 open-meteo.com 链接
```

实现约束：

- 定位只在用户前台触发（打开课表页或手动点刷新），**不做后台持续定位**；定位模式优先低功耗档，间隔取下限以上的保守值。
- 定位 SDK 调用任何接口前必须先完成隐私合规前置调用（`updatePrivacyShow`、`updatePrivacyAgree`），否则不出结果。
- 天气取值只依赖经纬度；`adcode` 用于城市级展示与地理编码结果核对，不作为天气请求的必需品。
- 天气请求的自变量数量与时间跨度要控制（请求变量数 >10 或跨度 >2 周会被折算成多次调用），只取课表页真正展示的字段。
- 缓存与去重：同一经纬度同一日期不重复请求；失败时展示「暂无天气」而不是阻塞。
- 署名是硬义务：**每一处展示 Open-Meteo 数据的位置旁都带 `https://open-meteo.com/` 链接**（CC BY 4.0 要求），这条写进第 7 章的治理条目与 3.3 验收点。

### 4.7 桌面小组件实现路径

小组件是「Flutter 数据层 + Android 原生 RemoteViews／AppWidgetProvider」的**双份实现**，不是 Flutter 直写：

```
Dart 侧：算出今日课程 / 对方状态 最新快照
   → HomeWidget.saveWidgetData('<key>', value)      // 数据下发
   → HomeWidget.updateWidget(name: '<Provider>')     // 通知刷新
   ↓
原生侧：<receiver> 声明 android.appwidget.action.APPWIDGET_UPDATE
        + android:appwidget.provider 元数据指向 AppWidgetProviderInfo XML
   → AppWidgetProvider.onUpdate() 读 SharedPreferences 快照 → RemoteViews 渲染
```

- `home_widget` 只提供**数据下发、读取与刷新通知**的统一接口；Flutter 不能直接渲染原生小组件。
- 小组件分为单人小组件（今日课程／下一节课）与情侣小组件（对方此刻状态），各自独立的 Provider，不要一个 Provider 用开关切换（避免刷新逻辑耦合）。
- **刷新分层**：
  1. 小组件刷新本身受系统后台限制，不保证分钟级；对方状态在小部件上的**分钟级推进由本地推算完成**（缓存里已有下课时间与下一节课时间，`in_class → break → free` 可在本机按时间自推），不依赖每次刷新都联网。
  2. 联网校时走后台执行插件（如 `flutter_workmanager` 一类后台执行方案）与 `GET /v1/couple/status`，返回 304 时不重绘。
  3. 变更驱动：通过 `POST /v1/couple/events` 注册的变化通知（通道待定，见 8.2 Q9）收到对方课表变更时，立即触发一次数据下发与刷新。未注册任何通道（`channel=none`）时，本条缺失，改为依赖下一次拉取时机（见 5.10）。
- **重排刷新**：必须监听并处理开机、修改系统时间、修改时区三类事件后的小组件重排（`RECEIVE_BOOT_COMPLETED` + `TIME_SET` + `TIMEZONE_CHANGED` 广播，并让小组件 Provider 也响应 `APPWIDGET_UPDATE`），否则设备重启或跨时区后小组件内容与当前周错位。
- 小组件主题跟随系统深色模式，样式常量放在应用侧 style，原生与 Dart 侧共用同一套色值定义。
- 小组件的后台刷新周期上限与 Doze 下的行为，官方文档本次取证失败，需在 v0.1 动工前补齐官方依据（见 8.2 Q3、Q12）。

### 4.8 通知与厂商系统集成路径

| 能力 | 实现路径 | 证据等级 |
| --- | --- | --- |

### 4.9 与「超范围」的架构隔离

- 情侣相关的所有网络能力集中在 `couple` 与 `sync` 两个模块，单人功能不依赖它们，保证「不登录也能用」。
- 状态推算在 `domain` 层纯函数实现（输入：课表 + 当前时间 + 时区；输出：F2 四种状态之一），便于单元测试与后续复用。
- 后续候选功能（6.7）不得在第 4 章的模块边界内预留半成品入口。

## 5. 客户端对服务端的接口口径

本章只写**客户端需要服务端提供什么**：能力、路径、字段、错误码、鉴权、同步时序与冲突处理、时间格式、分页约定。不涉及服务端实现、部署、存储选型。

### 5.1 通用约定

- 传输：HTTPS + JSON（`application/json; charset=utf-8`）。
- 路径前缀：`/v1`。版本升级不兼容时提升前缀版本号，不做同一路径下的破坏性变更。
- 请求头（除注册接口外全部必带）：

| 头 | 必填 | 说明 |
| --- | --- | --- |
| `Authorization: Bearer <access_token>` | 是 | 见 5.5 |
| `X-Client-Version` | 是 | 客户端版本号，服务端据此做最低版本拦截 |
| `X-Device-Id` | 是 | 设备标识，用于冲突裁决的确定性排序（见 5.6） |
| `Idempotency-Key` | 写接口必填 | 客户端生成的 UUID，重试复用同一值 |
| `If-None-Match` | 读接口可选 | 携带上次响应的 `ETag`，用于省流 |

- 响应体统一信封：

```json
{ "data": { }, "error": null, "server_time": "2026-10-20T02:41:00Z" }
```

失败时 `data` 为 `null`，`error` 为：

```json
{ "code": "COUPLE_NOT_BOUND", "message": "对方还未与你建立关系", "retryable": false, "details": {} }
```

- 列表响应统一分页字段：`{ "items": [], "next_cursor": "…", "has_more": false }`（见 5.9）。

### 5.2 能力清单与接口路径

| # | 能力 | 方法与路径 | 对应功能（见 3.4） | 说明 |
| --- | --- | --- | --- | --- |
| 1 | 设备注册／登录 | `POST /v1/auth/device` | A1 账号与设备 | 匿名设备注册，返回令牌对 |
| 2 | 令牌续期 | `POST /v1/auth/refresh` | A1 账号与设备 | 刷新 `access_token` |
| 3 | 注销账号 | `POST /v1/auth/delete` | A1 账号与设备 | 注销并解除关系、删除云端副本 |
| 4 | 生成邀请码 | `POST /v1/couple/invite` | F3 情侣关系管理 | 生成一次性邀请码 |
| 5 | 建立关系 | `POST /v1/couple/bind` | F3 情侣关系管理 | 用邀请码双向绑定 |
| 6 | 解除关系 | `POST /v1/couple/unbind` | F3 情侣关系管理 | 单方即可解绑 |
| 7 | 读取／设置可见性 | `GET`/`PUT /v1/couple/visibility` | F3 情侣关系管理 | 双方各自的可见性权级 |
| 8 | 课表快照上传 | `POST /v1/sync/push` | A2 云端课表副本 | 批量 upsert，带版本号 |
| 9 | 增量拉取 | `GET /v1/sync/pull` | A2 云端课表副本（`scope=self`）、F1 互相查看对方课表（`scope=peer`） | 按游标拉取，支持拉自己或拉对方 |
| 10 | 对方状态点查 | `GET /v1/couple/status` | F2 对方此刻状态小组件 | 返回峰值状态与 ETag |
| 11 | 变更事件注册 | `POST /v1/couple/events` | B1 变化通知 | 注册变化通知通道，对方课表变更时通知（通道待定，见 8.2 Q9） |
| 12 | 关系状态查询 | `GET /v1/couple/link` | F4 关系状态查询 | 关系状态、双方可见性、绑定时间 |

限流不占用单独接口：`429 RATE_LIMITED` 由上述所有接口共用，对应 A3（见 5.8、5.10）。

### 5.3 情侣关系与可见性规则（服务端必须实现的三条硬规则）

**规则 1：绑定不产生任何默认可见权限。**

- 新建关系后，双方的 `visibility` 默认都是 `off`。绑定成功时对方的课表不可见。
- 「我能看对方」的充分必要条件是**对方**的 `visibility != off`；不是「我设了就能看」。可见性由被查看方单方面决定并可随时刻修改。
- 字段命名固定为 `my_visibility`（我允许对方看到什么）与 `peer_visibility`（对方允许我看到什么），两者都是 `off` / `status_only` / `full` 三档之一。任何响应中都不用嵌套的 `peer.visibility` 形式。

**规则 1 补充：关系状态的取值与取值时机。**

| 取值 | 含义 | 何时返回 |
| --- | --- | --- |
| `none` | 从未建立过关系 | 仅由 `GET /v1/couple/link` 返回；本机从未绑定过，或对方提交的邀请码从未被使用 |
| `active` | 关系有效 | `POST /v1/couple/bind` 成功后，直到任一方解绑或任一方注销 |
| `unbound` | 曾经建立、现已解除 | 任一方 `POST /v1/couple/unbind` 之后、或任一方 `POST /v1/auth/delete` 之后，直到本机建立新关系 |

- `state=none` 与 `state=unbound` 的分工：`none` 是「从来没有」，`unbound` 是「有过但已解除」。客户端对两者的处理一致（都显示未绑定、都清空对方数据缓存），区别只用于「上次已解除」这类提示文案。
- `GET /v1/couple/link` 在 `none` / `unbound` 时仍返回 200，`link_id` 为 `null`、`peer` 为 `null`、双方可见性为 `off`；其余涉及对方数据的接口（`scope=peer` 的拉取、状态点查）在该场景统一返回 404 `COUPLE_NOT_BOUND`，与规则 3、5.4.9 一致。
- 无关系时 `GET /v1/couple/status` 是**唯一例外**：返回 200 + `state=no_data`，不报 404（避免小组件异常，见 5.4.10）。

**规则 2：可见性三档，语义固定。**

| 值 | 含义 | 允许下发的内容 |
| --- | --- | --- |
| `off` | 不共享 | 除关系状态外不下发任何课表内容；`GET /v1/couple/status` 返回 `no_data` |
| `status_only` | 只共享实时状态 | 只允许 `GET /v1/couple/status` 返回白名单字段；`GET /v1/sync/pull?scope=peer` 必须返回 403 `FORBIDDEN_VISIBILITY` |
| `full` | 共享完整课表 | 允许 F2 状态，且允许按 5.4 的字段白名单拉取对方课表 |

**规则 3：解绑与撤回立即生效。**

- 任一方 `POST /v1/couple/unbind` 后，`GET /v1/sync/pull?scope=peer` 与 `GET /v1/couple/status` 立即返回 404 `COUPLE_NOT_BOUND`；客户端必须清空 `status_cache` 与对方课表缓存。
- 任一方把 `visibility` 改为 `off` 时，对方的读取立即返回 403 `FORBIDDEN_VISIBILITY`（状态接口则降级为 `no_data`，不报错，避免小组件异常）。
- 解绑后落败方已缓存的对方数据不做远程擦除承诺（技术上不可保证），但客户端在解绑后必须立即删除本地缓存；服务端在解绑后不得再向任一方下发对方数据。

```json
{

  "state": "active",
```

#### 5.4.8 `POST /v1/sync/push`

请求：

```json
{
  "semester": { "id": "uuid", "name": "2026 秋", "start_date": "2026-09-01", "total_weeks": 20, "week_start_day": 1, "rev": 3 },
  "time_slot_sets": [
    { "id": "uuid", "name": "夏季作息", "rev": 1,
      "slots": [ { "index": 1, "start_minute": 480, "end_minute": 530 } ] }
  ],
  "courses": [
    { "id": "uuid", "semester_id": "uuid", "name": "高等数学", "teacher": "…", "location": "教三 201",
      "color": "#3B82F6", "week_pattern": "custom", "weeks": [1,2,3,5,7], "day_of_week": 1,
      "slot_start": 1, "slot_end": 2, "base_rev": 4, "updated_at": "2026-10-20T02:30:00Z", "deleted": false }
  ],
  "overrides": [
    { "id": "uuid", "course_id": "uuid", "date": "2026-10-06", "type": "cancelled", "base_rev": 1 }
  ]
}
```

响应（**HTTP 状态恒为 200**；`applied` 与 `conflicts` 同时存在于同一响应，见 5.6 冲突处理）：

```json
{
  "applied": [ { "entity": "course", "id": "uuid", "rev": 5 } ],
  "conflicts": [
    {
      "entity": "course",
      "id": "uuid",
      "server_value": { "name": "高等数学", "location": "教三 201" },
      "server_rev": 6,
      "your_value": { "name": "高数（A）", "location": "教三 201" },
      "merged_value": { "name": "高等数学", "location": "教三 201" },
      "losers": ["name"]
    }
  ],
  "cursor": "opaque-cursor",
  "server_time": "2026-10-20T02:41:00Z"
}
```

字段约定：

- `week_pattern` ∈ `all` / `odd` / `even` / `custom`；为 `custom` 时以 `weeks` 数组为准。
- `slot_start` / `slot_end` 指节次序号（从 1 起），不是时刻。
- `start_minute` / `end_minute` 为当日 0 点起的分钟数（0–1439）。
- `base_rev` 是客户端最后一次见到的该实体版本号；服务端版本号从 1 起单调递增。
- `deleted` 为软删除标记，客户端不得物理删除后静默重传。
- `conflicts[]` 的四层语义：`server_value` 是该实体裁决前的服务端版本（三方合并的共同祖先之后的远端值）；`your_value` 是本次提交中**被裁决掉**的本地值；`merged_value` 是服务端最终落库的服务端实体完整状态，也是服务端返回的 `server_rev` 对应的内容；`losers` 列出被裁决掉的字段名。
- 客户端处理 `conflicts[]`：用 `merged_value` 更新本地实体（连同 `server_rev`），把 `your_value` + `losers` 写入 `conflict_log`，并在界面上提示「有字段冲突，可查看／恢复」。不得用 `your_value` 覆盖本地实体，也不得丢弃 `your_value`。
- 同步冲突**不使用 409**：只要 `base_rev` 能对上某一历史版本，服务端必定能按 5.6 的裁决规则给出确定结果，因此永远返回 200 + `conflicts[]`。409 只用于关系状态类冲突（`COUPLE_ALREADY_BOUND`）。

| --- | --- | --- |
| `scope` | 是 | `self`（默认）／`peer`（需 `full` 可见性） |
| `semester_id` | 否 | 限定学期 |
| `since` | 否 | 游标；首次不传 |
| `limit` | 否 | 见 5.9 |

响应：

```json
{
  "items": [ { "entity": "course", "id": "uuid", "rev": 5, "updated_at": "…", "deleted": false, "payload": { } } ],
```

约束：`scope=peer` 且对方 `visibility != full` 时返回 403 `FORBIDDEN_VISIBILITY`（不返回部分数据）；`scope=peer` 且无关系时返回 404 `COUPLE_NOT_BOUND`。

#### 5.4.10 `GET /v1/couple/status`（F2 的唯一数据来源）

查询参数：`at`（可选，ISO 8601；不传则取服务端当前时间）。

`at` 的允许窗口与判定规则（用于消除客户端时钟偏差，不用于查询历史或未来状态）：

- 判定基准是服务端的当前时间 `T`。允许区间为 **[T−5 分钟, T+5 分钟]**。
- `at < T−5min` 或 `at > T+5min` → 返回 400 `BAD_REQUEST`，`details.reason = "at_out_of_window"`，`details.allowed_window_seconds = 300`。
- 客户端只能传「本机时间经 `server_time` 校正后的当前时刻」；不得用 `at` 遍历历史或以未来时间探测对方后续课程。
- 请求不带 `at` 时按 `T` 计算，与传 `at = T` 等价；窗口判定针对客户端显式传入 `at` 的情况。

响应 `data`（成功且有数据时带 `ETag`）：

```json
{
  "state": "in_class",
  "course_name": "高等数学",
  "location": "教三 201",
  "started_at": "2026-10-20T02:00:00Z",
  "ends_at": "2026-10-20T02:50:00Z",
  "next_course_name": "线性代数",
  "next_starts_at": "2026-10-20T04:00:00Z",
  "my_visibility": "off",
  "peer_visibility": "status_only",
  "as_of": "2026-10-20T02:41:00Z",
  "stale_after": 300
}
```

字段语义：

- `state` ∈ `in_class` / `break` / `free` / `no_data`（与 3.2 的四态一一对应，不允许其他取值）。
- `location` 只在对方 `visibility == full` 时返回，否则为 `null`。
- `next_course_name` / `next_starts_at` 在 `free` 或 `no_data` 时为 `null`。
- `my_visibility` 是本机用户对对方设置的可见性，用于展示「你也未共享」这类对称提示。
- `stale_after` 建议客户端多久后重新校时（秒）；客户端在本机可自推状态，此值只影响校时频率，不决定状态展示。
- `no_data` 的判定优先级：无关系 > 解绑 > 对方 `off` > 对方当天无课 > 对方未上传课表。前四种返回 200 + `no_data`（小组件不能因此报错），最后一种也返回 `no_data`。

#### 5.4.11 `POST /v1/couple/events`

用途：注册「变化通知」的送达方式（对应 B1）。通道本身**不是**本接口的契约内容，客户端上报的只是一个通道标识与投递凭据，服务端按标识选择投递实现。

请求：

```json
{ "channel": "<channel_id>", "token": "<delivery-token>", "subscribe": ["peer_schedule_changed", "link_state_changed"] }
```

响应 `{ "channel": "<channel_id>", "subscribed": ["peer_schedule_changed", "link_state_changed"], "expires_at": null }`。

| 字段 | 说明 |
| --- | --- |
| `channel` | 通道标识，**开放字符串**，不是枚举。取值由服务端与客户端约定，至少包括：`vendor`（厂商推送通道）、`self_hosted`（自建长连接）、`none`（不注册推送，客户端只靠拉取）。服务端必须接受未知标识并返回 200，只把该设备标记为「无可用通道」，不得返回错误——避免新增通道时出现客户端与服务端版本耦合 |
| `token` | 该通道对应的投递凭据；`channel=none` 时为 `null` |
| `subscribe` | 订阅的事件类型；服务端对未知事件名忽略并在响应中回显实际生效的列表 |
| `expires_at` | 凭据失效时间；无失效概念时为 `null` |

- 候选通道与取舍（具体选型见 8.2 Q9）：

| 候选通道 | 覆盖面 | 代价 |
| --- | --- | --- |
| 厂商推送通道（各 Android 厂商各自的推送服务） | 国内设备覆盖面最好 | 需要逐厂商申请与配置，接入数量随厂商增加 |
| 自建长连接 | 不依赖第三方，自控 | 需要常驻连接，受省电策略影响，耗电与保活是持续成本 |
| 不注册推送（`none`），仅靠拉取 | 无需任何通道依赖 | 变化延迟取决于拉取时机（见 5.10） |

- 明确不采用**依赖 Google 服务的推送通道**作为唯一手段：本应用面向国内高校用户的 Android 设备，该类服务在很多设备上不可用，会把「对方课表变更后尽快看到」变成不可用功能。
- 推送只做「提醒去拉取」，不承载课表内容；客户端收到事件后走 `GET /v1/sync/pull?scope=peer` 或 `GET /v1/couple/status` 取数据。
- 客户端不得假设推送必达：所有展示必须能在只有拉取（或只有本地推算）的情况下自洽。`channel=none` 是合法状态，不是降级异常。
- 注销/换绑：`DELETE /v1/couple/events` 请求 `{ "channel": "<channel_id>", "token": "<delivery-token>" }` 解除注册（设备卸载、注销账号、解绑时调用）。

#### 5.4.12 `GET /v1/couple/link`

有有效关系时（HTTP 200）：

```json
{
  "link_id": "uuid", "state": "active",
  "peer": { "user_id": "uuid", "display_name": "…" },
  "my_visibility": "status_only", "peer_visibility": "full",
  "bound_at": "2026-10-20T02:41:00Z", "unbound_at": null
}
```

无关系或已解绑时（同为 HTTP 200，不用 404）：

```json
{
  "link_id": null, "state": "none",
  "peer": null,
  "my_visibility": "off", "peer_visibility": "off",
  "bound_at": null, "unbound_at": null
}
```

- `state` ∈ `active` / `unbound` / `none`，取值与时机见 5.3 规则 1 补充。这一条是**唯一**在无关系时返回 200 的关系类接口；它不返回任何对方课表内容，因此不需要 `COUPLE_NOT_BOUND`。
- 请求参数：`link_id`（可选）。不传时返回当前账号的关系状态；传已失效的 `link_id` 时按当前状态返回，不返回 404。

### 5.5 鉴权方式

- 设备匿名注册换取令牌对，不做手机号／第三方账号登录。
- `access_token` 走 `Authorization: Bearer`，有效期 2 小时；过期返回 401 `UNAUTHENTICATED`，客户端用 `refresh_token` 换新令牌后重放原请求（重放必须复用同一 `Idempotency-Key`）。
- `refresh_token` 有效期 90 天、一次性轮换；`POST /v1/auth/refresh` 失败返回 401 `TOKEN_EXPIRED`，客户端必须回到设备注册流程并清除本地令牌。
- 情侣关系的授权**不体现在令牌里**：令牌只代表「我是谁」，不代表「我能看对方」。每次访问对方数据的权限都由服务端按当时的 `visibility` 与关系状态即时判定（规则 1、规则 3），客户端不得缓存授权结论超过一次请求。
- 所有接口都必须同时校验令牌、关系状态、可见性；任一不满足时按 5.8 返回明确错误码，不得返回降级后的空数据（`status` 接口的 `no_data` 除外，见 5.4.10）。

### 5.6 同步时序与冲突处理

**推时序（客户端改动 → 服务端）**

```
1. 本地写库：更新实体 + 写 pending_change（记录 base_rev）
2. 前台时立即尝试 push；离线则排队，联网后按 created_at 升序重放
3. push 正常 → applied 中的实体用返回的 rev 覆盖本地 rev，删除对应 pending_change
4. push 返回 conflicts → 进入冲突流程（见下），不得盲目覆盖
5. 网络 / 5xx / 429 → 保留 pending_change，指数退避重试，复用同一 Idempotency-Key
```

**拉时序（对方改动 → 客户端）**

```
1. 收到 peer_schedule_changed 推送，或进入对方课表页，或轮询到期
2. 用本地 last_cursor 调 GET /v1/sync/pull?scope=peer
3. 逐条按 rev 覆盖本地缓存；cursor 前进；has_more 为 true 则继续
4. 写入 status_cache：用最新课表在本机重算 F2 状态（不等待下一次 status 请求）
5. 触发一次小组件数据下发 + updateWidget
```

**冲突处理（本应用自行定义，服务端与客户端共同实现）**

同类产品普遍不公开冲突规则（2.2），因此这里给出完整规则：

1. **并发模型**：以实体（课程／节次模板／学期／调休项）为粒度做乐观并发，每个实体带单调递增 `rev`。
2. **接受条件**：`base_rev == 服务端当前 rev` → 直接接受，返回新 `rev = base_rev + 1`，写入 `applied[]`。
3. **`base_rev` 不匹配时做字段级合并**：把 `base_rev` 对应的服务端历史版本作为共同祖先，做三方合并。服务端只要能在历史版本中找到 `base_rev`，就一定能算出结果，因此**返回 200 + `conflicts[]`，不返回 409**。
   - 只有本地改过的字段 → 取本地值。
   - 只有远端改过的字段 → 取远端值。
   - 两边都改过同一个字段且值不同 → **规则化裁决**（不允许服务端静默丢弃任一方）：
     - `deleted=true` 优先于任何字段修改（删除胜过编辑）。
     - 双方都是普通字段修改时，比较 `updated_at`，较新者胜。
     - `updated_at` 完全相同时，比较 `X-Device-Id` 的字典序，较大者胜（保证双方算出同一结果，不会来回覆盖）。
   - 裁决结果写入 `merged_value`，被裁决掉的字段名写入 `losers`，被裁决掉的本地值原样写入 `your_value`（响应形态见 5.4.8）。
4. **冲突落败方的处理**：被裁决掉的本地值不得静默丢弃——服务端在 `conflicts[].your_value` 中原样返回，客户端写入 `conflict_log`，并在对方课表／本机课表上给出一条「有字段冲突，可查看」的提示；用户可选择保留服务端版本或恢复本地版本。客户端按 `merged_value` + `server_rev` 更新本地实体。
5. **服务端无法给出结果的唯一情形**：请求里缺少 `base_rev`、`base_rev` 不是整数、或实体 `id`／`semester_id` 引用不存在。这些属于请求本身不合法，按 400 `BAD_REQUEST` 处理（`details.reason` 分别为 `missing_base_rev` / `unknown_entity_ref`），不进入冲突流程。
6. **禁止项**：不得使用「最后写入优先且无记录」的静默覆盖；不得返回 200 但丢弃 `base_rev` 不匹配的实体；不得用 409 表达同步冲突。
7. **幂等**：同一 `Idempotency-Key` 重复提交返回首次结果，不产生第二次 `rev` 自增。

**对方的写入不存在**：客户端不提供写对方数据的通道（与 2.2 中「写入对方日历」的模型相反）；接口层面也没有任何「写 peer 数据」的路径，因此不存在跨账号写冲突，只存在同一账号多设备冲突。

### 5.7 时间格式

| 场景 | 格式 | 示例 | 说明 |
| --- | --- | --- | --- |
| 交互时间戳（`updated_at`、`bound_at`、`as_of`、`ends_at`…） | ISO 8601 / UTC，带 `Z` | `2026-10-20T02:41:00Z` | 客户端展示时按本机时区转换 |
| 日历日期（`start_date`、调课 `date`） | `YYYY-MM-DD` | `2026-09-01` | 不带时区，语义是「当地日历上的这一天」 |
| 节次时刻（`start_minute` / `end_minute`） | 当日 0 点起的整数分钟 | `480` | 避免夏令时与跨时区歧义 |
| 有效期（`expires_at`） | ISO 8601 / UTC | `2026-10-21T02:41:00Z` | 与交互时间戳一致 |

约定：所有接口的时间字段一律按上表，不使用本地化字符串、不使用秒级以外精度（毫秒截断为 0）、不使用 Unix 时间戳。服务端每次响应带 `server_time`，客户端据此校正本地时钟偏差（偏差超过 2 分钟时以服务端时间为准推算 F2 状态）。

### 5.8 错误码

| HTTP | `code` | 触发条件 | 客户端行为 |
| --- | --- | --- | --- |
| 400 | `BAD_REQUEST` | 参数缺失／格式错／`at` 超出允许窗口（±5 分钟，见 5.4.10）／`base_rev` 缺失或非法／实体引用不存在 | 修参数，不重试 |
| 401 | `UNAUTHENTICATED` | 未带令牌或令牌无效 | 走 refresh 后重放（复用幂等键） |
| 401 | `TOKEN_EXPIRED` | `refresh_token` 过期或已轮换 | 回设备注册流程，清本地令牌 |
| 403 | `FORBIDDEN_VISIBILITY` | 对方 `visibility` 不足以完成该请求 | 展示「对方未共享课表」，清对方课表缓存，不重试 |
| 404 | `COUPLE_NOT_BOUND` | 无关系／已解绑（`GET /v1/couple/link` 与 `GET /v1/couple/status` 除外，两者返回 200） | 清情侣缓存，入口切回未绑定态 |
| 409 | `COUPLE_ALREADY_BOUND` | 己方已有 `active` 关系 | 提示先解绑 |
| 410 | `INVITE_EXPIRED` | 邀请码过期／已使用 | 重新生成邀请码 |
| 429 | `RATE_LIMITED` | 超出限流 | 按 `Retry-After` 退避，不并发重试 |
| 5xx | `SERVER_ERROR` | 服务端异常 | 保留本地队列，指数退避重试；本地功能不受影响 |

约定：错误响应不计入 `data`；`retryable` 明确标记是否可重试；错误码一经公开不得改语义，只能新增。**409 只用于关系状态冲突**（`COUPLE_ALREADY_BOUND`）；同步冲突一律走 200 + `conflicts[]`（见 5.4.8、5.6），因此不设 `REV_CONFLICT` 这类冲突错误码。

### 5.9 分页约定

- 采用**游标分页**，不用页码：请求 `limit`（默认 200，最大 500），响应 `next_cursor` + `has_more`。
- 游标是**不透明字符串**，客户端不得解析或构造；游标与 `scope` 绑定，跨 `scope` 使用返回 400 `BAD_REQUEST`。
- `GET /v1/sync/pull` 的游标只前进：即使中间有实体被删除，游标也单调递增；客户端发现本地数据与游标不连续时，以 `has_more` 为 true 连续拉取直到收敛。
- 顺序保证：同一 `scope` 内按 `rev` 升序返回，客户端按序应用，天然处理「先改后删」。

### 5.10 客户端侧配额与降级要求（接口使用约定）

- `GET /v1/couple/status` 的轮询间隔不短于 60 秒，且优先用 `ETag` 命中 304；小组件的分钟级推进由本地推算完成，不靠缩短轮询周期。
- 对方课表 `sync/pull` 只在收到变更事件、进入对方课表页、或距上次拉取超过 30 分钟时触发，不做定时常驻轮询。
- 所有请求失败都必须落到「本地已有数据继续可用」这一结果上；接口可用性不作为单人功能的依赖。

### 6.5 v0.5 账号与同步

- **交付物**：设备注册与令牌刷新；本地变更队列与幂等重试（`Idempotency-Key` 语义）；`sync/push`、`sync/pull`；游标管理；5.6 的冲突合并与 `conflict_log` 提示界面。
- **验收点（账号与令牌）**：首次使用自动完成设备注册；令牌过期后自动续期并重放原请求，用户无感知；卸载重装后重新注册得到新设备身份且不覆盖云端已有课表。
- **验收点（多设备同步）**：同一账号两台设备 A／B，A 改课表后 B 在联网下拉后看到变更。
- **验收点（冲突合并）**：两端同时改同一门课的不同字段后合并结果字段级正确且不丢改动；两端同时改同一字段后套用 5.6 的裁决规则，结果与规则一致，且落败值可在冲突提示中查看并恢复。
- **验收点（幂等与补传）**：断网改动后联网自动补传；同一 `Idempotency-Key` 重复提交（含主动重放一次相同请求）后服务端只产生一次 `rev` 自增、客户端不出现重复课程。
- **验收点（关系状态口径）**：`GET /v1/couple/link` 在 `none` / `unbound` 两种状态下均返回 200 且不返回对方数据；`GET /v1/couple/status` 在无关系时返回 200 + `no_data`；`scope=peer` 的拉取在无关系时返回 404 `COUPLE_NOT_BOUND`。

### 6.6 v1.0 情侣特色功能与开源发布

- **验收点（发布）**：仓库含许可证、贡献指南、隐私说明与构建说明；按构建说明在干净环境能构建出可安装包；应用内无法进入任何已列入 Out of scope（3.5）的情侣玩法与单人附加工具。

## 7. 开源治理

### 7.1 许可证

- 本应用采用 **Apache-2.0**，与作为参考的公开开源课表项目一致。
- **只借鉴设计，不复制代码**：可参照的同类项目中存在以 GPL-3.0／AGPL-3.0 许可发布者（例如已实现双人课表比对的公开 Flutter 项目为 GPL-3.0-or-later），复制其代码会引入强著佐权义务，与本项目的 Apache-2.0 目标冲突。因此第 4 章的所有架构决定均按自行实现书写。
- 依赖许可审查：`home_widget` 为 BSD-3-Clause，与 Apache-2.0 兼容；高德定位 SDK 为闭源二进制，未取得其开源许可声明，其使用受技术服务许可约束（见 7.5），不列入「可复用代码」来源；Open-Meteo 的客户端调用本身不构成许可障碍。
- 仓库内维护第三方许可清单，列出直接依赖的包名、版本、许可证与商标声明。

### 7.2 贡献流程

- 一切改动经 Pull Request；主干保持可构建。
- PR 必须说明：改了什么、为什么、如何验证（可复现步骤）。
- 教务适配脚本**不放在客户端仓库**：适配内容按社区贡献方式维护在独立仓库，客户端只提供插件式入口与格式约定，避免客户端仓库被适配数据淹没。
- 提交信息只写结论，不写过程。
- 新增平台权限、新增网络出口、新增第三方依赖必须单独说明理由与隐私影响。

### 7.3 隐私说明

必须在仓库与应用内同时提供，且内容与实现一致：

- **不采集行为数据**：不上报定位轨迹、不上报用机记录、不上报「对方是否打开了应用」。F2 的状态完全由课表数据与时间推算。
- **单人使用不联网**：不使用情侣功能时，除天气取值外不发生任何网络请求；不建立账号也能使用全部单人功能。
- **授权即撤即停**：可见性三档由被查看方单独设置，随时可改；解绑后对方立即无法读取（对应 5.3 规则 1、规则 3）。
- **最小化下发**：`GET /v1/couple/status` 只返回 F2 展示所需的字段；地点字段只在 `full` 档下发。
- **数据归属与删除**：注销账号删除云端副本并解除关系（`POST /v1/auth/delete`）；解绑后客户端立即清空对方数据缓存。
- **耗电披露**：应用内说明后台保活与刷新对续航的影响，并说明不授予后台权限会导致小组件与提醒不准。
- 不做「不可单方解除」的关系绑定。

### 7.4 密钥管理

- **任何真实密钥都不入库**。仓库只提交占位符与说明文档。
- 高德 Key 由使用者自备，构建期注入：从构建机本地未跟踪的配置文件或 CI 密钥变量读入，写入构建产物。`.gitignore` 覆盖本地密钥文件；提交前检查不得包含真实 key。
- 高德 Android 平台 Key 必须绑定 SHA1 与包名，且**1 Key 只能用于一个应用**（debug 与 release 的 SHA1 不同，发布包要按发布 keystore 重新配置），因此它必然随 APK 分发，属**客户端凭据**，只能构建期注入。
- 高德 Web 服务类型的 Key 属**服务端凭据**，只应放在自有服务端，**不下发客户端、不写进 App**。
- Open-Meteo 免费档无需密钥；若将来使用付费档，其 apikey 同样按「能放服务端就不放客户端」的原则处理。
- CI 只从加密变量读取密钥；构建日志不得回显密钥；PR 中禁止出现真实 key。

### 7.5 数据源合规

- **Open-Meteo**：免费档明确不允许商用，限流 600 次/分、5,000 次/时、10,000 次/日、300,000 次/月；数据为 CC BY 4.0，要求署名、给出许可链接，且**任何展示 Open-Meteo 数据的位置旁必须给出 `https://open-meteo.com/` 链接**。本应用「非商用」定位与该免费档一致；一旦涉及商用必须改用付费档。
- **高德**：官方明确，未购买技术服务许可时平台提供的 KEY 与配额**仅供短期、少量的测试目的**；面向公众提供、上架分发、收费或投放广告、长期或大量调用均构成未许可使用。因此上线分发前必须解决高德的技术服务许可问题（列入第 8 章 R7）。
- 由于所用免费数据源不允许商用，应用内不得出现广告、付费入口或商业化导流。

### 7.6 构建与发布

- 仓库提供从零开始的构建说明：环境要求、密钥注入步骤、签名配置、产物位置。
- 提供可复现的发布构建脚本，并说明签名校验方式；签名密钥同样不入库，由构建者自备。
- 发布产物以源码构建为主；在高德许可与商店合规前置条件未解决前不投递应用商店。
- 版本号与路线图里程碑对应；每个里程碑打 tag 并附变更摘要。
- 发布前检查清单：许可证与第三方许可清单完整、隐私说明已更新、仓库无真实密钥、天气署名链接存在、权限清单与实现一致。

## 8. 风险与未决问题

### 8.1 风险清单

| # | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| R1 | 差异点被同行追上：课表共享与多人比对已有先例，实时状态呈现容易被复制 | 卖点弱化 | 把「状态推算的准确性与低功耗」「小组件默认常驻体验」做深，而不是堆功能；状态推算实现为 domain 层纯函数并覆盖测试 |
| R2 | 教务适配是持续维护成本，覆盖数字对外无法承诺 | 录入门槛高、口碑不稳 | 四条录入通道并行（教务／JSON／ICS／分享码），适配脚本社区化 |

| R4 | 小组件在厂商省电策略下不刷新 | F2 价值失效 | 分钟级推进由本地推算完成、不依赖联网刷新；提供后台授权引导；处理开机／改时间／改时区重排 |

| R6 | 厂商「岛／胶囊」适配无官方开发者文档，厂商省电策略下的保活效果不可控 | 预期落空、返工 | 只按已核实的 promoted ongoing notifications 实现；HyperOS 焦点通知／超级岛列为待验证适配目标，作为条件性工作项；v1.0 只验收厂商授权引导项存在与跳转可达，不把实际常驻效果列为验收点（见 6.4、6.6） |

| R8 | 天气与定位的配额与耗电 | 请求失败、续航下降 | 天气按经纬度与日期缓存去重、只取展示字段；定位仅前台一次性触发；限流按 5.10 退避 |

| R10 | 邀请码／绑定被滥用 | 陌生人建立关系 | 邀请码一次性、24 小时有效；一个用户同时仅一个 `active` 关系 |

| R12 | 非商用定位与依赖的数据条款冲突 | 合规风险 | 应用内无广告、无付费入口；只使用允许非商用免费档的数据源；新增数据源前先核对许可 |
